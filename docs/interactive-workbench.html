Native workbench and live source-first REL

The native Workbench, Inspector and Worker are separately compiled Lean user programs. They receive commands through kernel IPC and call the user-mode Objects service under their own process instance and declared rights. The host control tool transports requests; it does not implement their object operations. Personal object state remains in guest RAM unless the separate encrypted Objects retention path is explicitly authorized.

Native client commands

Build the running platform with ./lt live-build. The build also creates build/live/workbench.bin, inspector.bin and worker.bin. Publish and install these through the same publisher envelope and exact-capability approval workflow as any application; no client release is embedded in the boot image. See the command guide.

ClientOperationActual behavior
Workbench20, handle, argument A=1 or 2Streams an uppercase or lowercase ROT13 transformation into a new immutable object revision.
Workbench23, handle, A=offset, B=bytes deleted, replacement payloadCreates a revision containing the unchanged prefix, arbitrary replacement bytes and unchanged suffix. Replacement is at most 512 bytes; the resulting object is at most 65,536 bytes. This supports insertion, deletion and arbitrary bounded edits rather than one fixed transformation.
Inspector22, handleReturns actual metadata, type, parent object identity, length, granted rights and SHA-256.
Worker21, handleStreams content and computes ASCII-whitespace word count and LF count. Reply words 1, 2 and 3 contain words, bytes and LFs; the payload contains the content SHA-256.

All clients can forward Objects operations 1–14 for direct API use and negative checks. The service still checks each client's actual kernel-supplied rights and scoped handle. A read-only Inspector cannot obtain revision authority by calling the raw create or commit opcodes. Client command endpoints accept only the trusted launcher's kernel-supplied administrator identity.

Grant a source handle to the Workbench with rights 13 (read, revise and share). Its successful edit returns a new handle explicitly delegated back to the launcher. Existing source bytes remain unchanged. The owner grant reflects the client's declared rights; it cannot manufacture rights that were not approved. Process instance numbers and handles are session-local, and stopped/restarted process instances require fresh grants.

# Use the exact process instance and object handles printed by your session:
./lt ctl --socket /tmp/lt.sock share "$SOURCE_HANDLE" --to "$WORKBENCH_INSTANCE" --rights 13
./lt ctl --socket /tmp/lt.sock app "$WORKBENCH_INSTANCE" --operation 23 \
  --handle "$WORKBENCH_SOURCE_GRANT" --a 10 --b 3 --data replacement.bin
./lt ctl --socket /tmp/lt.sock metadata "$NEW_LAUNCHER_HANDLE"
./lt ctl --socket /tmp/lt.sock export "$NEW_LAUNCHER_HANDLE" --output edited.bin

Restricted source-first REL

./lt rel-live accepts the same explicit source grammar as tools/rel.py: one Python transform_byte function that conditionally rotates a bounded interval of byte values. Imports, calls, arbitrary loops, attributes and other source effects are rejected. Extraction compares the validated original source with the semantic model on all 256 byte values. This is a narrow source-first component workflow, not a general Python compiler or the complete REL application.

The live path imports the actual source bytes as a Source object and the canonical semantic record as its child Object. An edit uses Workbench operation 23 inside the running guest. The tool then exports and validates the resulting bytes, SHA-256 and parent identity before updating an explicitly requested host project snapshot. Build reads the authoritative running object again; changing a local JSON head alone does not change the selected guest object.

# A live session and an installed native Workbench must already be running.
mkdir -p build/live-rel
./lt rel-live import examples/rel/rotation.py --socket /tmp/lt.sock \
  --output build/live-rel/project --license CC0-1.0 \
  --authorization 'Authorized use of the repository local source fixture'
./lt rel-live edit build/live-rel/project --socket /tmp/lt.sock \
  --workbench "$WORKBENCH_INSTANCE" --shift 7

# Generate your own explicit publisher key with OS entropy; keep it on the host.
./lt release keygen --private build/live-rel/publisher.pem --public build/live-rel/publisher-public.pem
./lt rel-live build build/live-rel/project --socket /tmp/lt.sock \
  --sign-key build/live-rel/publisher.pem --name rel-rotation --version 1.0.0 \
  --output build/live-rel/rotation-1.ltexe

Build generates real Lean functions from the selected semantic values, compiles them with the normal freestanding backend and signs a publisher-owned release envelope. The native component accepts operation 24 and transforms arbitrary brokered input up to 64 KiB in 512-byte chunks. It never substitutes a host-computed result. The same project name retains a release-parent chain; later builds must increase the version and use the same publisher identity or explicitly use a separately named fork.

# Inspect and authorize the exact produced release before activation:
./lt ctl --socket /tmp/lt.sock trust --project rel-rotation --public build/live-rel/publisher-public.pem
./lt ctl --socket /tmp/lt.sock inspect build/live-rel/rotation-1.ltexe
./lt ctl --socket /tmp/lt.sock approve "$RELEASE_ID" --rights 127
./lt ctl --socket /tmp/lt.sock activate
./lt ctl --socket /tmp/lt.sock start "$RELEASE_SLOT"

# Use the resulting native process instance:
./lt rel-live compare build/live-rel/project --socket /tmp/lt.sock --instance "$REL_INSTANCE"
./lt rel-live run build/live-rel/project --socket /tmp/lt.sock --instance "$REL_INSTANCE" \
  --input authorized-input.bin --output authorized-output.bin
./lt rel-live export build/live-rel/project --socket /tmp/lt.sock \
  --output build/live-rel/exported-project --release build/live-rel/rotation-1.ltexe \
  --public-key build/live-rel/publisher-public.pem

compare actually sends all 256 byte values to the selected running native process through Objects IPC and checks its exported result against the edited semantic model. Its evidence distinguishes original extraction equivalence from intentional semantic changes. run accepts arbitrary bounded input, preserves brokered source lineage and writes plaintext output only to an explicitly selected export path. export preserves source, semantic revisions, verified authoritative bytes, lineage and optional authenticated release files. Its reconstruct/ directory includes the generated Lean and normal build inputs with a bounded JSON reconstruction recipe.

Limits and trust boundary

The user-mode service, IPC, generated native computation and local release path are executable development components. Source parsing, semantic validation, build orchestration and publisher signing remain disclosed host tooling. Host project snapshots and explicit exports are ordinary source artifacts; they are not an encrypted personal vault and do not establish physical external-drive erasure. After an ephemeral reset, their old handles must not be reused; reimport source to obtain new scoped authority.

REL records are limited to 4 KiB, source import to 16 KiB, byte input/output to 64 KiB and semantic ancestry to 32 revisions. Native code is limited to 64 KiB and uses the current scalar/effects runtime subset. A SHA-256 proves content integrity, not publisher identity; publisher signatures, technical compatibility and local capability approval remain separate checks. Source-to-binary compilation is unverified. Comparing all byte values proves the selected finite transform behavior, not arbitrary program safety, independent-builder reproducibility or full MVP release-gate completion.
