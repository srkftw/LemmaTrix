29 October 2026. Implementation branch codex/networked-forge descends from reviewed implementation 2edb0dfd06794985397023b756d8864c66103df0. The checkout was not reset to documentation-only main. Campaign 003 remains preserved history, not newly executed evidence. This record describes actual local development execution and its limits, without marking an entire MVP release gate complete.

Two native users can build an explicitly selected snapshot, exchange its signed Release/source/evidence, inspect chosen-federation admission and precise execution authority, run it, create a distinct fork, edit both source and a consumed resource, build/sign under the selected fork publisher, receive a next generation and explicitly roll back. Two independently retained seed stores can supply both signed fork generations after the publisher and first seed are absent. A separately configured builder and verifier actually compiled the same source in distinct sandboxes and returned identical bytes over the guest protocol.

Federation, metadata and failure behavior

Physical creator F11 sent the exact original signed 14-node/127,788-byte closure to a normal headless registry node. The isolated guest Registry evaluated actual publisher signature, graph/code material and policy; its distinct federation signer signed the immutable decision. Portable admitted Native classification 2; independently configured restricted rejected input authority (classification 3/reason 4). After publisher exit, fresh readers discovered and rendered actual federation/publisher/source/evidence/rights information. Portable permitted explicit F5; restricted denied it without importing a graph. Unsigned decisions were not accepted as listings or Fetch authority.

Registry persists a bounded 16-record signed catalog separately from seed content. A restarted catalog can expose actual verified metadata with zero available graph records; native F5 displays METADATA ONLY - CHOOSE SEED. Recovery uses the same own backing/namespace through normal node commands, and does not replay source files. Tampered signatures, a different federation key and a known superseded/revoked sequence are rejected. Sequence freshness is knowledge-relative; there is no trusted global clock or unseen-revocation oracle.

The combined final integration journey recovered the fork generation from seed2’s own backing, published it through native F11 to a new isolated federation, restarted that registry from its own catalog store, and discovered metadata from a fresh reader. The reader then selected a separately pinned seed2 relationship with fresh keys/grants; the same public federation admission was reverified for the exact immutable root. Remote computation and assurance

The real builder and separate verifier each received the same exact source/toolchain/recipe under a unique approved contract, CPU 60s/wall 120s/output 64KiB. Each executed Lean/LLVM inside its own key-free network-disabled namespace sandbox and returned actual38,320-byte artifacts through native graph Fetch. Byte comparison matched the artifact SHA256 above. Original publisher signatures, relationship-authenticated builder assertions, actual reproduction, tests, named source proofs and unknowns remain separate labels.

The normal headless builder/verifier ingestion path additionally starts without display/input rights or preloaded source. Physical client F7 explicitly uploads the frozen source; actual guest validation precedes Ready17, then the contract request and quote; F10 alone queues execution. Focused role tests inspect the actual frozen job via the executor interface and cancel it without repeating compilers. Wrong role, truncation, root substitution and duplicate requests are checked. Existing validated source may be reused for a fresh nonce after cancellation; it cannot inherit execution approval. The one real compiler pair used the earlier graphical-provider source-fetch path on its recorded image; this later headless integration does not relabel that pair as a new execution.

The integration image also completed QEMU-to-native-x86 graphical Forge transfer/approval/run and QEMU-to-ARM64 public-SDK transfer/approval/run using the same signed application. ARM64 assembly executed under qemu-aarch64; its 59,648-byte headless fixture exercises public protocol/import APIs, while trusted graphical controls approve and start the actual application. This is not a claim that the complete graphical Forge client journey passed on ARM64.

Reproduction commands and native actions

The full reproducible setup, package rights, peer/node commands and native key sequence are in the operator/developer guide. Use separate backing, role/network/federation/publisher keys and config for each operator. Numeric addresses can name separate hosts; this campaign used local endpoints. No public service was deployed and no repository-wide license was invented.
