Intentional server retention, format 1

The Lean Guest.ServerStore module runs inside the isolated Vault/device broker (service 3). It provides a separate, unencrypted operator store on a deliberately attached lt-server-v1 block device. Its namespace grant authorizes a particular caller incarnation, role, namespace digest and byte quota. It does not use the personal Objects unlock key, imply personal retention or restore application signing/installation authority.

Eight namespaces each retain at most one MiB of committed content with two transactional generations. A registry, seed, builder or verifier role number labels the operator grant; this byte-store API does not itself implement those application policies. The native Forge archive consumes it for exact selected graph closure retention and recovery. Metadata, object availability and federation admission remain different assertions.

Setup and authority

./lt server-store init /explicit/seed-one.img
./lt run --backend qemu --socket /tmp/seed.sock \
  --network-listen 127.0.0.1:19431 --server-store /explicit/seed-one.img
./lt server-store mount --socket /tmp/seed.sock
./lt server-store permit --socket /tmp/seed.sock --instance FORGE_INSTANCE \
  --namespace NAMESPACE_SHA256 --role seed --bytes 1048576
./lt forge --socket /tmp/seed.sock --instance FORGE_INSTANCE configure \
  --credentials /explicit/seed.credential --role seed --store-grant GRANT
./lt server-store revoke --socket /tmp/seed.sock --grant GRANT

Provisioning exclusively creates a 33,088-sector, 16,941,056-byte development image and flushes its format header. Existing paths are refused. The selected device must advertise its exact versioned purpose serial through virtio GET_ID. An unknown or duplicate purpose is not mounted. The personal vault serial is lt-objects-v1; attaching both cannot redirect a server write into personal backing. --server-store-readonly mounts an existing server image for read-only failure/recovery checks.

Only management can mount, grant or revoke. Normal callers need signed right 2048, server.store, plus a fresh server-store grant. A package with display/input authority has neither. A restart invalidates old caller/grant handles; unattended role startup must explicitly provision a fresh grant from its selected operator configuration. Revocation prevents future serving under that grant and cannot erase copies already distributed.

Server SDK operations

Endpoint 3 uses ABI2 messages and eight little-endian UInt64 header words ending in version 1. The same broker serializes storage transactions; application code never sees a physical block address.

OperationBehavior
230 / 231 / 239Administrative mount; authorize role/namespace/quota to a caller; revoke grant.
232 beginGrant, intended byte length and expected SHA-256. One caller-bound inactive-bank stage.
233 appendOwned transaction, exact sequential offset, at most 512 bytes. The last chunk may be partial.
234 commitRequire complete length and actual digest. Flush payload and index, publish a checked root sector, then flush.
235 cancelAbandon private inactive-bank work; retain the last complete generation.
236 describe / 237 readGrant-scoped generation, length and hash; bounded reads checked against the committed per-4-KiB index.
238 progressActual accepted stage offset/length. This is not a graph publication receipt.

Quota, wrong owner, stale handle, misordered append, short device I/O, write failure and failed flush are explicit failures. Dead-owner stages are reclaimed. The server retains the last committed generation; it never treats an incomplete stage as current. The theorem incomplete_never_commits covers the pure complete/digest commit predicate used here, with explicit assumptions; it does not prove hardware persistence or the whole imperative driver.

On-device transactions and recovery

Sector 0 contains magic 0x31524f5453544c, format 1 and sector count 33,088, with zero reserved bytes. Namespace slot s has alternating commit roots at sectors 8+2*s and 9+2*s. A root commits magic 0x3152565253544c, format, slot, monotonic generation, content length, role, namespace SHA-256, content SHA-256, index SHA-256 and a root-header SHA-256; unused bytes are zero.

Two 2,064-sector banks per slot start at 64+s*4128. Each holds one MiB of payload plus an 8-KiB index of 4-KiB page digests. The alternate bank receives new bytes before any root is published. On mount/describe, the guest validates both roots and their indexes, selecting the newest complete valid root or falling back to its valid predecessor. Each actual read authenticates the complete relevant page against that index. The native graph importer independently validates canonical objects and selected root closure before exposing recovered project capabilities.

A failed flush after a root write has an explicitly uncertain device-persistence outcome; the last complete old or new root is selected after restart. Regular-file fsync evidence is not proof of physical drive durability, power-loss behavior, malicious whole-device rollback resistance or encryption. Root/index hashes provide corruption checking, not operator authentication. Protect backing and unattended credentials under the operator's own access policy.

Forge archive 2

Forge F8 freezes the selected root, enumerates only its permitted closure, streams a version-2 bundle and explicitly commits it under the separately granted server namespace. F9 first displays the actual stored name/head; a second F9 imports the selected stored closure through native Import-v1. A headless seed may explicitly authorize --recover-and-seed during startup. This reconstructs the guest graph from its own block store and advertises that retained root. No host directory replays graph nodes.

The bundle has a 192-byte header (magic 0x324c444e42544c, version 2, count, payload-byte sum, head ID, name length, name and zero reserved bytes), then 128-byte records (kind, length, node schema, absolute payload offset, canonical ID, predecessor ID and payload hash), then actual payloads. Local handles and approvals are absent. Index storage and 512-byte scratch buffers are bounded; the archive is not loaded into one giant application arena.

At most 24 graph records and one MiB are supported by the current network/client importer profile. Existing 64-KiB record limits remain; aggregate content can exceed that size. Durable resumed chunk transfer, multiple independently queried repositories, automatic durable build-job recovery and signed federation catalogs remain separate work.
