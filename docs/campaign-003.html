Reproduce the workflow

The complete command guide supplies publisher provisioning, standalone package creation, all controls and the one-shot build/sign boundary. These are the normal entry points; no particular developer package-store path is required:

./lt setup
./lt doctor
./lt build
./lt emulators
./lt vault-init build/objects-v2.img --sectors 24576 --key-out build/objects.key
./lt run --backend qemu --socket /tmp/lt.sock --graphics /tmp/lt.qmp \
 --display gtk --vault build/objects-v2.img
# In another terminal, after provisioning/staging the separately signed editor:
./lt project --socket /tmp/lt.sock import examples/creator --name creator
./lt ctl --socket /tmp/lt.sock trust --project creator --public build/publisher.pub
./lt project --socket /tmp/lt.sock serve --project creator \
 --sign-key build/publisher.pem --version 1.0.0 --output build/creator-worker
# Native controls: Shift-F2 select project; F3 file; F4 commit; F5 build.
# F6 diagnostic/Inspector; Ctrl-E accent.txt schema editor; F12/Enter approve.
# Alt-F9 lifecycle; B explicit rollback. F10 requests exact snapshot approval.
./lt ctl --socket /tmp/lt.sock vault unlock --key build/objects.key
# Restart with that same vault, unlock, then:
./lt project-vault --socket /tmp/lt.sock recover
# Assembly backend and its disclosed raw-pixel adapter:
./lt run --backend x86_64 --socket /tmp/lt.sock --graphics /tmp/lt-display
./lt display --graphics /tmp/lt-display
# Use --backend aarch64 for the independent ARM64 assembly implementation.

Import, initial publisher provisioning and vault unlock/recovery use explicit bootstrap byte/management adapters. Ordinary typing, navigation, commits, build requests, diagnostics, exact install approvals, lifecycle/rollback and exact retention approvals use native controls. The persistent worker handles subsequent F5 jobs without a per-build UART command. It is restricted to the explicitly selected project name; a foreign job is rejected before source export or signing. Without --vault, the same editing/build/run session is explicitly ephemeral. The presenter requires a Python installation with Tk; the system Python in this environment lacks it, while the pinned Python 3.14/Tk 9 component check succeeded.

Engineering boundaries and assurance

Lean guest code implements the kernel and capability checks, device policy, compositor, trusted chrome, editor, Text Tools and Creator computation, Objects graph, build-job service, Launcher signature/approval transitions, vault policy and ChaCha20-Poly1305 storage. Assembly implements startup/traps/primitives and the independently authored x86-64/AArch64 CPU/device emulators. Host adapters carry raw pixel/event, block, entropy and explicitly authorized object bytes. Host Lean/LLVM elaboration/code generation/linking run in a bounded Linux namespace/chroot sandbox; a separate, explicitly chosen publisher key signs afterward. The signer key is absent from compiler input, guest memory and retained graph data.

The resource/runtime profile is versioned and signed. Profile 2 gives bounded 256 KiB RX code, 64 KiB data including a reusable 32 KiB constructor heap, 16 KiB guarded stack and 2 MiB private RW/NX arena. Applications own bounded clipped surfaces and current-incarnation handles, without global display memory or unchecked DMA. Structured constructors carry tags, scalar fields and owned references; unsupported closure/upstream heap forms fail explicitly. The runtime is a useful subset, not the general upstream Lean runtime.

Remaining TCB includes host OS/hypervisor and I/O adapters, firmware/QEMU or the assembly machine implementation, Lean elaborator/optimizer, custom RV64 lowering and structured allocator, LLVM assembler/linker, startup/primitives, kernel mapping/device validation, guest services, cryptography, entropy, publisher provisioning/signing and physical storage/flush behavior. Source-level transition lemmas remain scoped to their enumerated assumptions; no compiler-correctness, universal isolation or source-to-binary proof follows from them. Present source/evidence consistency, publisher authentication, builder assertions, technical compatibility, local execution approval, catalog admission and federation membership remain distinct.
