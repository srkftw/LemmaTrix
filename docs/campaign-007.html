Implemented authority boundaries

Guest.Identity is an installable, statically linked native profile2 package. It runs in one existing ordinary process slot7–11, with exactly zero package rights. Its private 2-MiB arena holds at most eight independent 32-byte seeds and sixteen one-use signing approvals. It has no Network, stream device, Objects, Vault, block device, display, input, console or administrative authority. The kernel's role1 registration permits only seed-sized entropy through syscall130. The host receives public descriptors and certificates, never these seeds. Existing RSA verification and bootstrap package publication remain separate.

Each creation obtains fresh entropy inside its own guest. Project1, Messenger contact-certification2, node3 and receipt4 scopes use separately generated keys, explicit nonzero federation and purpose commitments, and independent handles. Identical scope labels do not reuse a seed. Only contact certification under role2 and service declaration under role3 are enabled. Project publication and receipt signing remain unavailable; creating their public identity descriptors does not implement either consumer. The Messenger descriptor signer is not an X3DH/XEdDSA messaging identity or a ratchet key. Joining scopes requires a future explicit linking operation; no global directory is created.

Only the kernel-authenticated administrative Launcher can create, export, authorize, revoke or lock keys. Public export remains administrative so an application cannot enumerate separate scopes by guessing handles. An ordinary package needs both an exact operation binding and a one-use approval naming its full incarnation, selected key, key generation, current operation402 binding generation, purpose, body length and exact SHA-256 body commitment. Typed validation rejects other body formats. There is no raw signing or private-key-export operation. Revocation/rebinding cannot revive an old approval. Cancellation can consume an approval without producing a certificate.

The broker rechecks the current kernel request before and after secret work. Cancellation after an operation has committed does not undo that operation; unused approvals can be cancelled explicitly or removed with the key/lock. Authorize checks again before leaving a live approval. Failure and cancellation clear temporary state. Explicit primitive scratch, expanded scalars and intermediate points are cleared. The compiler emits fixed-frame cleanup for Guest.Ed25519.*, Guest.Noise25519.* and Guest.SHA512.*, including error returns, and clears temporary/argument registers apart from the result. Teardown erases the entire arena, data, guarded stack, input and queued payloads. A compromised host can still inspect guest memory and input/output; this is not host-resistant key custody or certified erasure.

Kernel service registry v1

The supervisor-only registry has four role slots and 32 exact operation grants. A registration pins the actual service incarnation, actual admitted service release identity, actual caller incarnation, actual admitted caller release identity, operation and a monotonically increasing revocation generation. Built-in callers use a checked zero release sentinel. PID aliases, role strings and caller-provided rights are not credentials. Installed role1 services must use profile2 and exactly zero package rights. The kernel rechecks queued delivery and reply against the binding; revoke/replace/termination removes pending grants and payloads. A revoked registered target cannot regain generic Launcher/Compositor bypass privileges. Existing built-in broker paths retain their prior contracts.

Primitive and certificate formats

The signer uses pure Ed25519 from RFC8032, January2017, SHA-512 and fixed-count scalar/field arithmetic with mask selection and no secret-indexed tables. Verification rejects noncanonical A/R/S, negative zero, invalid square roots and small-order A/R, and checks the exact uncofactored equation. It does not claim full prime-subgroup validation, Ed25519ctx, XEdDSA, Signal interoperability, post-quantum security, independent audit or a constant-time proof. Generated RV64 control flow and accesses were inspected for the selected routines; CPU multiply timing, the compiler, runtime, emulator, entropy device and host remain assumptions. The crypto execution record pins separate vector-probe images.

All certificate integers are little-endian UInt64; fixed-size opaque commitments/keys are32 bytes. Identity descriptor256 contains magic 0x314449544c, version1, role, key generation, federation32 at32, scope32 at64, public key32 at96, signature profile1 at128, explicit-revocation validity policy1 at136, zero48, and a64-byte signature over the first192 bytes. Export adds SHA-256 of those192 bytes as an inspectable fingerprint. A self-signed descriptor is not evidence of a person's identity.

One-use certification signs a canonical160-byte frame followed by exactly the approved body. The frame contains magic 0x31474953544c, version1, key role, purpose, key generation, body length, federation32 at48, scope32 at80, signer public key32 at112 and zero16. The64-byte signature follows the body. The API has no private-message, project-message or transcript operation, and adds no public signed conversation event store. Approved opaque declaration fields are not an end-to-end messaging protocol.

The signed image commitment is an operator declaration, not measured attestation. The new Ed25519 declaration does not replace PeerDescription's existing client-specific RSA mode3 enrollment or authenticate a new network relationship. Relay/mailbox kinds are deliberately rejected until their complete enrollment and network protocols exist. Local key revocation prevents future broker use; it does not recall exported certificates or implement remote revocation distribution. No mailbox acceptance receipt was generated.

Native SDK and commands

Guest.IdentitySDK discovers the current typed endpoint before every call. Operations:400 create,401 administrative selected public export,402 certify approved body,403 revoke selected key,404 lock/erase all keys,405 authorize one exact use,406 bounded status,407 cancel selected approval. Header/schema follow existing LiveSDK-v1 eight-word requests. Status1 denies authority,2 rejects format,3 indicates stale/revoked state,4 capacity,6 entropy unavailable,7 unsupported operation. Transport errors remain the SDK's all-ones error. There is no automatic fallback or raw-key API.

HEX32 means an explicitly chosen nonzero64-digit commitment. start admits the selected signed rights-zero package and binds Launcher operations400–407; its output identifies the exact service incarnation/release. Additional application bindings require both exact admitted release identities through identity bind. A permit names its actual intended requester: the CLI can consume only a permit issued to the Launcher; an ordinary native client consumes its own permit through SDK402. Certificate bodies follow the table, not unrestricted prose. Running the commands in separate guest processes creates independent credentials; no central private identity key file is produced. Existing publisher bootstrap remains host RSA, disclosed separately from native identity generation.

Retention, resources and outstanding dependencies

All new personal identity state is ephemeral. Lock, signer termination and guest restart destroy seeds, approvals and handles; there is no identity backup/import or retained recovery operation. Public files explicitly exported by the user remain files and may link the chosen scopes. Objects domain3 behavior and formats are unchanged. Messenger domain2 and Wallet domain1 remain denied by the existing VaultPolicy proofs. Enabling domain2 without an isolated key/state owner, nonce allocation, atomic commit/recovery and old-backup fresh-session handling would not implement the requested recovery contract.

The eight-key/sixteen-approval limits and 32-grant registry are fixed. Cancelling or consuming an approval reclaims its row; revoking a key wipes its seed and approvals. Serial counters do not wrap; exhaustion denies new handles. Handle derivation includes the full process incarnation and its randomized32-bit boot epoch, with finite local serials and reserved values denied. These ephemeral names are not permanent global identifiers or a rollback freshness anchor; kernel access independently binds the full current service and caller incarnations. No disk or network association log is introduced. Existing durable operator data remains intentionally separate and can retain public journal terms under its approved contract.

The primary-source review records the next implementation dependency: native AES, SHA-1, SHA3/SHAKE and the complete selected ntor-v3/circuit state machine, with channel authentication, independent per-hop state, flow control and routing policy. XEdDSA, complete asynchronous X3DH/Double Ratchet state, ciphertext mailbox admission/queue/receipt/reclamation, atomic retained outbox/inbox, Messenger domain2 recovery, native Messenger UI and routed Forge consumption remain absent. No latency/throughput/attachment-memory/route-setup benchmark is reported for these missing paths. Full group messaging, Feed, payments, other privacy modes and the public MVP remain subsequent requirements. Services remain voluntary zero-price, with settlement unavailable and no new monetary policy.
