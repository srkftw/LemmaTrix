Guest-authorized remote build contract

Documentation index · Encrypted stream contract · Disclosed compiler sandbox. Campaign 006 continuation, 30 October 2026; earlier execution evidence remains identified below.

Guest.RemoteBuild is a bounded application protocol over Network SDK operation 2. The provider's Lean application owns quote, explicit approval, expiration, cancellation and job identity. The existing isolated BuildJobs service freezes the approved root, derives its logical identity from the canonical graph and delegates only that snapshot to the disclosed host compiler executor. The executor receives no publisher key, network namespace access or unrelated project files. A build result grants no publication or local execution approval.

Supported contract

The current bounded profile supports the fixed Main.main Lean-to-RV64 recipe, runtime profile 2, the exact pinned toolchain digest, at most 4 MiB of authorized input closure, CPU 60 seconds, wall time 120 seconds and a 256 KiB generic-content artifact limit. Older explicitly approved 64 KiB requests remain accepted. The existing namespace sandbox limits address space to 16 GiB, writable work to 128 MiB and temporary storage to 16 MiB. The binary-producing objcopy child has an OS-enforced file-size limit matching the approved 64 or 256 KiB profile; the bounded result parser also checks it. The request digest includes that output limit. The guest checks actual closure size before enqueueing and rejects an unsupported budget, recipe, profile, changed source, logical identity or toolchain.

All terms are voluntary zero-price. Paid service, wallet settlement, escrow, confidential execution and source concealment from the builder are unavailable. Encrypted transport does not hide the uploaded source from the configured builder. Builder and verifier roles have separate deliberately selected identity pins. Same-host namespace isolation is recorded separately from independent hardware or operators.

The requester physically chooses F7 to request a quote and F10 to approve the displayed source/provider and fixed limits. A provider cannot enqueue an execution before the matching approval. Job IDs use a fresh 32-byte broker nonce. The authenticated contract binds job ID, source root, canonical logical Project identity, toolchain, provider role, recipe/profile and limits. Repeated requests for the same completed input/job return the cached result; substituted fields under a live job ID fail. Expiration uses local application turns and does not claim trusted wall-clock freshness.

Durable operator execution and generic results

With an explicit indexed purpose-2 server store and --operator-config, the normal worker binds the native approved request to the shared Guest.ServiceJobs lifecycle before compilation. The journal binds the scoped operation ID, requester relationship, exact source, policy generation, selected signed service description, toolchain policy, allowed mode and finite attempt/work budgets. Exact repeats identify the existing operation; conflicting reuse is rejected. A fresh execution incarnation must be bound after restart. Process numbers, capability handles, network sessions and installation approval are never retained as authority.

Before executing, BuildJobs retains the exact frozen source using the existing authenticated ServerStore bundle format and records safe checkpoint 1. The adapter uses the native bounded completion-wait operation; the service pumps storage independently and continues handling unrelated IPC. The persistent worker waits for the selected requester’s approved native job through operation32, bounded to100 ticks and awakened by IPC or deadline, then selects that exact job. It stays running after completion; it has no idle status-poll/sleep loop. This checkpoint means the source bundle committed; it is not compiler progress or client byte acceptance. Generic results use ContentFormat-v2 format 2, with the frozen source as provenance and the actual binary SHA-256 as content identity. BuildJobs independently reads and hashes the completed actual bytes, then commits the result's manifest root to the durable job. Only the small typed metadata enters Project records. Normal RemoteBuild transfers the manifest, index proofs and verified data ranges through the existing authenticated Network relationship; the client automatically acquires the complete artifact through ContentStore. A generic artifact is never described as playable audio.

The explicit export portal delegates only the selected complete artifact and verifies its bytes against the build digest. An output destination is chosen by the operator; the guest receives no arbitrary host path authority. Completed artifacts can also be opened directly through the indexed retained inventory, with fresh range scopes after restart. A lost response is resolved by querying the logical terminal job and retained result, rather than treating a timeout as rollback.

service-jobs supports bounded enumeration, inspect, pause/drain, cancel, retry and terminal lookup. Sixteen logical records are stored in two alternating checksummed sectors each. Terminal records can be explicitly forgotten only after a later kernel boot, preventing a reused numeric slot from aliasing a live scope; forgetting also ends that record's idempotency horizon and does not delete its artifact. The native source archive engine serializes its transactions and returns busy rather than retargeting an active source.

Native service clients use Guest.ServiceSDK through the existing Vault endpoint: inspect285, reserve283, newAttempt284, complete290 and fail291. Reservation accepts actual byte, checkpoint and admitted-work amounts and commits the remaining finite budget before external work. A new attempt preserves those counters. Inspect returns the authorized512-byte logical record after the normal64-byte response header; a slot number alone grants no authority. Administrative submit/bind/control and receipt operations use the same journal through service-jobs. BuildJobs31 waits for selected frozen-source persistence;32 waits for an approved queued job belonging to the selected requester. Both waits are bounded to100 ticks while the native service continues unrelated work.

Qualified stage and terminal receipts contain the exact approved-terms hash, operation, role, requester, source/result roots, generation, attempt count, finite consumption and outcome. The disclosed host bootstrap signs only a fixed native-prepared receipt for a persisted approved job; the native guest verifies RSA2048/SHA256 against its selected pinned role key before committing or reading the receipt. The compiler remains key-free and network-disabled. Role keys are separate from publisher keys and from each other. This is a retained bootstrap signer boundary, not remote attestation, post-quantum assurance or zero-knowledge execution. Role-key rotation needs a future explicit migration.

Time validity currently uses an explicitly approved finite admitted-work-quanta basis and bounded execution attempts, not durable absolute wall-clock expiry. Uptime cannot silently renew that policy. Paid terms and unavailable privacy modes fail before work; settlement remains unavailable and voluntary work earns no monetary reward. Provider transmission reservations, client integrity acceptance and independent reproduction remain different claims; a signed provider receipt does not assert the latter two.

A running compiler has no execution checkpoint. An interruption requires an explicitly permitted new attempt within the remaining budget; restoring its source does not resume the interrupted computation. The current source/quote selection remains one per Forge instance, with four bounded BuildJobs slots and four generic reader contexts. Automatic reconstruction of an interrupted remote request into a newly authorized Forge execution is remaining work; the recovered source and terminal result are already directly usable. Cancellation blocks late attachment; an already running disclosed host compiler may continue until its hard deadline. Independent administration, hardware, confidential execution, broader recipes, payment and privacy routing remain separate requirements.
