Preserved campaign-002 contract and evidence

The live system separates ephemeral Objects from explicit retention. Objects owns immutable committed records and scoped grants in U2. Vault runs in a different user compartment, U3; it can read only an exact granted object and can access checked block/RNG operations through the kernel. A trusted local Launcher command authorizes each operation. The current Vault retains one Objects record of at most 65,536 bytes. Wallet and Messenger domains are denied.

This page specifies the current code and transaction boundaries. The implementation has source proofs, known-answer tests and runtime tests with distinct scopes. It has no compiler-correctness, whole-service noninterference, side-channel resistance, storage-device durability or whole-store rollback theorem. Current measured results are recorded in status and assurance; no final image identity is asserted here.

Ephemeral Objects authority and integrity

Object rights are read=1, create=2, revise=4, share=8, revoke=16, enumerate=32 and export=64. Both the caller's kernel-declared profile and the record grant must permit an operation. Console=128 is a separate kernel right. Administrative authority is a trusted kernel prefix bit, not an IPC argument. Kinds are Source=1, Object=2, Build=3, Release=4, Evidence=5, Fork=6, Offer=7, Receipt=8 and Event=9; schema 1 has byte payloads.

There are 64 records, each ≤65,536 bytes, and 256 grant slots. A normal owner may reserve eight records and 256 KiB including staged capacity; a normal recipient may hold 32 active grants. The trusted administrative caller can use the global bounds. Begin reserves capacity, append is sequential in chunks ≤512 bytes and commit checks the final expected SHA-256 before publishing immutable state. Metadata/read do not grant write authority. Revision creation requires a scoped parent. An aborted or malformed stage does not publish a committed record.

Vault authorization and key lifetime

Kernel IPC admits Vault requests only from Launcher. Vault independently requires the kernel-issued administrative bit and explicit Objects domain 3. It accepts exactly 32 raw key bytes through an authorized unlock operation. There is no password KDF, ambient key recovery or application access to another domain's key. The local UART management channel and launcher are trusted; it is not a remotely authenticated key-provisioning channel.

Launcher retention first checks its object grant includes read, share and revoke, grants read=1 to the current full Vault instance, and sends that returned recipient handle. Vault fetches the committed metadata/content through Objects, hashes the complete bytes and compares the committed digest. Launcher revokes the one-shot recipient grant after Vault returns, including denied/failed retention, while preserving the actual Vault response. An IPC error during cleanup is reported as an error rather than a successful cleanup. Service restart clears its private arena and makes the former instance unusable.

Lock wipes the key, recovered plaintext, cached bank, crypto scratch, state/header/root buffers, incoming request and user I/O buffer. Recovery requires a fresh explicit unlock after lock. Consumed key bytes in Launcher input and temporary buffers are cleared. Wiping is an explicit software operation, not a claim about host snapshots, physical remanence or all microarchitectural state.

Cryptography and bounded workspaces

The Lean AEAD implementation uses the IETF ChaCha20-Poly1305 construction in RFC 8439 §2.8: a 256-bit key, a 96-bit nonce, associated data and a 128-bit tag. Data is bounded to65,536 bytes and AAD to256. Encryption emits ciphertext followed by tag16. Decryption compares the complete tag before writing any plaintext destination bytes; authentication failure leaves that destination untouched. Crypto scratch is wiped after use. No constant-time claim is made.

Vault requests fresh nonce12 from the real entropy device for every retained write. Nonce uniqueness with a long-lived key is probabilistic; no durable nonce counter, key-rotation policy or retry deduplication is implemented. Service SHA-256 uses caller-selected 640-byte private scratch, and service RSA verification has a separate user-private workspace. Vault crypto uses 0x610000..0x61033f; key/state/header/root metadata starts at0x620000, bank staging at0x630000 and plaintext at0x650000. These are private virtual addresses, not supervisor identity scratch.

The actual guest test in aead_check.py checks the RFC8439 §2.8.2 ciphertext/tag vector, decryption, tamper rejection with an unchanged output sentinel, empty and partial blocks, maximum input/AAD sizes and oversized no-write behavior. Boundary expectations use an independent host byte-level ChaCha and bigint Poly1305 oracle. These tests do not establish security or a verified compilation chain.

Authenticated disk format

Storage is explicit. A backing of at least296 sectors (151,552 bytes) is required by the fixed extents;304 sectors is the recommended development allocation. Sectors0/1 hold alternate512-byte commit roots. Bank0 begins at sector8 and bank1 at152; each reserves144 sectors. No host file is silently created by ordinary object operations. Losing the backing or key is reported; Objects remain ephemeral until an authorized retained write succeeds.

The header and its length/kind/provenance/content-digest metadata are visible on disk; this is content encryption, not metadata hiding. The complete128-byte header is AEAD associated data, so domain, generation, bank choice, length, kind, provenance and content hash are authenticated. Recovery requires the root header/tag to match the selected bank, verifies the ciphertext commitment, authenticates AEAD and checks the plaintext digest. Root hashing is an additional commit-to-bank consistency check; it is not a replacement for AEAD authentication.

Publication, interruption and deletion

  1. Fetch only the authorized committed object, verify its digest, obtain fresh entropy and encrypt into private staging.
  2. Write the next bank, then flush. This bank alone is uncommitted and cannot be selected by recovery.
  3. Write the matching root at sector generation%2, then flush.
  4. Only after both flushes succeed, publish the new in-memory generation and acknowledge success.

Recovery considers only valid committed root descriptors and their matching authenticated banks. It tries the higher generation first, then the other root. A partial inactive-bank write or corrupt new root can therefore leave the previous root/bank usable. The generation helper in VaultPolicy is used at publication; its proof states that denied source authorization preserves that helper's old generation. It is not a proof of atomic disk writes or the whole retention function.

A lost acknowledgment or failed flush can leave commit outcome uncertain; the caller must inspect/recover. Two alternating roots/banks preserve one preceding committed candidate, not arbitrary history. The design does not detect replacement of the entire backing with an older valid image, guarantee durable nonce uniqueness, support multiple retained objects, journal a complete filesystem or protect against malicious host/device rollback. The host is responsible for honoring flush durability. Logical deletion invalidates roots and clears accessible RAM; it does not securely erase ciphertext or prevent restoration from host copies. A failed deletion must not be reported as deleted.

Supervisor virtio driver and host adapters

The Lean device driver scans eight MMIO slots for magic0x74726976, legacy version1, device2 block and device4 entropy. The transport follows the legacy MMIO and split-queue structures in OASIS VIRTIO1.0 CS04 §§2.4,4.2.4,5.2,5.4. It is a narrow polling implementation, not full virtio conformance. Queue size is8, guest page size/alignment4096, and the driver negotiates only block read-only and flush features. Completion polling is bounded and ordering uses device fences. Timeout latches the transport FAILED; later requests fail until explicit device initialization resets it. Reset acknowledgment precedes ring/buffer reuse so a timed-out asynchronous transfer is not silently reused.

Each16-byte descriptor contains address64, length32, flags16 and next16. The available ring follows eight descriptors at queue+128; the used ring starts at queue+4096. A block request chains type32/reserved32/sector64, optional data and a one-byte device status. Types0/1/4 mean read/write/flush. Entropy uses a device-write descriptor. The driver validates used completion, status and requested entropy length. Queue indices wrap modulo65,536. Interrupt status is acknowledged even though completion is polled.

Device absence, read-only writes, capacity/extent errors, timeout, bad completion/status and short I/O return an error. Devices and DMA pages have no user mapping. Read-only backing refuses writes before mutation.

QEMU supplies legacy virtio devices and host entropy. The x86_64/aarch64 assembly interpreters expose the same narrow guest-facing queue/device behavior and use explicit host file read/write/flush and entropy syscalls. --vault PATH selects backing; --vault-readonly exercises write failure. No backing path means no block device. These adapters implement the development subset and are not a general virtual-device platform. Guest cryptography, authentication and retention decisions still execute as compiled Lean on the guest CPU.
