Preserved campaign-002 contract and evidence

LT-Dev-v2 / LT-U64-effects-v2 / IPC ABI 2 describes the current live development image. It is a single-hart, little-endian RV64IM machine with Zicsr, instruction-cache synchronization, M/S/U privilege modes and Sv39 translation. Compressed, floating-point, atomic and vector instructions, multicore, complete privileged-architecture conformance, networking and a display stack are outside this profile. The earlier finite bring-up uses a different memory layout and capsule encoding; its campaign 001 ABI remains archived.

This is an implemented development contract. It does not freeze the release machine requested by the governing platform specification. The compiler, assembly boot/traps, devices and complete machine-code policy enforcement are not verified. Source proofs and executable tests have separate scopes; see status and assurance.

Boot, memory and privilege

The tracked M-mode boot and trap code begins at physical 0x80000000, establishes PMP, timer/delegation and the S-mode kernel, then enters user services through SRET. QEMU uses virt, 128 MiB RAM, one hart, -bios none and legacy virtio MMIO. No OpenSBI or external firmware is loaded. The assembly interpreters implement the development instruction subset and report unsupported operations.

Slot 0 is the supervisor idle context. Slots 1–6 run Launcher, Objects, Vault/server storage, Compositor, BuildJobs and the network broker in U mode; separately installed native applications occupy slots 7..11. Timer interrupts preempt runnable code. A U-mode fault tears down that exact process, cancels waiting clients and clears its frame, data, stack, queue and any service-private arena. An S-mode fault is fatal. The saved trap frame is 272 bytes: x0..x31 occupy offsets 0..255, SEPC is at 256 and SSTATUS at 264. Machine timer save storage is separate from the supervisor stacks. The timer forwards SSIP, and the trap entry acknowledges SSIP only for that cause.

Process identity is (generation56 << 8) | slot8. Generation starts with a random 32-bit boot component and a 24-bit per-slot counter. Restart refuses counter or generation wrap before teardown. Authorities compare the complete identity, including the incarnation. Restart creates a fresh context; it does not transfer the previous process's object grants. Boot randomness gives probabilistic cross-boot separation, not a persistent monotonic counter.

Freestanding Lean values and effects

The Lean-authored backend consumes reachable optimized Lean IR from pinned Lean 4.34.1 and emits RV64IM assembly. UInt8/16/32/64, USize, Bool, scalar lets, conditionals, direct calls, joins and self-tail recursion are supported. Arguments use a0..a7, return a0, stack slots are 64 bits and SP is 16-byte aligned. Narrow arithmetic results are masked. Division by zero follows Lean's zero result, and shifts retain their width-specific Lean behavior. A self-tail call reuses its frame; other recursion can exhaust the bounded stack.

The Effects SDK supplies single-field Handle, Buffer, ByteCount and Result wrappers and fully applied monomorphic StateM/do functions. In actual IPC consumers these inline to scalar IR; they allocate no guest closure or heap pair. The token is internal to this interface. Escaping closures, arbitrary structured runtime values, strings, exceptions, heap allocation and GC remain unsupported and produce compiler diagnostics. The wrappers do not encode every bound or authority in Lean types; kernel and service checks still enforce those at the boundary.

Opaque primitives carry an explicit scalar dependency token. lt_effect_value consumes a token while returning a selected scalar. @[never_extract] on primitives and compiler.extract_closed=false prevent upstream closed-value extraction from duplicating effects. Entrypoints consume an initial token argument supplied as zero by startup. Only the compiler's explicit primitive allowlist may link. Assembly primitives cover loads/stores, ECALL, fences, context entry, idle and test finish; there is no upstream Lean runtime or libc in the guest.

Kernel calls and service IPC

ECALL uses a7=operation, a0=handle, a1=pointer, a2=length and a3=value; a0 returns a scalar. 0xffffffffffffffff is the kernel error. Buffer ranges must lie within the caller's 0x410000..0x41ffff data area and pass overflow-safe length checks. Process identity and declared rights come from kernel state, never from request payload fields.

Every delivered service request begins with four little-endian UInt64 fields: caller instance at +0, request token at +8, actual caller rights at +16 and ABI=2 at +24. The request payload follows at +32. Each endpoint queue has eight entries, each caller has one pending request and queued bytes are cleared on consumption. Objects accepts callers with relevant object rights; Vault accepts only Launcher; direct application RPC targets require a full instance and Launcher authority. Replies have no user-controlled replacement for this trusted prefix. RPC deadlines are 30,000 timer ticks for Vault and 5,000 for other targets; UART reads have a 500-tick empty-read deadline. These are development bounds, not wall-clock latency guarantees.

Objects/Vault requests have a 64-byte UInt64 payload header: operation, handle, five operation-specific values and schema=1 at offset 56. Their common reply header is status, result, length, parent, kind, state, rights/domain and object ID/generation. LiveSDK and the Objects/Vault contract define each interpretation. An IPC error may follow a committed service effect if the reply is lost; callers must inspect state rather than assume cancellation rolled the operation back.

Local management framing

The local UART channel authorizes Launcher operations. It is not a remotely authenticated protocol. Request header: LT2\0 (4 bytes), payload length (UInt32), request ID (UInt64, nonzero), operation (UInt64), reserved zero (UInt64): exactly 32 bytes, all integers little-endian, payload ≤1024. Response: LR2\0, status (UInt32), matching ID, payload length (UInt64), reserved zero, then payload. Header fields are binary, not terminal text. Application console output is a separate encoded APP frame.

Launcher caches the last successful or rejected command's response and hashes the complete request header and payload. Repeating the same ID and bytes returns the cached response; the same ID with different bytes is rejected, as is an older ID. A new local connection has to account for that session state. Truncated reads stop on kernel error and resynchronize on magic; a partial frame with a complete ID receives a malformed-frame response. Key-bearing input, temporary hashing buffers and consumed UART bytes are cleared. A request timed out after an external effect can still require explicit inspection.

RSA2048 verification rejects out-of-range representatives and checks the exact SHA-256 EMSA-PKCS1-v1_5 encoding described in RFC 8017 §9.2. Verification is public-key and variable-time. Private signing keys remain in the explicit publisher tool; guest trust stores public moduli. Signed source/evidence/license hashes are publisher commitments, not proofs that the compiler, artifact or legal assertion is correct.

Upload is sequential and bounded. Successful guest inspection freezes the exact candidate; approval binds its release ID and requested rights. Installation rechecks hashes, signature, compatibility, trust and approval. An update must retain the project's pinned publisher, be strictly newer and name the current active release as its parent. The kernel receives a free staged code slot, copies all code and seals it before Launcher publishes active/previous catalog pointers. Failed admission leaves the former active release available. Rollback swaps active and previous only if the target remains trusted and unrevoked; it does not automatically restart existing instances.

Publisher revocation and individual release revocation prevent subsequent launch/restart/rollback through Launcher. Existing processes keep their current authority until explicitly stopped. Collection removes only releases no longer active/previous and no longer used by a live process. The catalog, trust and project state are session memory; Vault retention is a separately authorized Objects operation, not durable package-catalog storage.
