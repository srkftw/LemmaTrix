Explicit streamed encrypted content retention

ContentVault adds explicit streamed selected-content transactions to the existing Lean Vault compartment. The v1 single-object and v2 Project graph roots/banks remain untouched. Format 3 retains selected content; format 4 atomically includes its exact admitted consumer metadata; format 5 retains a private verified partial-content checkpoint and optional selected metadata. Earlier readable roots remain valid until a new transaction commits. This path requires an attached sufficiently large Objects-vault device, the existing explicit Objects-domain unlock, trusted approval for the selected content root and a read-only grant delegated to the actual Vault incarnation. It cannot open Wallet or Messenger domains.

The format retains one selected immutable content root or checkpoint. A new successful selection replaces the current selected generation; the prior bank remains its interruption fallback. This is not a complete multi-item personal library store, physical-drive validation, rollback freshness or secure erasure. Format 4/5 co-stores exactly 1536 selected admission/consumer bytes in the same root transaction as content commitments. Existing selected save objects use the independent v1/v2 paths. No transport key, local capability, live acquisition job, execution approval or unattended personal monitoring authority is serialized.

Independent indexed retention

The selected-content formats below remain readable and continue to preserve existing saves. New indexed personal retention uses a separate format/namespace with independent item authentication, crash-safe authenticated nonce reservation, metadata-only inventory and on-demand verified chunks. ./lt indexed-migrate copies an explicitly recovered old selection through the actual guest validator; the old commit remains available until and after the new commit. It does not silently reformat backing or turn operator plaintext into personal encryption. Separate encrypted collection/history records recover awaiting fresh approval.

Bounded encryption and authenticated recovery

The guest fetches the selected manifest and authenticated chunk proofs through ContentSDK, then copies at most 512 selected media bytes per content-read quantum. One chunk record contains index, exact payload length, Merkle depth, raw SHA-256, sibling commitments, reserved zeros and at most 4096 payload bytes. Its 4608-byte plaintext is independently ChaCha20-Poly1305 encrypted. The service uses one plaintext buffer, one 5120-byte padded ciphertext buffer and 512 bytes of encrypted manifest metadata; it never constructs a payload-sized encrypted snapshot.

Each transaction obtains a fresh 96-bit nonce from the guest entropy device. Part zero is the encrypted metadata; parts 1–1472 are chunks. Adding the part number modulo 2³² to the nonce's final word is injective within one bounded transaction. A restarted or retried new transaction obtains fresh entropy. Across transactions, nonce uniqueness depends on the declared random-source assumption; the format does not claim a durable monotonic nonce allocator. The AEAD additional data binds format/domain, bank generation, total length/chunk count, manifest commitment, exact chunk position and exact chunk length. There is no shared key with Wallet or Messenger.

Recovery authenticates selected metadata and each encrypted record, checks canonical fields and padding, then feeds decrypted bytes and retained authenticated proofs to the normal ContentJobs importer. The content service independently rehashes every chunk and checks its Merkle position before publishing a complete volatile root. The recovered recipient receives a fresh read-only grant. The Vault's temporary acquisition grant is released; recovery does not restore network jobs, peer grants, transport session keys or application execution authority.

A private format-5 checkpoint has an authenticated 184-byte availability bitmap, retaining only fully verified chunks. Missing chunks and unfinished staging are excluded. Recovery imports marked chunks into a private state-1 content root without claiming complete availability, and returns a fresh read-only grant. ContentSDK operation 315 can subsequently adopt this checkpoint under a new explicit mode/budget/provider/federation policy and operation ID after current admission and peer authentication. It downgrades old writers and creates fresh acquisition authority; it never revives an old transport/job handle. Existing read grants remain read-only.

An explicitly provisioned device needs at least 50,456 sectors. Retention writes the inactive bank, encrypted metadata, and flushes all of it before publishing its alternate root; the root receives a final flush before successful completion. An interrupted data write leaves the prior complete root selected. Recovery chooses the highest authenticatable root and can fall back to the older root if newer root metadata is incomplete. Integrity failure in an encrypted payload fails recovery before a complete content root is published. Physical torn-write and persistence guarantees remain those of the disclosed device/backend; a host-file flush is not proof of physical external-drive behavior. Restoring an entire older backing remains possible and is not detected as a freshness violation.

Cancel revokes unpublished recovery acquisition and clears private staging. It cannot promise to undo a root whose final commit already reached the device. Status remains queryable by the owning incarnation. Lock cancels/releases temporary content access, clears v3 private buffers and then follows existing key wiping. Previously disclosed content held through another authorized read grant follows its own session lifetime.

For format 5, each chunk's authenticated header normalizes the eventual checkpoint count fields to zero; the final encrypted index authenticates the completed bitmap and its count. Immutable format, generation, manifest, position and length remain bound to every chunk. This permits bounded streaming without knowing the final availability bitmap before the first encrypted write. A second unlock cannot change a personal transaction's key while it is active. The separate intentional server backend never uses this personal key and continues under its own authorized operator grant when the personal vault is locked.
