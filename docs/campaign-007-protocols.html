Modes 2 and 4 also remain unavailable. Existing explicit mode 3 remains encrypted direct bulk with endpoint/traffic visibility. A local network of distinct keys cannot establish independent operators, resistance to global traffic correlation or hostile-state resilience.

ServiceJobs schema 2: allocation handles and reclamation

Guest.ServiceJobs reuses the existing sixteen 512-byte records and the same two sectors per row,24–55, on the intentional purpose 2 operator store. No capacity increase or extra historical slot is introduced. Publication generation at byte 24 remains monotonic across tombstone and reuse. Schema 2 adds allocation epoch at byte 416 and the allocation's first publication generation at 424; unused 432–447 remain zero. Schema 1 is accepted with zero extension fields. Each persisted publication is checked and flushed before its success response.

A job handle is (allocationEpoch <<8) | storageIndex; index is 0–15 and epoch is bounded to 56 bits. Initial allocations keep the legacy handles 0–15. Reallocation increments the epoch; it never restores an old owner binding. Every ordinary operation, including administrative mutation, checks the entire handle before accessing current job state. Receipt lookup also checks the receipt's publication lies within the current allocation. Exhausting epoch or publication counters refuses new work.

Terminal forget 299 now works in the same boot. It publishes a tombstone and clears the owner binding; it retains the exact operation/requester/terms until explicit reuse. An exact retry of a retired request returns8; conflicting terms return2. After a row is reused, old handles return9. Read-only administrative inventory 296 selects a physical index and returns its current opaque handle; it grants no mutation by index. Typed ServiceSDK consumers preserve the entire handle.

The retained deduplication window is the last request in each of sixteen rows, including tombstones. After any reuse, an unknown request through automatic allocator 16 returns8 unless management explicitly sets header word5 to1 for a new operation. This is a new approved finite allowance, never an automatic retry. Known exact live requests preserve all charged budgets. Older requests whose terms have been evicted require operator reconciliation; they must not automatically regenerate an allowance. A tool deliberately marking an old request as new crosses a fresh administrative authorization boundary. The service does not claim indefinite deduplication or a freshness anchor against malicious whole-store rollback.

The focused executable check uses a fresh explicitly provisioned backing and one identified guest image. It submits real native journal operations, reserves finite bytes/work, completes using the actual ServiceJobs source artifact commitment, retries exact and conflicting operations, reuses a physical row beyond 16 operations, restarts the guest and tests corrupted-latest-bank fallback. It does not send an attachment or compose a conversation. Native and assembly-backend results must be identified separately in the campaign evidence record; AArch64 under qemu-aarch64 remains emulated ARM evidence. Source typechecking and these executions do not establish a source-to-binary proof, constant-time compilation, physical power-loss durability or independent security review.
