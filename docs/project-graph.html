Canonical Project graph and streaming Project Vault

Development format 1 for canonical graph nodes; additive Project Vault format 2. This increment advances DAT-001, DAT-003, DAT-005, VAULT-001, VAULT-002 and SDK-001. It does not complete the MVP graph, federation, compiler correctness or independent builder gates.

Identity and authority

Objects remains the guest owner of immutable payload records and operational grants. ProjectGraph supplies canonical typed node commitments, portable relative names, named roots, exact expected-head publication, root delegation and reachability. Knowing a digest never grants read access. Object and root capabilities bind the kernel-supplied caller incarnation, the service epoch and a generation. Persisted graph data contains neither session object IDs nor capability handles.

The payload digest is SHA-256 over the exact bytes. The canonical node ID is SHA-256 over this 96-byte little-endian envelope: u64 magic=0x3145444f4e544c; u64 version=1; u64 kind; u64 schema=1; byte payloadDigest[32]; byte ancestryNodeID[32]. A zero ancestry ID denotes no predecessor. Existing Objects kinds 1–9 retain their previous behavior; graph kinds are 10 Source/resource, 11 Project manifest, 12 Build, 13 Release and 14 Evidence. A Source may contain arbitrary bytes, including UTF-8 source and binary resources. A graph revision may refer only to an already authorized predecessor of the same type.

Kinds 11–14 have an authenticated payload envelope: four little-endian u64 values (magic=0x31464e4d544c, version=1, entryCount, detailByteLength), then entryCount 128-byte entries, then exactly detailByteLength opaque bytes. Each entry is u64 referencedKind; u64 nameByteLength; byte nodeID[32]; byte name[80], with zero name padding. Names are unique, sorted bytewise and canonical relative printable ASCII. Empty segments, dot or dot-dot segments, absolute paths, backslashes, colons and control bytes are rejected. Entry count is at most 32. This name limitation is distinct from payload UTF-8 support.

Manifest edges require at least one Source and may additionally reference Build, Release or Evidence artifacts. Editors and compiler exports distinguish source files from typed artifact entries. Build edges target a Project manifest and optional Evidence, with at least one manifest. Release edges target Build, optional manifest and Evidence, with at least one Build. Evidence edges may target Source or manifest and may be empty. These typed graph records are content; a Release node alone does not authenticate a publisher, admit a catalog item or authorize local execution.

Ordinary callers may own at most four named roots and two temporary snapshots; the purpose-limited BuildJobs service may hold four export snapshots for its four jobs; administration remains globally bounded by the same root table. There are 64 immutable records, 256 object grants, 16 named roots and 64 root grants. A graph producer has a 24-record, 1 MiB reserved-payload and 64-grant ceiling; legacy ordinary non-graph creation retains its earlier 8-record/256 KiB limit. Each payload is at most 64 KiB. Repeated open/resolve calls reuse a sufficient existing grant. Root reachability protects complete source ancestry and typed edges across editor death and forbids dropping a pinned record. Dead-owner collection preserves all live roots and surviving grants. History is bounded by these quotas; automatic history truncation is not implemented. An explicit quota error preserves the previous root.

The graph arena is Objects-private 0xd10000–0xd17fff, inside its bounded existing private mapping. Hash scratch is 0xd00000. No app receives raw graph memory, a physical address or an ambient global-digest lookup capability. The small stale_head_denied theorem describes only the pure publication guard used by the service; memory operations, SHA-256, compiler lowering, kernel caller identity and the service implementation remain assumptions.

Build jobs and attributable graph records

The separately scheduled BuildJobs service freezes an explicitly delegated read/share/export root through operation33. The kernel supplies a separate service-purpose bit 0x200000000 only to this service; packages cannot claim it. Operation33 requires source scope73 and returns a hidden immutable export snapshot with scope89 (read/share/remove/export), which can delegate read/export65 to Launcher. Ordinary root creation and restored publication require a derivation grant4 on the manifest; reading a manifest cannot promote its rights through another named root.

The guest image embeds the current fixed compiler/SDK/toolchain identity. BuildJobs retrieves it through kernel operation100, which is denied to other callers, and refuses jobs if it is unavailable. Queued replies are192bytes, with the expected compiler identity at +128. Completion requests contain source root32 at +64, output binary digest32 at +96, attributable host request digest32 at +128, expected compiler identity32 at +160 and at most512 diagnostic bytes at +192. The service checks current job/service incarnation, exact frozen source, runtime profile, compiler identity and diagnostic length. The fixed recipe is Main.main. A host request digest remains an attributable builder assertion; this mechanism does not prove source-to-binary correctness.

Every accepted failure creates an immutable Evidence14 record with a typed source-manifest reference and actual bounded diagnostics. Every accepted success additionally creates Build12 with typed Evidence and source-manifest references. Their details bind the job ID, service incarnation, status, source root, runtime profile, output hash, host request digest, frozen compiler identity and recipe. A completed response preserves its128+diagnostic-byte layout, and provides requester-scoped read grants to Build at +48 and Evidence at +56. Completion of revision A never edits a newer source head B. The requesting app can inspect these independently through Objects21 and ordinary reads.

Four jobs are bounded in the service. Requester-only cancellation5 removes the frozen export root and its grants, clears the job slot and drops unrooted Build/Evidence records; rooted records remain protected by Objects. These records are not publisher signatures or local installation approval. The explicit publisher path obtains Build/Evidence read grants from the current service, creates inert Release content and attaches it to a selected published project snapshot. Its complete typed closure can therefore be retained with source and build history. Unattached job records remain job/grant-held until cancellation; building alone does not retain them.

Release content and selected published snapshots

Publishing uses an explicit publisher key outside the compiler sandbox. The host obtains current Build/Evidence grants through administrative BuildJobs operation6 and verifies its service incarnation, source and output commitments. Root grants record their kernel-bound issuing incarnation. Enqueue requires that issuer to equal the requester, preventing another app from replaying a handle delegated to the build service for a different caller. Four at-most64KiB Source chunks hold executable bytes; a typed binary manifest orders those chunks. Release13 uses exactly four typed entries named build, code, evidence and source. Its opaque detail begins with eight little-endian u64 values: magic 0x31544e43524c544c, version1, header/signature prefix length768, manifest JSON length, sources JSON length, evidence JSON length, license-assertion JSON length and reserved zero. The768-byte signed prefix and these four exact canonical JSON byte strings follow.

The guest checks the signed header's stable release identity and the SHA-256 commitments of all four supplied metadata byte strings. It joins the ordered code chunks in an Objects-private bounded256KiB buffer at0xd20000–0xd5ffff, checks the actual executable hash against the header, and requires the typed Build's source, runtime profile and binary commitments to match. This verifies present material and its commitments; JSON publisher assertions and source-to-binary correctness are distinct. The signature is carried as content and must still pass Launcher's current publisher-signature verifier and local trust/approval policy before execution. A Release graph ID differs from the signed release header ID.

The published project snapshot copies source entries and adds release.ltrel as a typed Release13 edge. An explicit attach-root request can publish by exact expected-head CAS when the source root is still the built revision A. If the user has advanced to B, publication creates a separately named snapshot project-release-version and preserves B. A fresh snapshot has no invented predecessor or claimed Fork operation; its Release-to-source edge binds the actual lineage. The snapshot is delegated to the trusted shell for selection and Vault retention. None of these operations installs, trusts or executes the package.

Project Vault format 2

ProjectVault extends the separate encrypted Vault compartment. Version 1's sectors 0/1 and bank extents remain unchanged; version 2 uses commit roots at sectors 2/3 and two 10,240-sector banks beginning at sectors 512 and 10,752. A backing needs at least 20,992 sectors; 24,576 sectors (12 MiB) is recommended. An old smaller development image is not silently expanded or reformatted. A failed capacity-bound write does not acknowledge durability.

A version 2 snapshot contains up to six selected named project roots, 64 graph records and 4 MiB of aggregate payload. Existing retained names and their frozen content remain selected when another named project is added. Updating a selected name replaces that head while retaining previously selected history until quota exhaustion or explicit deletion of the version 2 archive. This format currently has no per-project deletion or automatic history pruning control.

The fixed 14,368-byte encrypted index consists of header32, sixteen reserved root descriptor128 slots, and sixty-four node descriptor192 slots. A root descriptor is name length8, stable manifest ID32, name64 at +40 and zero padding. A node descriptor is kind8, payload length8, stable ID32, predecessor ID32, payload digest32, first chunk8 and chunk count8, followed by zero64. Unused slots are zero. Operational handles are held in separate transient memory and are never serialized.

The commit descriptor's first 128 bytes bind magic 0x32564a4f5250544c, format 2, Objects domain 3, generation, bank parity, fixed index length, node/root counts, total chunk count and aggregate byte length. A fresh random nonce12 is at +96; reserved bytes are zero. The rest is index AEAD tag16, SHA-256 of index ciphertext32 and zero336. The encrypted index starts at the bank's first sector and occupies 29 sectors. Body chunks start at bank sector +32. Each chunk occupies nine sectors: ciphertext4096, tag16 and zero padding. The AEAD is the existing RFC 8439 ChaCha20-Poly1305.

Nonce zero is used for the index. Every body chunk derives a distinct nonce by adding its global chunk index plus one to the nonce's final little-endian 32-bit word. A bank has at most 1,024 chunks, so those nonces are distinct within the transaction. Fresh random base nonces make reuse across transactions probabilistic, not impossible. Body associated data is commit header128, member stable ID32, relative member chunk index8 and actual member chunk byte count8. This binds the record, graph membership and commit generation. The final chunk's unused plaintext bytes are zero.

Saving first clones each exact selected stable head through Objects operation32. These hidden roots omit mutation authority and remain pinned until explicit cleanup. The Vault receives only read grants to those frozen closures, so concurrent edits cannot expand retention scope. Payloads are processed one bounded record and one 4 KiB encrypted chunk at a time. The entire project is never materialized in one plaintext object or buffer. The complete inactive bank is written and flushed before the matching root is written and flushed. Only then is the new generation reported durable. The prior root/bank remains available if staging, quota, device writes, authentication or the root commit fails. Recovery checks the authenticated encrypted index, every chunk, every payload and canonical node commitment, names, typed references and ancestry; a failed higher candidate can fall back to the other complete candidate. Entire-store rollback detection requires a separate trusted freshness mechanism and is not claimed.

Version 2 operations are 210 save (count at +24; delegated root handle array at +64), 211 authenticate/recover, 212 summary, 213 root descriptor by index +8, 214 node descriptor by index +8, 215 member read (index +8, offset +24, count ≤512 at +32) and 216 logical delete. They require existing Vault unlock and Objects-domain administration. Deletion invalidates both version 2 roots and flushes before acknowledgment; it does not erase old ciphertext or delete the separate version 1 object snapshot. Lock clears the key and both versions' plaintext and working state.

The disclosed host byte adapter transports bounded authenticated recovery records without writing plaintext files, reimports them through the same guest schema and identity checks with fresh grants, and requests operation 30 only after all members validate. Its dependency ordering is orchestration, not authorization. A failure before publication drops private imported stages and leaves visible project roots and durable commit roots intact. Retained release bytes remain inert: publisher trust, install approvals, input history, process handles, unrelated private objects and signing keys are absent. Wallet and Messenger domains remain denied by the existing VaultPolicy.
