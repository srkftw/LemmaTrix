Native release and decision profiles

Campaign010, 1 November 2026. This page specifies implemented encodings and authority boundaries; the campaign execution record identifies which connected operations were executed.

Release-v2 remains the original 512-byte header, 256-byte RSA2048/SHA-256 signature and executable. Its identifiers and public pins are unchanged. Release-v4 uses the same 512-byte header, a 64-byte pure RFC8032 Ed25519 signature, a 32-byte public key, then the executable. Its prefix is 608 bytes. Parsers dispatch on the explicit version and never reinterpret a failed v4 verification as v2.

Launcher memoizes a successful v4 signature check only for the complete 608-byte envelope hash, exact selected trusted public-key hash and current session staging epoch. Every subsequent installation still hashes the actual executable and header, resolves current publisher trust and requires separate exact permission approval. New staging clears the cache. Revoked trust, substituted signature or public key, altered artifact bytes and unknown algorithm profiles cannot inherit cached verification. Legacy verification keeps its existing path; this optimization creates no durable execution or signing authority.

The signed message is exactly the 22 bytes LT-PROJECT-RELEASE-V1\0, where \0 denotes one NUL byte, followed by the complete 512-byte header. This is neither Ed25519ph nor an Identity certificate envelope. The release ID hashes the header with only its own 32-byte ID field zeroed. The signature does not participate in that hash.

A NativeApplication must bind an actual nonempty aligned executable, supported entry point, rights and resource profile. A DevelopmentArtifact has zero executable length, executable hash, entry, runtime resource profile, data, stack and rights. Its signed source and manifest commitments remain required. Accepting that inert source facet grants no installation or execution authority. SDK, dependency lock, exports, recipe, provenance, license and assurance declarations are committed through the exact manifest bytes.

Identity purpose 6 belongs only to role 1 project keys and the exact native Launcher coordinator incarnation. One-use approval binds the complete header hash, key generation and current operation binding. The generic management forwarding portal refuses purpose-6 approval requests; the coordinator validates actual Objects graph and Build/Evidence records before requesting it. The host release adapter prepares or assembles bytes and verifies returned signatures; it accepts no Ed25519 publisher private key.

Explicit project retention produces an authenticated, typed encrypted seal for the existing Objects domain3 storage path. Recovery derives fresh handles and increments the key generation. An older sealed backup supplies no external freshness evidence: recovered publisher keys are restricted to inspection until a supported reconciliation or explicit fresh publisher/fork continuation establishes authority. The implementation does not claim whole-store rollback detection.

Registry decisions use independently generated role 7 keys and purpose 7. The native Identity411 lifecycle binds an exact current Registry incarnation, policy hash, operation generation and finite decision allowance. Version-2 decision signatures cover the exact 26-byte domain LT-FEDERATION-DECISION-V2\0 and 512-byte decision header. A repeated identical decision sequence and header returns its cached identical signature without renewing the allowance; a changed header at that sequence is refused. Registry descriptor transport can retain its 768-byte storage row with the unused tail explicitly zeroed.

Operator sealing preserves its decision sequence and remaining allowance, increments key generation on recovery and creates a fresh operation binding. Accepted server state must be reconciled with that sealed identity; copying a backup does not establish independent freshness. Publisher authority and federation admission remain separate, and neither grants user execution consent.

Native operator commands

Start the current common image with an explicitly selected server backing and install the Identity, Registry and Forge roles using the existing operator package/start commands. The service-package bootstrap publisher is separate from the native project publisher and federation decision keys. Record the actual Identity/Registry package release IDs and process incarnations from their command results. The examples below use consumer with an explicit rights mask895 for Project Notes; a second independently initialized operator can select256 and refuse the same release. These are declared policy choices, not a package-name exception.

./lt server-store mount --socket SERVER.sock
./lt server-store permit --socket SERVER.sock --instance REGISTRY_INSTANCE \
 --namespace CATALOG_NAMESPACE_HEX --role registry --bytes 1048576
# Use the returned fresh grant, not a grant saved before restart:
./lt federation --socket SERVER.sock --instance REGISTRY_INSTANCE native-init \
 --policy consumer --allowed-rights 895 --limit 16 --store-grant CATALOG_GRANT \
 --identity-release IDENTITY_RELEASE_ID --registry-release REGISTRY_RELEASE_ID
./lt federation --socket SERVER.sock --instance REGISTRY_INSTANCE trust-publisher \
 --public project-publisher.pub --project-id LOGICAL_PROJECT_ID
./lt forge --socket SERVER.sock --instance FORGE_INSTANCE federation \
 --identity FEDERATION_ID --policy consumer

Save the returned public key, federation ID, key handle and generation as configuration metadata. No host federation signing worker or private signing key is needed. The configured Forge receives an authorized closure and the native Registry decides from its actual objects. Client Forge separately selects the same federation and a public-only native Registry verifier:

./lt federation --socket PERSONAL.sock --instance VERIFIER_INSTANCE native-verifier \
 --public FEDERATION_PUBLIC_HEX --policy consumer --allowed-rights 895 --generation KEY_GENERATION
./lt forge --socket PERSONAL.sock --instance FORGE_INSTANCE federation \
 --identity FEDERATION_ID --policy consumer

Configure the explicitly approved ordered endpoint using the existing Network provisioning commands and Forge configure --peer-slot 0 --stream 1 for multiplexed bulk. The current private Forge client requires broker lease operation17: exact caller/context/peer/service/root/operation/stream stay fixed, remaining bytes and rate counters survive renewal, and an exhausted, revoked, dead or replaced grant cannot renew. A failure never mints another grant. Physical F3/F4/F11 refresh the existing lease; bounded background maintenance does the same while idle. New service incarnations after a deliberate restart need fresh configuration and authorization. Selected routed Feed/Messenger profiles remain independent.

Choose a separate32-byte unlock credential and namespace for the operator seal; it is not an exported native seed. Create it once and preserve it independently from the backing, using the credential creation example in the retention guide. Explicitly retain the signed catalog and seal before stopping the server:

./lt federation --socket SERVER.sock --instance REGISTRY_INSTANCE retain-verified
./lt federation --socket SERVER.sock --instance REGISTRY_INSTANCE native-retain \
 --key OPERATOR_KEY_HANDLE --credential OPERATOR_UNLOCK_FILE \
 --namespace OPERATOR_NAMESPACE_HEX --policy consumer --allowed-rights 895
# After normal restart and fresh service installation/store grant:
./lt federation --socket SERVER.sock --instance NEW_REGISTRY_INSTANCE native-recover \
 --credential OPERATOR_UNLOCK_FILE --namespace OPERATOR_NAMESPACE_HEX \
 --identity-release IDENTITY_RELEASE_ID --registry-release REGISTRY_RELEASE_ID \
 --store-grant NEW_CATALOG_GRANT

Recover Forge's selected authorized graph archive separately with F9 and its freshly approved seed namespace. Native recovery checks the sealed policy/key against the retained catalog, advances generation and retains the remaining decision allowance. Use the new returned bindings. An older whole-store backup still needs explicit operator reconciliation; no independent freshness oracle is supplied.

A seed can explicitly retain already verified public decisions with ./lt federation --socket SEED.sock --instance REGISTRY retain-verified, after selecting an approved Registry-owned server-store grant. This operation accepts no descriptor bytes and creates no signature: it commits only the private catalog's previously validated records and their maximum verified sequence. Fresh verifier configuration and ordinary catalog recovery revalidate the original signed decisions. Forge can then reattach the unchanged descriptor for an exactly matching recovered root, chosen federation and policy. A retained rejection remains a rejection; no recovered live handle or seed key becomes federation signing authority.

./lt release inspect build/project-notes.ltrel --public-key build/project-publisher.pub --manifest build/project-notes.ltrel.manifest.json verifies an explicitly selected raw 32-byte or PEM Ed25519 public pin. Legacy RSA public PEM and exact 256-byte modulus pins remain supported. See the campaign report for the actual supported create, build, native review and distribution commands.

A new publisher requires an explicit public pin independently of federation admission. Inspect the chosen release and provenance, save its exact public Ed25519 key (32 raw bytes), then approve that publication namespace through the normal public control interface:

./lt ctl --socket PERSONAL.sock trust --publication-id PUBLICATION_ID --public publisher.pub

This pins a public key; it grants neither installation nor execution. Forge F6 subsequently materializes and checks the exact chosen release, then the native execution review separately shows its permissions. A missing or wrong publisher pin refuses that step. A Feed card and a valid federation decision never install the pin automatically.
