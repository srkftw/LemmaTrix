Public Lemma SDK 0.1.0

Ordinary projects import the public Lemma.* namespace, keep their own source tree, and build actual freestanding RV64 applications through the same frozen-source sandbox used by local and remote BuildJobs. No repository allowlist edit or publisher private key is required. The canonical sdk/manifest.json identifies every public module, its complete client implementation closure, source bytes, and compiler/runtime recipe. Its domain-separated SHA-256 content identity is pinned in lemma.lock.json.

Set up and build

The declared hosts are x86-64 Linux and ARM64 Linux with Nix, Linux user/mount/network/PID namespaces and working mounts/chroot. The pinned Nix expression selects the native architecture and resolves Lean 4.34.1, LLVM 20.1.8 and Python from the same fixed nixpkgs revision and source hash on either host. Setup writes an ignored local descriptor; no developer-specific Nix output path is required. Doctor validates the exact versions, immutable read-only closure and namespace prerequisites used by app builds. An arbitrary PATH compiler that lacks that closure is not accepted as a successful isolated-build setup.

./lt setup
./lt doctor
./lt sdk init build/my-tool --name my-tool --template utility
./lt sdk check build/my-tool
./lt sdk build build/my-tool --output build/my-tool-build
./lt emulators
./lt build
# Native host backend: x86_64 on x86-64 Linux; aarch64 on ARM64 Linux.
./lt run --backend x86_64 --socket /tmp/lt-developer.sock

build/my-tool-build/app.bin is native LemmaTrix machine code, not a Linux executable. Run/install/sign it through the native workbench and publisher review; building does not authorize execution or publication. QEMU RV64 system execution is optional. The matching assembly emulator runs directly on its host architecture. Selecting the opposite assembly architecture explicitly uses QEMU userspace; emulated AArch64 execution does not establish physical ARM64 validation. Host Lean/LLVM remain a disclosed, key-free compiler bootstrap.

The starter's --template objects uses the same public object client to stage and abort a real bounded object. --template social adds the same narrow intent clients used by Project Notes, with rights831 for its surface, input and object operations. It requests no raw network capability; consequential sharing uses the native intent review. These starter patterns do not create a social identity, send a message or claim an unimplemented payment capability. Project Notes supplies the useful complete object-backed and sharing application.

Exact dependency and SDK bytes

Locks bind the SDK content identity, exact signed dependency release and carrier identity, publisher, exported modules, license/provenance, declared capability effect, transitive dependency pins, supported toolchain versions, recipe, target profile, entry and module. SDK caches preserve the selected SDK and compiler/runtime recipe bytes instead of substituting checkout HEAD. Export an SDK cache for another offline developer and explicitly import the same content identity:

./lt sdk export-sdk build/sdk-export
./lt sdk import-sdk build/sdk-export
./lt sdk identity

A source library is a signed DevelopmentArtifact with canonical source, exported modules, SDK/dependency lock, license and provenance. It has no dummy executable, execution rights or entry point. It can be checked and elaborated in the ordinary sandbox without producing executable bytes:

./lt sdk lock examples/notes-schema
./lt sdk check examples/notes-schema
./lt sdk build examples/notes-schema --output build/notes-schema-check

After native signing, the key-free pack command assembles the returned envelope, signed manifest, public key and actual committed source. It verifies the signature and source closure. Import requires the user's exact selected release and publisher identity:

./lt sdk pack-dependency --release build/notes-schema.ltrel \
 --manifest build/notes-schema.ltrel.manifest.json --public build/notes-schema.pub \
 --source examples/notes-schema --output build/notes-schema.source.json
./lt sdk import-dependency build/notes-schema.source.json \
 --release RELEASE_ID --publisher PUBLISHER_KEY_ID --project examples/project-notes
./lt sdk check examples/project-notes
./lt sdk build examples/project-notes --output build/project-notes-build

The import command puts the verified exact carrier at deps/RELEASE_ID.json in the project source closure and updates the reviewable lock. Forge therefore distributes the actual signed helper release, manifest and source with the application's permitted source graph. A second user can build from those fetched immutable bytes without consulting the first developer's filesystem or network. A previously verified cache is an offline fallback, never an unpinned resolver. Lock changes report before/after dependency and capability declarations; they grant no guest authority.

After importing the application source into a personal guest, attach each selected signed dependency through the normal native graph admission path before freezing a release:

./lt sdk attach-dependency build/notes-schema.source.json \
 --socket build/personal.sock --root APP_ROOT

This command submits untrusted canonical Source, SourceManifest and source-only Release records to ImportJobs, resolves the admitted Release, and adds its exact kind-13 edge to the selected application source using compare-and-swap. Native release validation checks this actual signed graph against the lock and carrier commitment. A carrier alone does not establish native release authority. The command reconstructs an initial source-only library from its exact signed source provenance; libraries with additional source ancestry require the publisher's complete graph archive. Dependency admission grants neither installation nor execution authority.

Resolution verifies every source, normalized path and module, source/total byte limit, exact publisher signature, signed source/export/license/provenance declarations, pinned SDK, transitive identities and cycles before compilation. App and dependency paths must not collide or shadow Lemma, Guest, Compiler, Init, Lean, Std, runtime or sdk. Lean source paths use canonical directory separators, for example App/Other.lean; dotted filename aliases such as Lemma.UI.lean are rejected. Standard-library imports resolve only from the pinned immutable toolchain. A project can import only public SDK modules and its dependency's declared exports. The compiler receives only the frozen project, verified finite dependency closure, locked SDK/recipe and immutable toolchain inside a network-isolated namespace.

Preflight, evidence and limits

sdk check checks source/dependency closure, namespace, schema, entry/profile consistency, capabilities, explicit license/distribution declarations and obvious forbidden host/private effects, with practical diagnostics. License strings do not establish legal authorization. Native release signing, actual Build/Evidence and federation admission remain separate prerequisites. A successfully compiled theorem does not label an application fully verified.

At most 128 members and 4 MiB are accepted per build closure, 128 KiB per Lean source, and 16 unique exact source dependency releases. Native release verification additionally has a 16-reference work queue: the application’s flat pins and every library’s child pin consume entries, including repeated references in a diamond. Both limits apply. Public sdk check and sdk build count the authenticated signed child references, including repeats, and refuse oversized work before compilation with a smaller-closure diagnostic. Native release preparation independently enforces the same queue limit. Larger transitive graphs require checked native deduplication before that profile can publish them. Project Notes uses one separately verified helper. Runtime profiles remain 64-KiB or 256-KiB executable limits, with no executable for source-only libraries. Build results bind the frozen source root, snapshot digest, SDK, dependency lock, actual dependency source records, selected recipe/toolchain, request and artifact hashes. A changed source head cannot claim an older result. Local and remote/verifier workers call the same resolver and sandbox; two local workers provide reproduction evidence, not independent administration.
