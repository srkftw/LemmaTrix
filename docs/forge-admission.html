Native Forge publication and chosen federation admission

Documentation index · Authenticated encrypted bulk · Explicit server store · Remote build and verification. Campaign 004 development contract, 29 October 2026.

The native Forge selects a configured peer and a separately configured federation public identity/policy. F11 freezes the selected project revision, authorizes disclosure of that exact closure to the pinned peer, and sends a publication request over the guest broker. A headless registry role receives only that authorized root, fetches its actual records through the native transactional importer, and asks its separately isolated Lean Registry compartment to evaluate the canonical material. The signer bootstrap signs the immutable guest-evaluated decision under its explicitly selected federation key. That key is distinct from the original publisher and the ordered Noise relationship.

Native controls and authority

F2 selects the local root; F11 requests publication; F3 discovers metadata; F1 inspects the actual signed admission; F5 requests content; F6 opens the existing Launcher inspection/approval path. Normal source upload, publication, discovery and Fetch use the public SDK and graphical controls. Initial node installation, endpoint configuration, public-key enrollment, storage purpose and signing credentials are explicit operator setup. A configured registry role authorizes bounded incoming publication requests from its one pinned peer; it does not authorize arbitrary object queries or future descendants.

The admission view displays the exact root, configured federation identity, policy, signature state, listing classification and reason, publisher key identity, source/evidence commitments, requested rights and runtime profile. Zero/absent material remains unknown. Peer names remain untrusted text. A positive federation result permits the explicitly requested Fetch for that configured federation. It grants no local execution approval, signing authority, root ownership or personal durability. Existing direct-peer generic Fetch remains a separate explicit configuration.

The network-facing Forge never receives Registry's storage grant or publisher keys.

Subscription performs bounded metadata queries with backoff and offers a newer verified root; it does not Fetch, retain, install or approve execution. A changed identity or known revoked decision fails closed. F6 requires a currently positive verified descriptor for the exact selected root when a federation is selected. Read-only operation 60 reports subscription identity and state.

Wire and SDK versions

Forge graph protocol version 1 uses bounded authenticated application records. Its header is 96 bytes: magic/version/type/transaction/four bounded fields and root ID32. Type 13 is a 128-byte publication request containing the exact frozen root and fresh broker nonce32; the transaction equals its first eight bytes. It follows the selected root's ordinary metadata offer. Registry-role ingestion accepts that request only from its configured authenticated peer and permits the pre-admission upload only for that requested root. The server issues a completion receipt only after the actual complete graph atomically commits.

Type 9 carries decision512 after the header (608 bytes); type 10 carries its RSA2048 signature256 (352 bytes). Both name the same root and signed sequence. A new metadata offer clears the private assembly. Wrong roots, lengths, versions or mixed sequences fail closed. Metadata browsing imports no graph. The client calls the isolated Registry SDK verification operation only after both pieces arrive. A verified descriptor may be forwarded unchanged by a seed explicitly offering that same root; this gives the seed no federation signing authority.

Admission-v1 is 768 bytes: a fixed 512-byte signed decision and signature256. The decision commits classification/reason, configured policy, requested rights/profile, monotonic sequence, logical Project ID, versioned publication ID, release ID, source/artifact/evidence commitments, actual policy digest, federation key ID, exact root and publisher key ID. Generic portable content has classification 1; technically admitted native material has classification 2; rejection is 3. Missing source, evidence, publisher or executable material is not inferred from an admission label.

Forge provisioning operation 57 is an administrative request64 plus expected federation ID32, with enabled flag and expected policy in header fields. Read-only operation 58 returns header64, bounded state128 and remote descriptor768; operation 59 returns header64 and local descriptor768. Guest.RegistrySDK obtains the explicitly bound service incarnation through syscall 113. Display/input rights alone do not grant this path.

Bounded cancellation and verified record reuse

The offered head/name is held separately from the currently selected workspace root. Selecting another project does not advertise it or change the already approved frozen closure. Only F4/F11 prepares a new offer. Reconfiguring an idle relationship revokes the old metadata/root grants before issuing new ones.

Available content advertises metadata field d=3 for the checked-record extension. An explicit Fetch requests profile 2. Each record metadata is followed by a bounded sender wait for type 14 (send payload) or type 15 (skip this exact canonical node ID after the recipient has replayed its own checked bytes into the new hidden import). The sender validates root, transaction, ordinal and node ID before advancing. A legacy explicit direct-peer offer can use its original whole-stream contract; it receives no resume assurance.

The recipient caches at most 256 KiB of payload in its private session arena. Only a complete staged record that Objects operation 43 independently checks against the actual payload hash and canonical typed node identity can become reusable. The cache includes the exact root and record commitments; matching visibility and fresh authorization remain required. Incomplete candidates are reclaimed on cancellation. A reconnect or authorized provider change obtains a fresh Noise session, peer-bound broker grants and import transaction. The final importer still validates the complete requested closure before publishing any root. There is no unchecked suffix or imported capability reuse.

Esc sends authenticated cancellation type 12 and the provider responds with type 11 under the exact transaction/root. A bounded outstanding record drains before cancellation, preserving stream framing. A progress deadline also releases abandoned transfers. Checked RAM cache survives an in-session explicit reconnect, but process/session restart discards it. No personal directory, encrypted vault retention or server durability is created by Fetch or this cache. The native overview displays checked and reused session bytes; read-only operation 62 returns bounded cache progress.

Independent policies and lifecycle

The portable development policy lists generic canonical projects and admits compatible original-publisher-signed native releases requesting only its display/input mask. The restricted policy requires native release material, a smaller rights mask, and a declared license other than the recognized unknown declaration. This is a disclosed bounded rule set, not a legal rights audit. Both preserve the original publisher signature and keep local execution approval separate. A rejected listing leaves the portable project intact for another authorized destination.

A headless registry restarted from its own explicit store can answer native F3 with signed metadata even when no graph is loaded. Such an offer uses availability field d=2, zero nodes/bytes and an honest root-based fallback alias. F1 still verifies and displays the signed admission; F5 shows METADATA ONLY - CHOOSE SEED and creates no import. Repeated F3 advances a bounded catalog cursor; this native view presents one listing at a time. A listing signature commits admission facts, not a promise of source or artifact availability.

Registry has a bounded paginated 16-record signed catalog. Publication decisions persist only through its explicitly granted server store; recovery verifies complete committed descriptors without restoring source content. Catalog possession does not promise seed availability. Query refresh notices a newer signed result for the same exact root/release, including revocation. The verifier rejects known older/conflicting sequences. No trusted clock, global latest-version oracle or public membership index is implied; a new verifier cannot infer an unseen revocation.

The development transport has one explicitly configured ordered peer relationship at a time. Selecting a new relationship resets/re-authenticates and creates fresh grants for the already explicitly shared immutable root. It does not reuse the previous peer's authority or PSK. Interactive onion, padded mixing and private-cluster modes remain unavailable. This direct encrypted mode supplies content confidentiality and configured endpoint authentication, without anonymity or post-quantum claims.
