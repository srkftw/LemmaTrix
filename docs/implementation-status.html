Implementation status, evidence and trusted boundary

28 October 2026 campaign result. The historical specifications and RG-01–RG-11 are unchanged. No public MVP gate is claimed complete. The implementation supplies an executable development path for the next session.

Executed capabilities

One Lean-authored kernel, object broker, package validator and two isolated native applications execute from the same raw image on QEMU, native x86-64 assembly emulation, and ARM64 assembly emulation under qemu-aarch64. The Workbench imports arbitrary bounded UTF-8 text, reads installed release metadata, transforms text, creates an object revision and lineage, shares with a second independent client, revokes it and denies stale/forged authority. A busy client is preempted and its prohibited kernel load faults; healthy computation continues. Separately an illegal user instruction is contained. User code cannot map kernel, peer, MMIO, signing key or raw network/storage authority.

The guest validates signed capsules, activates a behaviorally distinct second version and rolls back. Bad content, invalid signature, incompatible runtime and unapproved capability increase fail before activation; rejection checks compare the previous executable hash, generation, quota and capability table. Revisions and release metadata use the same hash-checked object table. External native packages can be checked/exported on the host and run with explicitly approved object rights through the same guest signature/check path. The REL fixture imports a rights-declared restricted source, extracts and edits a semantic object, emits a real SDK application, signs/packages it, and differentially compares actual guest behavior. It is a source-first fixture, not general reverse engineering.

Focused evidence and limits

Recorded campaign evidence: final image 6ed5cb19d5f3fcd75fc8f40f71e740965dba954c24244ce4b0e5a004f43ab5c3, implementation commit 52cfcad67f846d8b94c13ba598248b12d912d495. Final acceptance passed on all three backends; a second full build produced identical bytes on the same host. This is not independent-builder evidence. The REL images in the record are separate, explicitly identified integration builds.

./lt check rebuilds from tracked sources and emits machine-readable build/acceptance.json. It records guest-image identity, execution environment, cross-backend traces, ISA/MMU/timer probes, fresh-session reconstruction, forbidden language/extern rejection, actual Lean control-flow mutation and changed binary/behavior, signature denial and theorem dependencies. Compiler checks additionally execute arithmetic and bounded tail recursion; SHA vectors include 0, 3, 55, 56, 64, 256 and 65536 bytes plus oversized no-write behavior. RSA checks accept OpenSSL signatures and reject changed messages/signatures, out-of-range representatives and malformed padding. Host Ed25519 checks include an RFC 8032 vector, authenticity/tamper/approval/export cases. Passing these checks is partial development evidence, not complete ISA conformance or cryptographic assurance.

The three authorization lemmas revoked_denies, stale_denies and missing_right_denies prove the actual pure predicate used by dispatch. Their enumerated Lean dependencies are propext and Quot.sound; no sorryAx or admitted goals are used. denied_preserves_generation proves the pure helper only, with no axioms; it is not a proof of the entire imperative activation function. Branch review and runtime rejection checks cover the current activation behavior. No source-to-binary correctness theorem exists.

The next highest-value extension is a proper trusted launcher and externally supplied generation queue, preserving declared authority and shared metadata while removing the scripted two-version lifecycle. Then the block/storage and encrypted vault broker prerequisites can advance approved Objects retention. General heap/structured-value lowering and selected isolation proofs are compiler/runtime dependencies for wider SDK applications. Native ARM64 hardware and independently administered builders/nodes remain external validation needs, not blockers to local development.
