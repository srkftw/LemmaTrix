Native Messenger session and domain 2 profile

This page specifies the implemented classical one-to-one session owner. The owner, cryptography, transactional state and attachment chunk operations execute as Lean-authored RV64 code. Routing, graphical interaction and ciphertext mailbox delivery have separate integration evidence. The owner component tests described here do not establish a connected routed product campaign, Signal interoperability, constant-time compilation or independent cryptographic review. Limited project groups, Feed, Wallet, other privacy modes and the remaining MVP gates remain outstanding.

Selected cryptographic profile

The profile selects X3DH revision 1, 4 November 2016, XEdDSA revision 1, 20 October 2016, and classical section 3 of Double Ratchet revision 4, 4 November 2025. It uses X25519, SHA-512 XEd25519 signatures, HKDF/HMAC-SHA256 and RFC8439 ChaCha20-Poly1305. No post-quantum protocol is implemented.

Encode(PK) is byte 05 followed by the 32-byte little-endian X25519 public key. The prekey signature covers exactly Encode(SPK). XEdDSA uses the clamped X25519 scalar, sign-zero Edwards normalization and SHA512(FE FF…FF || a || message || Z) with 64 freshly drawn random bytes, followed by its specified challenge and uncofactored verification equation. This is not the existing Ed25519 seed signer. The X3DH KDF uses 32 FF bytes followed by its three or four DH outputs, a zero SHA256-length salt and ASCII info LemmaTrix-Messenger-v1. Every all-zero DH output fails closed.

The Double Ratchet root KDF is HKDF-SHA256 with the current root as salt, the X25519 output as input material and ASCII info LemmaTrix-DR-v1, yielding root then chain key. The chain KDF uses HMAC-SHA256 with byte 01 for the message key and byte 02 for the next chain key. Each message key encrypts one committed message with nonce zero. Retries return those exact bytes. Each chain is bounded to 1,048,576 messages; no counter wraps. There are eight skipped message keys per approved device. Authentication failure discards the tentative ratchet, skipped-key and prekey changes.

Canonical invitation and message bytes

All integers in these records are little-endian UInt64 words. The 256-byte public bundle has magic 0x31424d544c, version 1, key generation and one-time-prekey presence at offsets 0, 8, 16 and 24. Identity, signed-prekey and optional one-time-prekey public keys occupy offsets 32, 64 and 96. The 64-byte XEdDSA signature is at 128, federation at 192 and random device/mailbox identifier at 224. The extended 320-byte invitation appends a scoped deposit token and the selected mailbox descriptor commitment. It supplies no fetch token. These are invitation bytes intended for explicit exchange, not an anonymous directory publication.

The certified 672-byte invitation appends a 352-byte native Identity role-2, purpose-1 certificate to that 320-byte public invitation. Its fixed 128-byte body is contact magic 0x315443544c, schema 1, device generation, flags 1, stable messaging identity key, device identifier and SHA256 of identity key, federation and device identifier. The enclosing certificate binds its independent scoped Ed25519 certification identity, federation and scope. Native import verifies that signature and every stable binding field, then separately verifies the XEdDSA signed prekey. The Ed25519 certificate is not an XEdDSA identity or prekey signature. Public certification establishes possession and declared linking, not a human identity. The legacy 256-byte and 320-byte invitation profiles remain explicitly unbound. Upgrading an approved unbound device to a certified binding requires contact approval again; a certified contact cannot silently accept an unbound refresh or a different certificate.

The displayed contact fingerprint is SHA256 of the identity key, federation and device identifier, in that order. Import verifies the prekey signature; approval requires the exact candidate fingerprint. A known identity with substituted bundle or mailbox-capability material is rejected. Blocked contacts cannot send. A changed key, unsupported rotation or simultaneous conflicting initiation requires explicit reconciliation; there is no silent identity replacement or automatic session merge. Prekey exhaustion is represented by a bundle without its one-time public prekey. A public mailbox claim never destroys the private prekey: only authenticated, committed initial-message reception does so.

The AEAD associated data is a 32-byte SHA256 commitment followed by the exact 192-byte header. The commitment hashes Encode(IK_A) || Encode(IK_B) || federation || device_A || device_B, with Alice/Bob fixed by X3DH initiation. The mailbox can inspect this public cryptographic header, including scoped identity keys, counters and lengths; it receives no conversation text, attachment key or human contact name. The fixed header is an explicit application framing adaptation and is not a Signal wire format. Initial and established envelopes are at most 720 bytes, requiring the routed broker's bounded fragmentation over smaller application payloads.

Authority and typed owner operations

Guest.MessengerSession is an installed rights-zero, non-networked role 2 owner. Kernel-issued exact caller, package, service, operation and generation bindings mediate its 420–435 operations. The graphical application receives no X25519 private key, ratchet key, vault credential export or raw network/device authority. The independently admitted network coordinator can obtain scoped mailbox capabilities through operation 434 only with its actual network right and exact operation binding. Mailbox tokens are separate from conversation keys. For a caller with a network right, operation 434 accepts only own-mailbox and approved-contact capability exports, reads of already committed attachment ciphertext, exact committed-envelope settlement, public prekey publication, stable public claim identity, and authenticated claimed-prekey acceptance. Plaintext attachment creation and decryption remain denied even when that caller knows a local handle.

The version-1 IPC header is 64 bytes with payload following it. Attachment subcommand 15 returns a selected contact’s public fingerprint, approval/block and certification state. For an approved contact with a committed text outbox, header words4–6 also return its exact retained message handle, state2 and ciphertext length; otherwise these fields are zero. Normal graphical recovery caches that public handle per contact so a user can explicitly press F7 to retry the committed ciphertext after a sender restart. Recovery never sends automatically. Lock clears the cached UI handles; history import clears the native contacts and outboxes and cannot recover this sending authority. Subcommands 16 and 17 stage and durably publish a bounded ciphertext batch; 18 reads that committed ciphertext. Subcommand 20 records an exact ciphertext commitment already accepted by the broker’s authenticated mailbox relationship, allowing the next outbox entry. It is not a public signed receipt. Subcommands 21 and 22 inspect a transfer’s public metadata and bind the canonical project root before encrypting its manifest. Subcommands 23 and 25 export only the local public prekey bundle and a stable per-draft claim commitment. The coordinator publishes the public bundle with recipient fetch authority, claims the approved contact’s prekey with deposit authority and that stable commitment, then calls subcommand 24. That command is available only to the admitted network coordinator; it verifies the approved identity, federation, device and XEdDSA signature, and durably records the claimed prekeys and exact pending-message serial. An initial encryption cannot proceed without that serial-bound committed claim. Retries preserve the stable claim identity and never consume another public claim merely because a response was lost. Publication and claim retries each admit at most 32 attempts per coordinator configuration or draft; cancellation closes an in-flight stream without asserting that the remote claim was undone. Private one-time-prekey destruction remains bound to authenticated initial-message receive commit. Subcommand 26 validates and durably attaches the local public contact certificate; 27 exports the certified invitation and returns unavailable if no local certificate has been attached. Subcommand 15 also returns whether a selected contact has a certified binding. Local and contact public certificates are included in the independently authorized Messenger snapshot. The separate contact-certification seed is not routed through the UI or retained by these operations. Status returns unlocked state, approved-contact count, outbox count, newest inbox serial and retained state. Import returns a candidate slot and 32-byte fingerprint. Poll returns message handle, ciphertext length, committed state and actual contact slot. Incoming exact duplicates return status 10 with the earlier accepted inbox serial; the delivery coordinator may acknowledge only success or this committed duplicate outcome. Failed authentication and failed storage commit never authorize mailbox deletion.

Structured errors are 1 authority, 2 malformed input, 3 expired/not found, 4 quota, 5 locked, 6 entropy failure, 7 unsupported profile, 8 identity/not approved, 9 integrity, 10 committed duplicate, 12 reconciliation and 13 storage commit failure. Kernel asynchronous submission 133, collection 134 and cancellation 135 keep expensive operations outside the graphical input loop; pending collection is a kernel result, not an entropy-failure service status.

Domain 2 publication and recovery

Without explicit domain 2 authorization and unlock, sessions, four outboxes, four approved devices, eight inbox/deduplication records and two attachment transfers are volatile. Restart loses them. Unlock operation 432 accepts an explicitly supplied 32-byte high-entropy credential, independently derives Messenger and nonce-allocator keys, and accepts separate history consent. This is not a human-password KDF. Retaining recoverable protocol state necessarily retains identity, approved contact and ratchet state; message history is an independent option. No Objects-domain key or general vault mount is consumed.

The kernel separately authorizes the current role-2 owner through management operation 174. Restricted syscalls 136–138 expose a 1,024-sector domain-2 region beginning at personal backing sector 5,394,976, immediately after the existing indexed Objects region. A backing needs at least 5,396,000 sectors. Only that current authorized rights-zero owner can access the region. Lock clears accessible owner and vault secrets and revokes the grant through syscall 140. Reauthorization and unlock are both needed afterward. Objects domain 3 and unavailable Wallet domain 1 keep their existing policies.

The 53,248-byte encrypted snapshot contains local protocol state, approved contacts, ciphertext outboxes, deduplication state, optional history and protected attachment keys. Pending plaintext drafts are omitted. When history is declined, deduplication commitments remain while plaintext bodies are omitted and history reads require reconciliation. Nonce allocators occupy relative sectors 0 and 1; alternating encrypted banks and root publications begin at relative sectors 2 and 110, with 108-sector spacing. Each encrypted publication occupies 53,760 padded ciphertext bytes plus its root sector. Allocator publications authenticate a prefix and monotonic counter under a separate key, and flush before encryption. Ciphertext and its commitment flush before the commit root is published and flushed.

A retained send commits exact ciphertext and next ratchet state before collection can return transport bytes. A receive authenticates first, then commits the accepted ratchet, inbox policy and deduplication state before its success response. Failed publication restores the prior accessible state. Unknown older messages beyond the eight-record deduplication/skipped-key window return reconciliation; there is no indefinite exactly-once contract.

Normal recovery requires the newest authenticated publication to agree with the latest authenticated nonce allocator. A missing newer root with a newer allocator cannot resume an older chain. Explicit history import may recover an eligible older bank, but first reserves and flushes a newer nonce counter, then invalidates and flushes both sending roots on that input copy. Even an interruption between those publications prevents normal recovery from resuming its old roots. The allocator remains, preventing nonce reuse when the same credential explicitly creates a fresh domain. Import clears the old identity, prekeys, session chains, outboxes, mailbox capabilities and attachment sending state. Eligible history is accessible in memory. F2 returns reconciliation-required while that archival view is open; first press F8 to clear its history and cached contact references, then F2 to create fresh device authority. This prevents an old conversation slot from being attributed to a newly approved contact. Explicit F9/create and renewed contact approval are required for retained operation. A later normal recovery of the retired input copy fails; the user must preserve an external backup separately if it is still needed as a history source. Entire-backing substitution remains undetectable without an external freshness anchor; selecting ordinary recovery after such substitution cannot be advertised as rollback detection. Forget invalidates roots but does not erase ciphertext remnants, external backups, host memory or recipient copies.

Bounded attachment profile

There are two transfers, each at most 8 MiB, with 512-byte chunks and sixteen exact ciphertext retry entries per transfer. Their 20,480-byte private cache begins at 0x6d0000, separate from cryptographic scratch, the vault snapshot, and rollback storage. A protected 128-byte manifest contains versioned magic, total length, chunk size, random key, random transfer identity and the selected canonical project root; only the end-to-end session carries it. The UI sees the attachment title and local handle, never the manifest key. Each chunk's AAD binds the profile, random transfer identity, total length, chunk index and actual length. Its nonce is zero-prefix plus little-endian chunk index. Ciphertext commitments, rather than plaintext content hashes, can address its transport bytes.

Staging encrypts into the private exact-ciphertext cache without returning transport bytes. Publication atomically commits that cache and its high-water counter before the broker can read any batch ciphertext. Recovery resumes from those committed bytes; a changed-plaintext retry is rejected, and a chunk no longer in the bounded exact cache requires reconciliation. Single-chunk operation 2 likewise commits before returning ciphertext. Authenticated received-chunk decryption is stateless and may be retried after recovery. Native bundle-2 processing reads authorized project slices through a trusted compositor picker; delivery aggregates at most fourteen encrypted chunks into a bounded mailbox blob. Receiving a manifest or blob does not install, run, publish or seed content. Explicit graphical import verifies the canonical project root and commits an Objects project before permitting destructive blob acknowledgment. Objects retention requires its separate consent; Messenger unlock does not mount Objects.
