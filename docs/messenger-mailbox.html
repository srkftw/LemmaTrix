Native Messenger surface and ciphertext mailbox

Current shared-client operation

Campaign009 supplies four independent8KiB upload banks, each bound to the complete native caller incarnation, internal terminal generation and relevant recipient capability. Native Network is a transport owner, not an authenticated person. A live upload handle never substitutes for durable exact-ciphertext idempotency. Newly authorized sessions can reconcile committed requests; stale origins cannot append or collect another client’s staging.

One finite writer publishes durable queue state and signed receipts before acceptance. An incomplete upload does not block unrelated prekey publication/claim, committed reads or other admitted clients. Receipt scratch is disjoint from every stage bank. Progress and absolute deadlines reclaim stalled staging; cancellation is scoped. Native listeners replenish without per-client operator stop/listen. The older single-client observations in Campaign008 retain their historical image identities; the current guide is shared Feed/LemmaNET operation.

Native delivery coordinator

Guest.MessengerDelivery is a separately admitted role-4 package with exactly right 1024. The graphical caller receives exact operations 460–463, while operation 464 is administrative configuration of its current role-2 owner. The coordinator has only owner operations 427, 428 and 434: it cannot read conversation plaintext. It verifies a queued ciphertext against that owner's exact committed outbox and approved contact, then obtains only the narrowly authorized mailbox capabilities. Before each terminal request it rechecks current contact or local ownership and compares the selected mailbox descriptor with the terminal's authenticated descriptor.

Operation 460 carries the stable message handle, ciphertext length, required mode 1, actual contact handle and explicit fresh-admission flag, followed by ciphertext SHA256 and exact ciphertext. A retry sets fresh admission to zero. Operation 461 reports local work or actual mailbox durable publication after the native owner commits its exact-ciphertext settlement marker; 463 reports completed receive acknowledgments. The receive path fetches bounded ciphertext, calls the native owner to authenticate and commit it, and sends a destructive mailbox acknowledgment only for owner status 0 or retained exact-duplicate status 10. Authentication, commit or reconciliation failures cannot authorize deletion. The live acknowledgment predicate has source-level checks for authentication and storage-failure denial.

Operation 462 cancels only when it can establish that no terminal request was transmitted; an in-flight or accepted operation reports uncertainty or stored state and retains exact retry material. Operation 462 with handle zero clears coordinator capability and ciphertext buffers and resets its terminal stream. The GUI calls it after successful lock/forget. Each RPC has a finite 5000-monotonic-tick completion deadline and a 512-attempt aggregate bound. Route loss reports unavailable; it does not select encrypted-bulk mode. The connected execution separately records actual signed mailbox acceptance, recipient decryption and the graphical Forge handoff; source availability alone is not that evidence.

Signed durable acceptance

An operator explicitly configures a finite Identity operation-409 authorization using administrative mailbox 440/action 4. The 416-byte public profile contains the role-3-certified receipt-key declaration352, admitted-terms SHA25632 and accepted node-certificate SHA25632. The native mailbox and broker require SHA256 of the exact 64-byte little-endian vector [1, 1, 8388608, 65536, 8192, 16, 8, 1]: schema, mode, maximum recipient bytes, maximum accepted operations, maximum envelope bytes, resident records, recipient count and bounded-retention contract. Its hash is ad3d1ca92a3d4bd84b678167fc4caf418b4a40d481a8595c409afa5922853588. Recipient enrollment may tighten these maxima; node admission has its own independent work/byte caps. The protected grant handle is volatile and exact to the current service incarnation; it is reauthorized after restart. A changed profile is refused while retained signed receipts exist. Administrative action 5 clears receipt metadata only when no live envelope exists and requires a fresh profile before deposits resume.

For this configured contract the first native publication makes ciphertext durable. An asynchronous Identity job signs exactly the 192-byte acceptance body: magic/version, accepted kind 1, original service incarnation, request32, ciphertext commitment32, terms32, node certificate32, byte length, durable generation, bounded-retention contract 1 and reserved zero. A second publication commits its signature64 before acceptance or recipient fetch is exposed. If signing or either publication fails, the mailbox cannot report signed acceptance. A recovered unsigned admission receives a current incarnation/generation binding and another durable publication before it can be signed. Already signed historical receipts are returned unchanged.

The broker obtains the accepted node certificate through native Network operation 47, checks its hash against the selected approved descriptor, and verifies the public declaration returned by mailbox 441/action 10. It then verifies the exact signed body/signature returned with durable acceptance before settling the native outbox. Public receipt material is distinct from conversation plaintext and contains no sender name or private title. Legacy unconfigured component mailboxes retain their unsigned wire contract; the product delivery broker rejects that profile rather than silently lowering its receipt requirement.

Mailbox wire version 1

All words are little-endian 64-bit values. The 64-byte header is operation, action, a, b, c, d, 0, version=1. Payload starts at byte 64. The kernel supplies the authenticated local caller incarnation and actual rights; the mailbox rechecks the current exact binding before dispatch. Transport must carry the complete terminal request, including its capability, inside the protected terminal stream. This profile is not a relay header.

Storage, resource and recovery contract

The native process uses one explicitly admitted legacy ServerStore namespace, at most one MiB. It performs no raw block syscall. The resident representation contains eight recipient records, sixteen queue rows of 256-byte metadata plus at most 8192 ciphertext bytes, and eight public 256-byte prekey bundles: 141,312 bytes total. Serialized schema 2 stores the 8704-byte fixed header/index and only live ciphertext, rounded to 512 bytes, at most 139,776 bytes. Startup also accepts the legacy 141,312-byte schema 1 representation; the next native publication writes schema 2. Each packed offset, live commitment, counter and zero-padding region is validated. The personal Messenger vault is not this operator store. The operator snapshot contains capability hashes, opaque recipient/request identifiers, ciphertext commitments, lengths and accounting. It contains no conversation text, private attachment hash, sender name, title or private session key. The operator can still observe recipient linkage, queue occupancy, lengths, arrival/fetch patterns and its terminal relationship.

Publication copies tentative changes into a candidate snapshot, appends one 512-byte storage request per scheduling turn and collects the durable ServerStore commit. Only afterward does the active snapshot change or a successful acceptance poll become visible. The storage service writes inactive ciphertext/index banks and flushes before publishing the root. Startup verifies the recovered namespace hash, schema, bounded counters and each live envelope's ciphertext commitment. Restart requires fresh exact process and ServerStore grants; stored capabilities are hashes rather than process authority.

Lifetime accepted bytes and attempts survive restart and exact retries do not replenish them. These are finite allowances, not civil-time leases. Incomplete staging has a1000-monotonic-tick inactivity lease. Only an authenticated positive append at the exact next offset renews it, before its existing deadline; the interval remains1000 and at most8192 renewals are admitted. Invalid, repeated or expired input cannot renew. An expired stage cannot be revived before maintenance by append, commit or an idempotent begin. This bounds incomplete work; no absolute retention-expiry guarantee is offered. Completed acknowledgment releases a row for reuse. Tombstones remember the last sixteen retained request allocations; once reuse evicts history, an unknown retry requires explicit reconciliation/fresh admission. There is no claim of indefinite exactly-once delivery. Recovery cannot detect an undetectably substituted whole backing without an external freshness anchor. Logical reclamation does not promise erasure of old banks or external backups.

Opaque attachment batch profile

Attachment fetch operation 463/action 1 accepts a one-shot explicit-retry bit in header word c. Ordinary chunk collection uses zero. An explicit graphical F7 may set one to re-admit a failed transport-unavailable fetch of an already parked transfer, up to three times per retained coordinator row. Authorization, integrity and acknowledgment failures remain failed; no retry deletes ciphertext. Re-admission retains the independently enforced native channel and service quotas. Acknowledged row release clears any matching resident blob, and cached access checks the random transfer identifier and batch range before returning ciphertext.

A mailbox attachment blob has a 64-byte header: magic 0x31424c424d544c, version 1, random transfer identifier32, first chunk index and count 1–14. Each record contains its absolute index, ciphertext length 17–528 and exact AEAD ciphertext. Fourteen full chunks occupy 7680 bytes, within the mailbox 8192-byte bound. Chunk authentication independently binds random object identity, total plaintext length, index and exact chunk length. The mailbox commitment hashes this ciphertext blob; it exposes no plaintext content hash. There is one admitted upload and at most sixteen parked receive blobs. The broker rechecks current contact approval before each deposit RPC and fetches ciphertext only through the session owner's committed cache API. Text and input remain separate from whole-archive allocation; a terminal RPC has a finite failure deadline. Scheduling and responsiveness still require the connected stalled-transfer execution check.

Shared terminal foreground admission

The coordinator admits one frozen Forge metadata reference in a160-byte region at 0x675000. Root, selected federation, policy and exact caller are immutable while queued. A status-zero phase6 reply means queued locally; it is not verified metadata. Exact same-caller retries are idempotent, conflicting requests are busy, and another caller cannot inspect or cancel the selected request. The live requestCallerAllowed predicate rejects zero or different owners. The queue drains already admitted owner and terminal work, including authenticated receive commit and deletion acknowledgment. It then prevents a new background mailbox poll from taking the next idle boundary and begins the existing Forge verifier. A queued request has an8192-turn bound and returns unavailable if it cannot begin. Cancellation clears the bounded queued reference; it does not claim to retract a request already forwarded.

Administrative464/action2 is a64-byte, read-only public diagnostic: header words1–6 contain Forge phase, Forge reason, owner-request-pending flag, terminal-request-pending flag, send phase and receive phase. It exports no capability, content, reference, key or ciphertext. Its existing exact administrative operation grant is still required. User operation461/action3 collects only that caller’s admitted Forge result and preserves signature, selected federation, immutable root, policy and current native Registry admission checks.

Attachment admission uses one passive scheduling hint, scoped to its exact caller, handle, chunk, contact and flag. It reserves at most8192 coordinator work quanta without extending that bound on matching retries. It starts no owner or network operation. Only a subsequent current kernel-checked request can consume the opportunity. The same bounded path covers a failed exact-batch retry and explicit receipt-window reconciliation; these cannot be starved by a new phase-zero background poll. New phase-zero background polls wait, while already admitted partial reads, owner commits and acknowledgment phases drain; expiry reports unavailable rather than retaining unbounded authority. Cancellation, reconfiguration and send/receive failure clear the hint. This scheduler-work bound is not civil time.

Administrative delivery464/action3 returns only send phase/reason, attachment phase/reason and passive-hint mode/work count in a64-byte header. It shares the current exact binding and administrative-right checks with existing464 controls, exposes no plaintext, key, capability or ciphertext, and does not mutate admitted work.

Administrative440/h6 and h7 expose only current incomplete-stage presence, handle, length, offset and monotonic deadline/observation, plus a bounded volatile last-expiration record. They require the existing exact administrative binding and export no recipient identifier, capability, plaintext or ciphertext. Delivery464/action4 similarly exposes only last RPC purpose, phase, length, offset, opaque remote handle and deadline. These diagnostics do not extend authority or staging leases.
