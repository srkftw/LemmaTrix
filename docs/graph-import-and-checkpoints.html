Native transactional graph import and stable signing authority

Campaign 004 adds one bounded Objects importer for explicitly selected local bundles, incoming peer closures and encrypted Project Vault recovery. Graph identity, local root authority, publisher namespace and execution approval remain separate. This page documents implemented interfaces; campaign evidence identifies the executions actually performed.

Import-v1 transaction

Every request uses the existing Objects ABI: eight little-endian 64-bit header words operation, handle, a, b, c, d, e, 1, then bounded bytes. No local capability crosses a peer connection. Callers need ordinary create/revise rights; no request can obtain management authority. The dedicated kernel-supplied Vault recovery flag expands only importer capacity, never returned rights.

The guest accepts records in any dependency order. Stages have no Object grants and are invisible to ordinary resolution/enumeration. A bounded native pass validates actual payload hashes, canonical node IDs, typed edges, canonical names and source/evidence/release commitments. All offered records must be in the selected root closure; unrelated extras are rejected. Missing/cyclic dependencies make no progress and fail. Only after all checks and root/capability capacity reservation does the single-threaded service publish the entire selected root set. Failure, cancellation or quota exhaustion clears transaction-owned stages without changing existing roots. An abandoned dead-caller stage is reclaimed on transaction-slot reuse. There is no durable personal import checkpoint.

Ordinary callers may own at most four named roots and import at most 24 records/one MiB per transaction; management and the dedicated trusted recovery profile permit six selected roots, 64 records and four MiB. The ordinary root quota is checked both when staging begins and immediately before atomic publication: overlapping transactions cannot each reserve the same remaining ownership capacity. A rejected final transaction reclaims its private records while earlier committed roots remain usable. Each record is at most 64 KiB. Capacity is shared with current projects and pinned work. A quota error is a real limit, not partial success. Names are local aliases; importing an existing logical identity creates a different live root instance and grants no signing ownership, publisher trust or execution permission.

Asynchronous validation and atomic publication

Campaign 005 adds Objects operations 44–46 without changing the Import-v1 record encoding. The transaction handle, full owner incarnation, selected immutable heads, frozen record allocation generations and nonzero caller operation ID bind one job. A UI selection change cannot replace its bytes or root names. There are four global job contexts of 8192 bytes each, scheduled fairly in round-robin order. Submitting requires the existing create/revise authority; unauthenticated peers cannot allocate jobs. Terminal results occupy their slot until explicit forgetting, permitting reconciliation of a lost completion reply.

States are 2 running, 3 paused, 4 committed, 5 cancelled and 6 failed. Status 3 rejects stale or foreign handles, 4 denotes quota/capacity failure, 6 incomplete input and 7 a busy/frozen operation. Before submit, operation 40 still reports staging progress. After submit, operation 43 can use only already checked generation-bound records; it cannot force a synchronous hash of an unchecked record.

Each hash turn compresses at most eight SHA-256 blocks (512 bytes). Typed validation handles at most one edge or canonical source entry per turn. Release validation hashes the actual ordered binary fragments with a private cursor rather than concatenating the executable into a second payload-sized buffer. A private 64-entry closure queue and exact read-grant witnesses bind committed dependencies to record and capability generations. Revoking a dependency grant or replacing its allocation invalidates later work. Staged bytes remain private to their transaction even after their typed checks have finished.

The global ProjectGraph scope and asynchronous context exist only around one non-yielding validation quantum. Before any other IPC dispatch, Objects clears both scope fields, graph marks, hash/small scratch, the release digest and the complete 8192-byte JSON scratch. Hash state and cursors survive only in the owning private job context. The scheduler uses the kernel's monotonic tick/deadline operations 116/117, not application loop counts. It serves incoming requests between quanta. Cancel/failure cleanup erases at most 512 payload bytes per turn and checks each allocation's owner, transaction and generation before reclaiming it. At most four liveness checks per turn find dead owners; a paused dead owner's state is reclaimed on the next Objects request or active job turn, without an idle polling timer.

Final publication is one short, non-yielding turn. It rechecks the current owner and captured rights, each staged allocation, all dependency witnesses, selected closure completeness, current root/capability capacity, ordinary root quota and current alias collisions. It then publishes all selected roots exactly once. Cancellation and failure reclaim unpublished stages; an acknowledged committed effect remains queryable even if the original reply was lost. A timeout does not establish rollback. This mechanism adds no personal persistence or restart authority.

Current-right checks distinguish raw process rights from the kernel-injected service-role flags 0x200000000 and 0x400000000. Only those two flags are excluded from comparison with syscall34; the raw Launcher administrative bit 0x100000000 remains required. Captured trusted role flags continue to authorize the selected recovery capacity at final publication. This relies on the kernel checking the full live owner incarnation and keeping its service role immutable for that incarnation. It grants no role authority to an ordinary application.

Operation43 rejects a matching cancelled, failed or cleaning asynchronous context immediately. Cleanup also invalidates the record's generation-bound integrity memo before wiping its first payload slice. Checked private bytes therefore cannot be returned after cancellation while bounded reclamation is still running.

Stable identity and publication scheme 3

Legacy signed release envelopes retain version 2 and scheme word zero at byte 488. Their project ID remains SHA-256 of the declared display alias under the original rules. Existing signatures and hashes are neither rewritten nor reinterpreted.

New graph-bound publications set the signed scheme word at byte 488 to 3 and keep bytes 496–511 zero. The publication ID at bytes 128–159 is SHA256("LT-PUBLICATION-3\0" || logicalProjectID32 || publisherKeyID32), including the single terminating zero byte. The canonical signed manifest uses schema 3 and an explicit identity_mapping containing the logical Project ID, publication ID and publisher key ID. Objects derives the logical identity from the actual canonical source graph and recomputes this mapping when admitting a Release record. A renamed alias preserves this namespace; a fork or a different publisher receives its own namespace. Launcher trust and local execution approval remain separate decisions.

BuildJobs freezes the source closure and records the exact source root, toolchain, service incarnation, job ID, original live root-instance binding, caller/delegator and fixed Main.main/profile-2 recipe. Pending queue and immutable authority replies are 256 bytes. At offsets 160, 192, 200, 208 and 216 they contain logical ID (32 bytes), live binding, requester, delegator and recipe 1. Administrative operation 7 returns this authority even after completion; it rechecks that the original delegation and requester remain alive. Reimporting identical graph bytes cannot reproduce the live binding.

Compilation has no publisher key. Standalone project publish also requires --root and compares session assertions with the actual current guest job authority. This is narrowly scoped bootstrap signing, not a native compiler or an independent operator.

Private verified record reads

Import-v1 operation43 and ProjectSDK.importVerifiedRead let only the stage owner read up to512 bytes from a completely received staged record. Before returning any byte, Objects hashes the actual payload and canonical node encoding against the offered commitments. Partial, substituted, stale or cancelled allocations fail. The checked flag is private to that allocation generation and resets on slot reuse. Such bytes are integrity-checked private transfer material; missing dependency closure still prevents commit, and the operation supplies no ordinary Object capability, publisher authority or published root. A transfer cache may reuse independently checked immutable records after fresh peer authentication/authorization, while the new complete import must validate the final selected closure again.

Checkpoint schema 2 and explicit history lifetime

Objects operation 41 and ProjectSDK.checkpoint take a live root, option 1 (source-only), and its exact expected head. Native editor Ctrl-K displays the source-only scope, selected project, current file count and origin/archive commitments; Enter performs the transaction and Escape cancels. Completion reloads all file capabilities and shows actual created/reclaimed counts. The current source remains editable. Non-source attachments leave this selected root; another named/frozen root may keep them pinned.

Schema 1 predecessor edges remain required history. Schema 2 Source and checkpoint Manifest nodes keep their exact predecessor IDs as explicitly archival commitments, so a missing predecessor payload is not advertised as present. Canonical node hashing still includes that predecessor and now commits schema word 2. Current typed Manifest edges remain required. A schema 2 checkpoint Manifest has the ordinary ordered entries followed by exactly 128 detail bytes: magic 0x3254504b4843544c, version 2, logical origin ID (32), original Manifest payload hash (32), archived head (32), source-only scope 1 and reserved zero. The guest recomputes the original schema 1 Manifest ID from its payload-hash commitment and a zero origin predecessor. Logical identity therefore retains its original verifiable content commitment without retaining the old payload closure.

Checkpoint allocation and validation occur before root publication. It clones current source files with archival predecessors, commits the checkpoint head atomically, and reclaims only superseded records from that old closure that the caller owns, that no other caller holds, and that no named/frozen root still pins. Private unrelated objects are outside that reclaim scope. Other owners' data and foreign grants remain. Previously pinned history released later may require a further explicit lifetime operation; the current collector does not promise automatic reclamation of every former archive. Larger capacity alone is not the checkpoint mechanism.

Project Vault v2 index node bytes 128–135 now declare graph schema 1 or 2; zero retains its existing legacy meaning of schema 1, with remaining reserved bytes zero. Both schemas remain authenticated inside the existing two-bank format. Older v2 images remain readable without reformatting; old software that does not understand this extension rejects a new schema-2 index. Vault named-root retention still merges prior explicitly retained history; local checkpoint reclamation does not promise deletion of already retained or distributed copies.

Fork-v1 lineage and independent publisher

Objects operation 42 and ProjectSDK.forkProject require a selected live root, exact expected head, explicit new local name and chosen publisher key ID. The trusted editor Ctrl-F prompt accepts the name and 64 hexadecimal publisher-ID digits. The guest clones current Source nodes under archival schema 2, creates a fresh origin Manifest with a typed .fork member, and draws a 32-byte entropy commitment through the Objects-only kernel primitive. An imported upstream identity supplies no signing authority.

The kind-15 Fork payload is 208 bytes: a canonical zero-entry typed record header, then detail magic 0x314b524f46544c, version 1, upstream logical Project ID (32), exact upstream head (32), upstream release ID (32, currently zero when a source-only fork is selected), explicitly chosen publisher key ID (32) and fresh nonce (32). It is a content commitment, not a standalone publisher signature. A later signed Release covers the source/Fork closure, and both native graph admission and the scoped bootstrap signer reject a different publisher. A source-only checkpoint preserves that Fork member and its publisher binding.

The fork has a distinct canonical logical identity and fresh live root-instance binding. Source/resource edits do not change upstream bytes. It inherits no upstream update, signing, trust, federation or network grant. Provenance beyond an archived exact fork point may be unavailable; the reference remains visible rather than claiming its payload was retained.

Native vault recovery

./lt vault-init /explicit/objects.img --sectors 24576 --key-out /explicit/objects.key
./lt run --backend qemu --socket /tmp/creator.sock --vault /explicit/objects.img
./lt project-vault --socket /tmp/creator.sock --key /explicit/objects.key inspect
./lt project-vault --socket /tmp/creator.sock --key /explicit/objects.key recover

Use the native trusted vault unlock/inventory/recovery controls for routine recovery. Operation 217 selects a root bit mask in header word b and optionally the displayed expected generation in c. The guest authenticates the selected vault generation, derives the selected dependency closure itself, streams it to the same Objects transaction API and delegates fresh ordinary capabilities to Launcher and the trusted workspace. Host provisioning can supply an explicitly selected opaque backing/key, but Python no longer reconstructs or orders graph semantics. The old 512-sector single-object development image is too small for multi-project banks; provision the explicit 24576-sector profile. A failed write preserves the previous committed vault generation and reports its failed stage.

Assurance and limits

The source-level theorem incomplete_import_denied proves the pure commit gate denies incomplete dependencies. It does not prove parser memory safety, cryptography, durable hardware writes, compiler correctness or full atomic execution. Existing scoped proofs remain in place. Focused executable checks are tests/graph_importer.py, tests/graph_checkpoint.py, tests/stable_publication.py and tests/native_project_recovery.py. See campaign 004 evidence for their actual image hashes and environments. These interfaces advance DAT, STORE, FORGE, SDK, IDE and VAULT prerequisites; they do not complete a whole release gate, privacy routing or independent administration.
