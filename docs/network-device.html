LT-Stream-v2: guest-owned byte transport

30 October 2026. LT-Stream-v2 uses modern virtio-mmio device ID3 with non-console port1 named lt-net1: receive queue4, transmit queue5 and control queues2/3. It negotiates VERSION_1 and MULTIPORT under OASIS Virtio1.2 sections4.2 and5.3; indirect descriptors, packed queues, event-index and console-size remain unavailable. QEMU explicitly binds virtio-serial-device,max_ports=2 and virtserialport,nr=1,name=lt-net1 to the selected socket chardev. UART remains management only.

The supervisor-owned shared control helper posts eight bounded64byte receive buffers, sends DEVICE_READY, validates the selected PORT_ADD/name, sends PORT_READY, observes host PORT_OPEN and sends its own PORT_OPEN. Each runtime pump consumes at most eight messages and observes closure. This is the same bounded mechanism consumed by PCM2, with separate queues, buffers and state. Unknown ports, unexpected messages, invalid names, lengths and queue indices fail closed.

Earlier images retain LT-Stream-v1 port0/queues0/1. Their QEMU virtconsole endpoint can discard bytes on short writes instead of applying backpressure, as confirmed by QEMU console implementation. It is unsuitable for claiming lossless operation under a blocked adapter. Stream2 uses the non-console path that preserves partial writes. The versioned image header at offset0x200420 is <8sQQ: magic LTDEV2\0\0, audio profile2 and network profile2. Earlier zero/short images select legacy profile1; unknown profiles reject. Both interpreters keep that legacy mode while supporting the new queues when MULTIPORT is negotiated.

Guest/Devices.lean discovers the device by ID, resets and acknowledges it, negotiates features, checks queue capacity, configures both direct split queues, and posts a bounded receive buffer. Queues contain eight entries with one descriptor outstanding per direction. Each buffer is at most 1,024 bytes. Descriptors, indices and data bounce buffers live only in supervisor memory at0x80e20000–0x80e24800. Stream2 adds control context0x80e31000, receive/transmit rings0x80e32000/0x80e34000 and buffers0x80e36000–0x80e36407; these are disjoint from PCM2, display, block and guarded application mappings. Application pointers never become device DMA addresses. Receive completion validates descriptor identity, bounded length and used index, retains unread suffixes, and reposts only after consumption. Transmit acceptance copies immutable bytes to its owned bounce buffer and applies backpressure until completion. Failed/needs-reset devices refuse further operations.

The independently authored x86-64 and AArch64 assembly emulators implement the same modern register/queue profile at MMIO slot 5. They validate queue address alignment, full DMA ranges, descriptor flags/indices/lengths and available-ring bounds before nonblocking recv/send syscalls. Partial sends retain descriptor ownership until all bytes complete. EAGAIN and EINTR preserve work; EOF and fatal socket errors fail the device. An explicitly inherited socket FD provides opaque bytes; no host component parses peer messages or decides catalog/object policy.

LT-Transport-v2 adapter envelope

The optional --network-mux host adapter carries four independent opaque socket channels over the selected LT-Stream-v2 generic-port queues. QEMU and both assembly emulators continue to transport identical raw queue bytes. The selected MULTIPORT device contract adds no host content parser. Guest/Transport.lean owns framing and channel buffers; tools/transport.py owns only explicit socket I/O. The adapter never receives credentials, graph handles, content admission or retention policy.

Every frame has a 16-byte little-endian header: magic32 0x324d544c (“LTM2”), opcode8, channel8 (0–3), payload length16 (0–1008), connection epoch32, and result/value32. Guest commands are 1 connect, 2 listen, 3 close and 7 data. Host events are 4 connected, 5 closed, 6 error, 7 data, 8 accepted and 9 listening. Connect/listen payloads contain 1–96 ASCII bytes of an explicit numeric IPv4 endpoint or, for connect, an absolute UNIX socket path. Data is opaque ciphertext. Channel and endpoint information are disclosed to the host adapter; encryption is not anonymity. The channel and epoch are local adapter identities and never remote authority.

Each accepted/connected socket and each loss advances its channel epoch; old queued input/output is not concatenated with a replacement connection. A data command with a stale epoch is rejected. Loss/reset clears the affected guest’s partial frames, authenticated inbox, keys, grants and pending jobs. Validated application chunks may survive separately only within an approved content policy. Fresh authorization is required after a new Noise handshake. A busy output frame finishes before its queued close control; revocation prevents future application work and does not recall bytes already accepted by the adapter.

A listener may be explicitly selected by several local channels at the same endpoint. It accepts into the lowest awaiting channel; each channel’s independently provisioned Noise relationship must authenticate before it can deliver application data. Operators should open ordered client relationships deliberately or use separate endpoints; a mismatched ordered identity fails authentication, and the host does not inspect identities to select credentials. The four-channel bound includes listeners and accepted relationships. Shared adapter framing can impose head-of-line backpressure; a high-throughput multi-queue transport remains future work.

Explicit host endpoints and reconnect boundary

./lt run --backend qemu --socket /tmp/creator.sock --network 127.0.0.1:7410
./lt run --backend x86_64 --socket /tmp/server.sock --network-listen 127.0.0.1:7410
./lt run --backend aarch64 --socket /tmp/recipient.sock --network /tmp/explicit-peer.sock

The legacy single-relationship host relay limits each directional buffer to64KiB and forwards bytes without interpretation. The native Library uses --network-mux and its explicit per-channel connection events above. TCP endpoints must be explicit numeric addresses; there is no ambient DNS. A listener accepts one peer at a time. Reconnection uses bounded backoff and discards interrupted relay buffers. A generic port being open describes only the local byte adapter; initialized status does not mean a remote authenticated peer is available. The guest protocol must detect inactivity, discard expired sessions, negotiate fresh keys and reauthorize resumable immutable content before accepting bytes from a new stream. No device-level claim of authenticated reconnect, anonymity or forward secrecy follows from this transport.

Objects and server backing are distinct purposes

Block discovery no longer selects whichever device appeared last. Guest initialization issues virtio-blk GET_ID and accepts only an exact twenty-byte, zero-padded serial: lt-objects-v1 for Objects Vault purpose 1 or lt-server-v1 for explicit server store purpose 2. Unknown serials remain unused. Duplicate devices claiming one purpose disable that purpose rather than choosing one. Device identity is an explicit operator binding; an untrusted host can impersonate devices, as it already controls guest execution. The on-disk vault format is unchanged, with no reformat or silent migration.

./lt run --socket /tmp/personal.sock --vault build/objects.img
./lt run --socket /tmp/server.sock --server-store build/server.img
./lt run --socket /tmp/recovery.sock --server-store build/server.img --server-store-readonly
# Both may be attached explicitly; they must be distinct backing files.
./lt run --socket /tmp/both.sock --vault build/objects.img --server-store build/server.img

Normal launch commands supply the serial to QEMU. Independent QEMU invocation must configure virtio-blk-device,drive=...,serial=lt-objects-v1 or serial=lt-server-v1. Assembly options --vault and --server-store map explicit files to those purposes. Backing files must already exist, contain whole 512-byte sectors and be regular files. No personal directory or backing is created by enrollment, download or launch without an explicitly selected file.

The 4,097-byte transport fixture executed on pinned QEMU RV64, native x86-64 assembly and AArch64 assembly under qemu-aarch64. Thirty-seven-byte opaque host chunks and 113-byte guest reads exercised suffix preservation, repeated queue completions and explicit device reset epoch. All returned the exact bytes (SHA-256 ce358f6bcf45badd0779f5dd38b4ce4a7badaef5621c850c2984c4edb3049323). The block fixture attached both disks and a network device simultaneously, wrote/flushed the server purpose, read the corresponding Objects sector and verified the Objects file remained unchanged on all three backends. QEMU devices with unknown or duplicate purpose serials were refused before any write. All three backends advertised read-only server backing and rejected writes while keeping both files unchanged. These are device component checks, not an authenticated project-transfer journey or native ARM64 hardware evidence.

On full guest image b03e54d30d96c53d69d3baa515f8164b58dcb18369b8ffd006b731b0fc20c01b, the QEMU server-store test published and retrieved 70,001 actual bytes, committed two generations, cancelled an incomplete transaction, and killed the guest after 8,192 bytes reached the inactive bank. A read-only restart retrieved that generation and rejected publication without changing the backing digest. The payload SHA-256 is 236f34dbc7949b759460b34d5b53e6b277f2d5d9e9d85203121861b62da2b8b9.
