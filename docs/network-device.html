LT-Stream-v1: guest-owned byte transport

29 October 2026. This development contract uses modern virtio-mmio console device ID 3, port 0 receive queue 0 and transmit queue 1. It implements the singleport profile in OASIS virtio 1.3, sections 2.6, 4.2 and 5.3. Only VIRTIO_F_VERSION_1 is negotiated; MULTIPORT, indirect descriptors, packed queues, event-index and console-size features are not negotiated. The QEMU invocation contract uses an explicit socket chardev and virtio-serial-device with a virtconsole port. UART remains the management console and is never the remote data plane.

Guest/Devices.lean discovers the device by ID, resets and acknowledges it, negotiates features, checks queue capacity, configures both direct split queues, and posts a bounded receive buffer. Queues contain eight entries with one descriptor outstanding per direction. Each buffer is at most 1,024 bytes. Descriptors, indices and bounce buffers live only in supervisor memory at 0x80e10000–0x80e14800. Application pointers never become device DMA addresses. Receive completion validates descriptor identity, bounded length and used index, retains unread suffixes, and reposts only after consumption. Transmit acceptance copies immutable bytes to its owned bounce buffer and applies backpressure until completion. Failed/needs-reset devices refuse further operations.

The independently authored x86-64 and AArch64 assembly emulators implement the same modern register/queue profile at MMIO slot 5. They validate queue address alignment, full DMA ranges, descriptor flags/indices/lengths and available-ring bounds before nonblocking recv/send syscalls. Partial sends retain descriptor ownership until all bytes complete. EAGAIN and EINTR preserve work; EOF and fatal socket errors fail the device. An explicitly inherited socket FD provides opaque bytes; no host component parses peer messages or decides catalog/object policy.

Kernel endpoint 6 requires explicit signed network right 1024; earlier packages receive no networking. Endpoint 3 additionally accepts explicit server-store right 2048; that right permits mediated store service requests, never raw block syscalls. The release rights ceiling is 4095. Service stop/restart supports broker 6 and storage/object services 2/3; broker restart clears private memory and resets the byte device.

Explicit host endpoints and reconnect boundary

./lt run --backend qemu --socket /tmp/creator.sock --network 127.0.0.1:7410
./lt run --backend x86_64 --socket /tmp/server.sock --network-listen 127.0.0.1:7410
./lt run --backend aarch64 --socket /tmp/recipient.sock --network /tmp/explicit-peer.sock

The host relay limits each directional buffer to 64 KiB and forwards bytes without interpretation. TCP endpoints must be explicit numeric addresses; there is no ambient DNS. A listener accepts one peer at a time. Reconnection uses bounded backoff and discards interrupted relay buffers. Singleport virtio-console does not advertise remote endpoint connection events: initialized status does not mean a remote authenticated peer is available. The guest protocol must detect inactivity, discard expired sessions, negotiate fresh keys and reauthorize resumable immutable content before accepting bytes from a new stream. No device-level claim of authenticated reconnect, anonymity or forward secrecy follows from this transport.

Objects and server backing are distinct purposes

Block discovery no longer selects whichever device appeared last. Guest initialization issues virtio-blk GET_ID and accepts only an exact twenty-byte, zero-padded serial: lt-objects-v1 for Objects Vault purpose 1 or lt-server-v1 for explicit server store purpose 2. Unknown serials remain unused. Duplicate devices claiming one purpose disable that purpose rather than choosing one. Device identity is an explicit operator binding; an untrusted host can impersonate devices, as it already controls guest execution. The on-disk vault format is unchanged, with no reformat or silent migration.

./lt run --socket /tmp/personal.sock --vault build/objects.img
./lt run --socket /tmp/server.sock --server-store build/server.img
# Both may be attached explicitly; they must be distinct backing files.
./lt run --socket /tmp/both.sock --vault build/objects.img --server-store build/server.img

Normal launch commands supply the serial to QEMU. Independent QEMU invocation must configure virtio-blk-device,drive=...,serial=lt-objects-v1 or serial=lt-server-v1. Assembly options --vault and --server-store map explicit files to those purposes. Backing files must already exist, contain whole 512-byte sectors and be regular files. No personal directory or backing is created by enrollment, download or launch without an explicitly selected file.

Focused execution evidence

./lt emulators
python3 tests/network_devices.py
python3 tests/storage_purpose.py

The 4,097-byte transport fixture executed on pinned QEMU RV64, native x86-64 assembly and AArch64 assembly under qemu-aarch64. Thirty-seven-byte opaque host chunks and 113-byte guest reads exercised suffix preservation, repeated queue completions and explicit device reset epoch. All returned the exact bytes (SHA-256 ce358f6bcf45badd0779f5dd38b4ce4a7badaef5621c850c2984c4edb3049323). The block fixture attached both disks and a network device simultaneously, wrote/flushed the server purpose, read the corresponding Objects sector and verified the Objects file remained unchanged on all three backends. A QEMU device with an unknown server serial was refused before any write. These are device component checks, not an authenticated project-transfer journey or native ARM64 hardware evidence.
