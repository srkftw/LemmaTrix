Guest graphics and physical input development contract

The live development machine has a guest-drawn 640 × 400 desktop through a bounded virtio-gpu 2D scanout and virtio-input event queues. The Lean device driver, Lean compositor, and independently installed Lean applications select pixels, glyphs, layout, focus, editing behavior and application state. Host presentation transports pixels and physical input. This is development-profile implementation work; it does not establish LT-Machine-v1 conformance, accelerated graphics, physical display hardware support or physical ARM64 execution.

Compatible transport and devices

The driver scans eight MMIO slots at 0x10001000 + i × 4096, validates magic 0x74726976, and distinguishes transport versions explicitly. Graphics and input require modern version 2. Existing block and RNG drivers accept version 1 or version 2 deliberately. The QEMU reference uses pinned QEMU 11.1.1 with virtio-mmio.force-legacy=false; the assembly machines keep their existing legacy block/RNG slots and add modern graphics/input slots. A guest binary discovers these devices without backend-specific guest code.

Modern setup resets status and awaits acknowledgement, sets ACKNOWLEDGE and DRIVER, requires and negotiates VIRTIO_F_VERSION_1, checks FEATURES_OK, selects queue zero, checks QueueNumMax, supplies separate descriptor/driver/device addresses and high words, sets QueueReady, then sets DRIVER_OK. It never programs QueuePFN on a modern device. Block/RNG retain their bounded legacy setup where version 1 is reported. No indirect descriptors, packed queues, event-index, 3D, blob resources, EDID, cursor resource or input LED feedback are negotiated.

The design follows the Virtio 1.3 MMIO, GPU and input definitions and QEMU's virtio-gpu device documentation. The primary specification includes features outside this implementation. The separately authored x86-64 and AArch64 assembly device implementations validate queue geometry, direct chains, complete DMA spans, resource shape and dirty rectangles before touching host memory.

These ranges are separate from block/RNG DMA and private service arenas. Applications do not map this global framebuffer or device MMIO. The kernel validates bounded surface uploads and the compositor's clipping/focus operations. Application surface storage has a separate per-process bound and is reclaimed on death. The compositor alone supplies trusted chrome. An application-supplied pixel cannot create installation authority.

Presentation and completion

Boot creates resource 1 with format B8G8R8X8, attaches exactly one bounded backing span and selects scanout zero. Runtime presentation uses TRANSFER_TO_HOST_2D followed by RESOURCE_FLUSH. presentBegin(x,y,width,height,token) validates the rectangle, queues a transfer and returns. presentPoll(token) checks one completion and advances to the flush, returning busy or complete. There is no supervisor spin loop waiting for frame completion during normal runtime. The compositor must leave the backing unchanged while a presentation is in progress.

Completion validates the used descriptor ID, returned byte count and GPU response type. A failed device or timeout does not permit an in-flight buffer to be reused. Explicit reset acknowledges transport reset before clearing driver state or queue storage. Boot-only negotiation has a finite polling bound. Rendering belongs to schedulable user code; trap dispatch validates copies and submits bounded device work.

Compositing copies at most eight rows, or 20 KiB, in one trap and yields between slices. Each application upload advances its surface epoch. The compositor snapshots that epoch and acknowledges only its completed final slice; if the application uploaded newer pixels meanwhile, that newer epoch stays dirty. Focus or modal transitions abandon an incomplete composite. Trusted chrome and approval rendering wait through schedulable user-service yields before altering backing owned by an in-flight presentation.

The visible 7 × 7 pointer is drawn by the Lean compositor with a clipped white outline and dark center. It saves at most 196 bytes of underlying pixels in private service memory, restores the old pointer before any application composition or trusted redraw, and overlays the pointer before submitting presentation. Compositor-only syscall 93 permits a single aligned framebuffer row read of at most 28 bytes into checked private memory; applications cannot read or map global scanout. Pointer-only presentation covers the union of the old and new pointer rows. The service waits for the prior transfer/flush before reading or altering backing. This uses the 2D scanout, with no hardware cursor feature negotiated.

Input, focus and loss

The physical input record is little-endian u16 type, u16 code, u32 value, following Linux evdev values. The driver keeps each event queue populated with eight writable buffers, checks used IDs and lengths, consumes bounded work and reposts completed descriptors. The scalar kernel-facing event packs type at bits 48..63, code at bits 32..47 and value at bits 0..31. Relative pointer deltas preserve their signed 32-bit representation. Zero means both physical sources were idle. All-zero SYN_REPORT records are skipped internally with a 32-record budget; nonzero marker 0xfffe000000000000 means bounded work remains and is ignored by the compositor. A queued report cannot make a trusted prompt believe its input queue has drained.

The compositor routes physical input to the current live process incarnation. Focus and surface authority are kernel-checked. Application event queues are bounded; overflow is explicit, and consumers clear modifier/button state after loss. The raw presenter releases held keys/buttons on focus loss and emits SYN_DROPPED. A bounded FIFO overflow preserves a pending loss notification and retries it when the transport drains. It never retries a click as an approval gesture.

Thin host adapter and protocol

The optional Python/Tk adapter contains no fonts, desktop widgets, permission prompts, object graph or editor. It displays complete guest-generated frames and converts host keyboard/pointer events to raw evdev. It requires Python with tkinter and a usable display server. The system Python in the current development environment lacks tkinter; selecting another Python with the package is an explicit dependency, not evidence of a guest implementation.

./lt run --backend x86_64 --socket /tmp/lt-session.sock --graphics /tmp/lt-pixels
python3 tools/pixel_presenter.py --frame /tmp/lt-pixels.bgrx --events /tmp/lt-pixels.evdev

Use --backend aarch64 for the AArch64 assembly interpreter under qemu-aarch64. The session creates and holds a mode-0600 named input FIFO; it removes only a FIFO that it created. The presenter refuses a regular input-history file. UART remains the independent management/recovery stream. The assembly machine's explicit --display-out FILE --input-events FIFO flags expose the same transport without the session helper.

The pixel transport file has 1,024,000 raw BGRX bytes followed by an eight-byte little-endian sequence. The device writes an odd sequence before a flush and an even sequence after its complete pixel write. The presenter accepts only an even sequence unchanged across its pixel read. A partial or failed frame leaves the previously displayed frame visible. This is a disposable pixel transport with no persistence or authenticity claim; it does not contain project objects or authority. Input transport records are raw device events only.

For QEMU, --graphics /tmp/lt-qmp.sock exposes a QMP endpoint while the guest drives the actual virtio-gpu device. Headless capture and input use QMP's screendump and input-send-event endpoints. The reusable device helper follows these boundaries on all backends:

python3 tests/graphical_devices.py --backend qemu --graphics /tmp/lt-qmp.sock --capture /tmp/lt-frame.ppm
python3 tests/graphical_devices.py --backend x86_64 --graphics /tmp/lt-pixels --text 'user input'

The helper's DeviceInput API supports evdev key press/release, ASCII typing, chords, relative pointer motion, buttons, explicit focus loss, and complete-frame capture. It never writes guest memory, invokes application-private setters or substitutes Launcher management calls for UI actions.

Focused executed device evidence

The recorded campaign-003 graphics evidence includes exact component and frozen integrated artifact identities, measured latency, the successful native x86 editor assertions, and AArch64 input-throughput failures. It preserves failed attempts and states which later source fixes were outside those frozen runs.

A temporary Lean driver consumer initialized the device, filled and presented the framebuffer, consumed an A key, relative X motion of seven pixels and a left-button press, then exited through the real finisher. The same RV64 binary ran successfully on QEMU 11.1.1, the native x86-64 assembly interpreter, and the AArch64 assembly interpreter under qemu-aarch64. All produced 640 × 400 pixels with normalized BGRX SHA-256 2786473bbb1aeb31e562d1cf2ac00712da98a421ff26acef90fbab5f2214f1c5. QEMU input came through input-send-event; assembly input came through the raw FIFO and actual device queue. An unaligned store found by both interpreters was fixed before that run.

The adapter's conversion of that completed frame was executed with Python 3.14 and Tk 9 on the available display server, including checking image dimensions and a pixel value. The window was withdrawn for this component check. These are device/component results, not the complete editor/build/vault journey, physical keyboard testing, interactive hardware validation or physical ARM64 evidence.
