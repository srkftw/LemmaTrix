Bounded native content jobs and volatile chunk storage

Campaign 005 development profile, 29 October 2026. ContentStore, ContentFormat and ContentSDK are Lean-authored freestanding guest code. Endpoint 5 hosts the content job module alongside the existing build job service. The host import adapter constructs manifests and transports explicitly selected bytes; it never authorizes content, validates guest storage, decodes playback or maintains a personal content database.

The content service itself has explicitly volatile RAM backing. Durable reservation returns status8, unavailable; it never silently persists a transfer. A separate, explicitly approved ContentVault transaction encrypts one selected complete root or verified checkpoint on authorized Objects-vault backing and imports fresh read authority after restart. Formats4/5 co-store the selected admitted consumer metadata atomically. Without those explicit transactions, restart loses content, collection state and all jobs/grants. The distinct operator namespace archive uses intentional purpose2 retention and never borrows a personal key.

Manifest and authenticated indexing

ContentManifest-v1 is exactly 256 bytes, little endian. Its SHA-256 is an immutable metadata commitment that a consumer release must separately sign and admit. Supplying a matching hash to this service does not establish publisher trust, consumer eligibility, distribution permission, acquisition consent or executable approval.

A leaf hashes 56 bytes: UInt64 domain 0x314641454c544c, UInt64 chunk index, UInt64 exact chunk length, and SHA-256 of the raw chunk. A branch hashes 72 bytes: UInt64 domain 0x3148434e42544c followed by its ordered left and right 32-byte commitments. Trees pad to a power of two using zero-length indexed leaves with SHA-256 of the empty byte sequence. A chunk proof supplies its raw SHA-256 and exactly the declared number of sibling commitments. The service binds the hash to the selected manifest, exact position and exact length before making any range available.

The chunk index lives in the scoped service, outside the resident Project graph and application arenas. The volatile profile keeps its authenticated index and validated chunks in private RAM. There are no nonresident disk index pages in this profile. Serving a range resolves a caller-owned, generation-checked grant, checks the immutable root generation and its validated index entry, then copies only that verified chunk's requested bytes. Neither an immutable hash nor a backing sector address is a read capability. Deduplication is limited to already authorized chunks of the selected root.

Bounds, transaction and job semantics

The dedicated mapping is virtual 0xe00000–0x15fffff. The first 256 KiB contain bounded root/grant/index/job metadata; the next 5.75 MiB contain 1472 × 4096-byte payload pages, 6,029,312 bytes total. The final 2 MiB reserve a bounded authenticated tree cache (four 128-KiB trees; the remainder is unused). Four manifests, 64 grants and four job records are available, with at most two job records per caller. Every chunk job owns one 4096-byte staging buffer and a private SHA-256 context. Each service quantum processes at most eight SHA-256 message blocks, one Merkle branch, one final index entry or one reclaimed payload page. The complete media payload is never allocated in an application arena or imported as thousands of resident graph records.

Reservation checks aggregate chunk capacity and exact manifest/budget binding. Append accepts at most 512 bytes at the next exact offset. Truncation, overflow, wrong proof size, duplicate conflicting digest, position substitution and unsupported versions/modes fail closed. Hashing and Merkle checks run across service turns without touching ProjectGraph.importScope, graph marks or graph hash scratch. An unrelated Objects import therefore uses its original isolated path while content validation runs in a separate service.

Only validated chunks become readable. A partially acquired root remains state 1 and reports unavailable ranges honestly. Finalization scans the required index in bounded quanta. Its final short publication rechecks caller liveness and create authority, root generation, acquisition revocation, complete byte/chunk counts and quota, then sets ready state 2 once. Completion remains queryable until the caller explicitly forgets the terminal job. A lost reply or RPC timeout does not undo an already committed chunk or complete root.

Pause preserves private staging and hash state. Resume requires current live root authority. Cancellation clears unpublished bytes and leaves a terminal result. Releasing the acquisition grant revokes subsequent publication; previously shared read grants remain scoped to their selected immutable root. Garbage collection removes unreferenced roots and reclaims payload pages in bounded service turns, clearing bytes before reuse. A root with any live read grant is retained in this volatile scope. This is a reference preference, not encrypted durable retention or seeding permission.

Public native API

Requests use the standard eight-word version-1 header and kernel ABI2 trusted caller incarnation, actual rights and reply token. ContentSDK calls endpoint 5. The launcher transport adapter uses management operation 160 to forward the same opaque request. Local grant/job handles are never remote protocol stream IDs. Their encoding folds the randomized kernel boot epoch and current service incarnation into the high32 bits before adding the bounded24-bit allocation generation and8-bit slot. The actual full caller incarnation and root generation are checked separately. Restarted grants/jobs are never restored authority, including after fresh allocations reuse numerical table slots; recovery creates new scoped grants instead.

Only enum value 3 is accepted. Interactive onion, delayed mix and private cluster are unavailable; they are never approximated with direct bulk transport.

The source-level lemmas in ContentFormat concern the actual publication predicate: incomplete bytes or revoked publication authority cannot satisfy it. Assumptions remain the truth of caller liveness, current authority/quota and immutable dependency commitments supplied by the service checks. These lemmas do not prove cryptography, correct memory mapping, the compiler, binary correspondence or the whole native Library.

The 30-second stereo edition has 5,760,044 bytes and 1407 chunks; the mono edition has 2,880,044 bytes and 704 chunks. Acquisition policy can choose a supported measurable stereo edition over mono, subject to its byte budget, but a catalog claim alone is not decoder validation.

The focused check uses actual guest APIs and compares every returned media byte by SHA-256. It covers >1 MiB ingestion, partial verified range reads, hash/position substitution, invalid modes, unavailable durable reservation, quotas, idempotency, pause/cancel/forgotten handles, premature publication and an unrelated Objects import/read between content hash quanta. Running the command is not evidence until its result identifies the tested image and environment. It does not establish native provider acquisition, durable restart recovery, audio speaker output or the full RG-06 journey.

No-vault restart and token regression

The focused restart-token check found and corrected a real bug on historical image e3767c2d12d335649bf9acf3e731e23abb24e453c1a03b85a5d8580dab02769a: shifting the full service identity directly discarded its randomized boot-high bits. Old content/job tokens were rejected before fresh allocation, then could name a different newly authorized scope after allocation. The corrected image 643b801e42091c99f5d20e3ff40f5ab293840c6c5377a260491201b2b71c4fe1 folds the boot epoch first. Two fresh guests obtained distinct tokens; old tokens remained rejected before and after fresh different-manifest allocations, while new grants/jobs worked. The finite randomized boot epoch does not establish rollback freshness.

The two-guest no-vault journey on that corrected image used secure Game release 3a56b13d0e211adf25e66d05c09dedc48506c84cb4fe328af8295b3460be7779 and Library release 3a440ae9d37a4f4a99cb0f6fe5634d55bcda12edfc6568c0941aa446afff2dbb. Real DD input solved the puzzle, GameSDK502 exported a192-byte ephemeral save, and public SDK calls created private metadata, a source root,4096 verified content bytes and a paused hash job. Restart without any vault/server backing lost every selected object/root/save/range/job. Repeating the operation created an empty fresh root; old handles stayed denied after allocation. An explicit unlock without backing returned5 and retention returned3. Fresh physical package approvals restarted the Game at moves0/completed0/won0/save0 and refused the old save scope. Library started empty. The private collection metadata was an explicitly labeled Objects boundary fixture; this check does not claim native Library Add or monitoring. Only disclosed framebuffer/transport/hash evidence was captured, with no personal payload backing.
