Native ntor-v3 and ordinary relay-cell profile

This document specifies the implemented circuit engine, its public enrollment adapter and its bounded terminal framing. Engine implementation and primitive vectors do not establish Messenger completion, Tor interoperability or independent operator deployment. The connected campaign report must identify which integrated paths actually executed. Modes 2 and 4 remain unavailable; ordinary explicit mode 3 retains its separate direct bulk profile.

Primary sources and adaptations

The reviewed sources are Noise revision 34, 11 July 2018; Tor’s mutable CREATE2 and ntor-v3 specification, circuit key partition, ordinary relay cells, relay processing, RELAY_EARLY and flow control, reviewed again on 31 October 2026. The preceding source-byte register pins the earlier fetched documents; a date or hash is not a numbered Tor release. AES follows FIPS 197 and CTR follows SP800-38A. SHA-1 follows FIPS180-4 solely for this selected relay profile. SHA3-256 and SHAKE256 follow FIPS202.

The adapter replaces Tor’s TLS channel with Noise_NK_25519_ChaChaPoly_SHA256: responder static pre-message; initiator sends e,es; responder sends e,ee. The prologue is the exact ASCII bytes LT-OnionChannel-v1 followed by SHA-256 of the accepted 480-byte native node certificate. Both handshake payloads are empty. The initiator sends no static identity. Each handshake message is 48 bytes. Channel records use Noise’s little-endian 64-bit nonce with four leading zero bytes, ordered counters and a limit of 2²⁰ records per direction. Reconnection requires fresh native entropy. This adaptation does not establish Tor interoperability.

Public enrollment

Each native Network owner generates separate X25519 transport and onion private keys. An independently scoped native Identity role-3 key certifies a canonical 256-byte declaration inside the existing 480-byte certificate envelope. Only public material crosses management IPC. The declaration binds magic, schema 2, role 7 relay or 8 mailbox, mode 1, profile 1, finite byte/work terms, zero-price contract, transport key, onion key, declared family, generation, revocation bit and a bounded numeric IPv4 endpoint. Its federation, scope and signing identity are bound by the enclosing native certificate. The accepted certificate hash is the channel prologue binding and the ntor verification string.

Approval stages and verifies the complete certificate, then requires its exact displayed SHA-256 commitment. Rotation must retain the same signing identity, federation and scope and increase generation; identity replacement requires explicit revocation and separate approval. Active outgoing channels recheck the accepted certificate commitment and revocation state. A self-signature establishes neither a human identity nor operator independence. Family declarations constrain selection but do not defeat Sybils. Credentials are ephemeral by default. An operator may explicitly authorize native Network retention and supply a 32-byte unlock credential with lt onion retain --key; recover --key requires fresh authorization after boot. Native NodeStore encrypts the two static DH scalars, existing signed public certificate and an optional opaque 192-byte Identity retention blob into alternating authenticated schema-3 records in the separate operator purpose-2 backing, sectors 1–6. It checks the recovered private/public possession relationship before publishing the node. Static-only retention remains supported, including schema-2 recovery. Explicit retain --node-key HANDLE --receipt-key HANDLE asks the native Identity owner to seal separate role-3 node and role-4 receipt seeds under the supplied 32-byte credential; Network stores only that sealed blob. Recovery asks Identity to authenticate and unwrap it, checks its derived node public key against the accepted certificate, and creates fresh ephemeral handles. Live Noise, circuit counters, automatic receipt grants and session keys are never retained. The dedicated extent avoids ServerStore roots at sectors 8–23 and ServiceJobs receipt keys at 56–63. This path requires the operator to protect the backing and unlock credential and explicitly unlock after restart; substituting an older whole backing is not detectable without an external freshness anchor. lt onion lock clears accessible static material and revokes the operator retention grant. A host key file is not a node private-key export or automatic recovery mechanism.

Handshake and cells

The circuit handshake is exactly ntor3-curve25519-sha3_256-1, CREATE2 HTYPE 3. It uses the specified X25519 operations, SHA3-256 domain-separated hashes and MACs, SHAKE256 key derivation and AES-256-CTR encrypted extensions. Every encapsulation length is an unsigned eight-byte big-endian byte count. The optional verification string is exactly the accepted descriptor SHA-256, 32 bytes. The selected CM and SM are exactly one zero byte, the canonical empty extension list; congestion-control or alternate relay-cipher extensions are not negotiated. Client handshake data is 129 bytes; server data is 65 bytes. All-zero DH results, changed descriptors, invalid authentication and unsupported extension messages fail closed.

The first 32 bytes of the final ntor SHAKE stream encrypt SM. The next 92 bytes partition into Df 20, Db 20, Kf 16, Kb 16 and the ordinary profile’s remaining 20-byte nonce. Each hop seeds independent SHA-1 contexts with Df and Db and uses independent zero-IV AES-128-CTR streams with Kf and Kb. The 509-byte body is command 1, recognized 2, stream 2, digest 4, length 2 and at most 498 data bytes, all multi-byte fields big-endian. Digest input covers the full body with its digest field zero, including padding. Failed recognition restores the received digest bytes and leaves the running SHA-1 context unchanged.

Each authenticated adjacent link carries modern fixed 514-byte cells: a four-byte channel-local circuit identifier, one command byte and 509 body bytes. Each Noise transport record therefore contains 514 plaintext bytes and a 16-byte tag, prefixed by a two-byte little-endian ciphertext length. Circuit identifiers are independently drawn from native entropy and use the connection initiator’s high-bit half. The first hop uses CREATE2/CREATED2. Later hops use protected EXTEND2 in RELAY_EARLY and EXTENDED2. An EXTEND2 contains only the next Ed25519 identity and its ntor transcript; the relay resolves its endpoint from its own explicitly approved descriptor. This directory-based link-specifier adaptation does not claim Tor interoperability.

Ownership, bounds and failure

Client selection requires three approved relay identities, pairwise distinct identities and declared families, and the same selected federation. Each relay owns only its adjacent channels, its own hop keys and a bounded forwarding mapping. No full route or original application header is attached to every hop. Native operator commands may open listener channels 0 and 2 to support two simultaneous ingress circuits; outgoing channels 1 and 3 remain available. There are four channel banks, one circuit per channel, one immutable output record per channel and one retained opaque terminal chunk. Backpressure retains an undecrypted input so retry cannot spend its CTR state twice. The pump rotates channel priority and admits at most one frame per channel per quantum. Each adjacent channel binds the selected responder’s signed byte/work allowances at admission. Both directions count the complete length-prefixed Noise wire record; each record spends one work unit, including the fixed handshake records. Exceeding either allowance destroys the route. These are per-channel admitted bounds, not monetary charges, civil-time expiry or an operator-wide durable balance. Reboot does not preserve an ephemeral circuit allowance.

DATA circuit windows start at 1000 and increment by 100. The engine retains at most ten expected authenticated SENDME digests and ten pending acknowledgments per direction. SENDME checks version 1 and the actual rolling digest; duplicate or unexpected acknowledgments fail. Control cells do not spend DATA credit. Each circuit admits one nonzero endpoint stream. Its independent directional package and deliver windows start at 500 and replenish by 50 through empty nonzero-stream SENDME cells. Transit hops do not allocate endpoint stream credit. A second stream requires a fresh circuit. Circuit and stream acknowledgments have control priority while DATA is blocked; stream acknowledgments for an unknown stream or an already-full package window fail. RELAY_EARLY is capped at eight per circuit. Each cipher direction expires before 2²⁰ cells; setup has a finite scheduler-work deadline, not a civil-time promise. Unsupported extension, integrity failure at a terminal hop, stale descriptor, channel loss or exhausted authority produces unavailable and destroys circuit authority. No branch selects mode 3 as a fallback.

Terminal BEGIN carries only an explicitly approved mailbox Ed25519 identity inside the circuit. The final relay opens its adjacent authenticated mailbox channel and proxies records encoded as marker 4d, stream ID 2, length 2 and at most 498 opaque bytes. Those bytes carry an independent client-to-mailbox NoiseNK session bound to the mailbox descriptor; the final relay’s adjacent channel key cannot authenticate that session’s answers. Native mailbox/request authorization must additionally be applied inside that terminal session. Ciphertext forwarding is not a receipt for durable storage, decryption or reading.

Finite durable acceptance receipts

A receipt key is an independent scoped pure-Ed25519 role-4 key. Its 128-byte typed declaration binds the public key, accepted node-certificate SHA-256, key generation and retention contract; the accepted node’s role-3 identity certifies that body with purpose 3. The complete declaration certificate is 352 bytes. A client obtains the full 480-byte selected node certificate through the current terminal owner’s operation 47, matches its SHA-256 to the selected pin, verifies the declaration under that node’s key and verifies the receipt under the declared receipt key. An unrelated self-signed receipt key is insufficient.

Identity operation 409 issues finite, revocable authority to the exact current registered Mailbox incarnation and exact IPC-binding generation. It binds SHA-256 of the canonical terms hash concatenated with the node-certificate hash and consumes one allowance before signing a fixed 192-byte body. The body contains magic 0x315250544c, schema 1, accepted 1, original full service incarnation, request commitment, ciphertext commitment, terms hash, node-certificate hash, ciphertext byte length, durable publication generation, bounded-retention contract 1 and a zero reserved word. Its signature is 64 bytes. The canonical terms are eight little-endian 64-bit words [1,1,8388608,65536,8192,16,8,1]: schema, mode, maximum recipient bytes, maximum accepted operations, maximum envelope bytes, resident records, recipients and retention contract. Per-recipient admission may be stricter. There is no civil-time expiry, reading proof or settlement claim.

Mailbox first publishes opaque ciphertext durably, obtains the admitted asynchronous native signature, then durably publishes the exact cached body and signature before returning stored acceptance or exposing the record for fetch. An exact retry returns the same cached 256-byte receipt even after the finite signer allowance is exhausted. After an explicitly unlocked whole-guest restart, cached signatures retain the original service incarnation and publication generation; fresh signing requires a new current grant. An unsigned pending record never had an accepted receipt and is durably rebound before fresh signing. Profile replacement is refused while retained records or receipt tombstones remain. The outer operator record and inner Identity blob use RFC8439 ChaCha20-Poly1305 with native random 96-bit nonces; their credential-derived SHA-256 keys use separate fixed domains. This assumes a protected high-entropy 32-byte unlock credential, trusted native owner and disclosed compiler/runtime; it is not a password-hardening or external rollback-freshness mechanism.

Memory and assurance

AES has a caller-owned 576-byte context, SHA-1 a 128-byte context and 704-byte scratch, SHA3/SHAKE a 224-byte context and 256-byte scratch. Ntor uses serialized scratch at 0x6c0000, 8192 bytes, and a 256-byte temporary client state. A hop context is 2560 bytes at 0x6d0000 with 4096-byte spacing; hop scratch begins at 0x6d8000. Four channel banks occupy 0x6e0000..0x6effff; router state occupies 0x6f0000..0x6fffff. Existing transport at 0x640000 and relocated Ed25519 scratch at 0x6b0000 are disjoint. Existing X25519 scratch remains serialized at 0x630000. Circuit teardown clears channel banks, hop contexts, temporary ntor state and serialized ntor/hop scratch. Per-cell padding clears its temporary SHA3 state after producing the output. The compiler emits sensitive-frame erasure for the new crypto, router and terminal namespaces; this is an explicit compiler policy with inspected emitted code, not a verified erasure or timing theorem. No yield or cross-service call may preserve an unbanked cryptographic workspace.

The AES implementation uses a lookup table indexed by secret state. Neither it nor this compiler has a constant-time proof or independent cryptographic audit. Primitive and transcript comparisons execute the actual compiled RV64 code and compare NIST fixtures, the published Arti ntor-v3 transcript, OpenSSL X25519/AES and independent SHA implementations. Focused flow checks carry 600 actual DATA cells through independent sender/receiver contexts with reverse authenticated circuit and stream acknowledgments. Live record admission and pin-approval guards call the proved TorPolicy.recordAllowed and NodeEnrollmentPolicy.pinAccept predicates; these narrow lemmas do not prove the entire dispatcher or cryptographic implementation. Cross-backend vectors establish selected functional observations only. A local three-relay execution does not establish independent operators, resistance to global traffic correlation, hostile-government resilience, post-quantum messaging or a verified source-to-binary bridge.

Terminal reset and fresh routing

This profile has one serialized protected client context per mailbox Network owner, and one terminal stream per circuit. Concurrent personal terminal clients at the same mailbox are unavailable. An accepted adjacent connection consumes the selected listener slot. Switching personal guests therefore uses explicit native stop/listen and fresh-route handoff on the selected operators. Operation42 clears the local terminal and its authenticated owner; it cannot resume the peer’s previous inner Noise epoch. Before opening a new terminal after cancellation, broker replacement or a terminal failure, use the supported circuit stop35 and reconstruct the selected approved route, then start the terminal again. A local clear followed by a fresh NK handshake on the old stream is unavailable; it is not a direct-mode fallback. The operator commands onion stop, onion listen, onion route and onion terminal perform these native operations. Explicit selected Registry configuration is reapplied on the terminal operator after its reset. Personal ciphertext retries remain owned by Messenger and are not recreated by route setup.
