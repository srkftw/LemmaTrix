Native Feed and federation operation

Feed is a signed native graphical package with a separate account/network owner. Identity holds author seeds; each federation owns its native event service, moderation key, storage and finite policy. Host tools compile/package, configure public pins and supply opaque devices. They do not sign Feed events, choose moderation outcomes, replicate events or maintain a social database. Execution results and remaining acceptance work belong to the Campaign009 record; this guide describes the implemented interfaces.

Build and install

./lt build
./lt feed package --publisher-private tests/keys/development-rsa.pem --output build/feed-packages
./lt feed vault-init build/feed-personal.img
./lt run --backend qemu --image build/live/guest.bin --socket build/feed-personal.sock --graphics build/feed-personal.qmp --display gtk --network-mux --vault build/feed-personal.img
# Run subsequent commands in another terminal while this guest remains running.
./lt feed --socket build/feed-personal.sock start --identity build/feed-packages/identity.ltrel --owner build/feed-packages/feed-account.ltrel --ui build/feed-packages/feed.ltrel --public tests/keys/development-rsa-public.pem --federation 1111111111111111111111111111111111111111111111111111111111111111 --peer 2222222222222222222222222222222222222222222222222222222222222222

The example RSA key is the existing disclosed development release bootstrap. Select your own package publisher and public pin for another trust root. This does not generate a Feed author key. Press F2 in the native Feed window to create that separately scoped key. Omitting the backing gives an ephemeral personal session. Attaching a backing alone does not authorize retention. The printed owner and UI instances are full live incarnations; use those exact values in commands below.

Feed uses three ordinary slots including Identity. Messenger's separate owner, UI and delivery coordinator, plus one Registry, can coexist within the eight ordinary slots. Initialize and certify Messenger before starting Feed when using the existing temporary-contact-signer helper. That helper deliberately refuses an already bound Identity owner. Feed does not share Messenger ratchet/contact keys or its domain 2 retention.

Federation operators

Repeat this sequence on each operator's own guest and fresh backing. The second operator exchanges the two Feed federation IDs in federation-start and uses its own namespace, family, endpoint and certificate path. The node declaration's public routing federation/scope are separate from the Feed author's community scope; use the same routing federation/scope for the approved route declarations. These hexadecimal IDs are public configuration, not shared secrets. An operator's native credentials come from its own guest entropy.

Wait for a three-hop route and authenticated terminal before publishing. Terminal NK authenticates the selected service; it does not authenticate a human. Remote events require their own application signatures. A route failure is visible as unavailable/reconciliation required. Feed never substitutes direct bulk access for a mode 1 client request. Selecting a different destination deliberately requires closing that personal route, revoking its old slot 3 approval with onion revoke --peer 3, then staging and approving the selected certificate. An unexpected replacement is refused. This changes only that personal client's route; the shared relay and destination listeners continue running.

On each federation, stage and approve the other operator's role 16 certificate in peer slot0. The following relationship explicitly permits direct encrypted inter-operator mode 3 on a distinct numeric endpoint. It cannot satisfy a personal mode 1 request. Both sides select the same public replication scope and endpoint, with their own independent credentials and finite grants:

./lt feed --socket build/feed-a.sock replication --peer 0 --side server --endpoint 127.0.0.1:39200 --scope bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb --bytes 16777216 --rate 65536 --lifetime 100000 --auto-renew

./lt feed --socket build/feed-a.sock replication-status
./lt feed --socket build/feed-b.sock timeline --cursor 0

The native services continue after these management commands exit. Replication preserves the author's exact signed 480 bytes and checked content. Only a signed home-plus-selected-peer audience is eligible. Before granting Network access the service commits a conservative allocation of at most 1 MiB from its selected total (at most 16 MiB); unused allocations are burned after restart. Each outgoing event reserves its complete worst-case byte/work allowance and each of at most 9 attempts is committed before transmission, with at most 128 acceptance polls per attempt. Repeating an existing live configuration returns its current grant. The policy hash binds exact peer, service descriptor, scope and limits; changed configuration requires a distinct explicit policy rather than silently refilling the old allowance. Local-only posts, reports, appeals and federation decisions do not become public merely because a peer relationship exists. Each live inter-operator grant lasts at most 100000 local work ticks. The explicit --auto-renew option selects rolling policy variant 2: native code commits another allocation of at most 1 MiB from the same durable total before replacing an expired grant. It preserves policy hash, event reservations and charged attempts; it never renews the total allowance. Exhaustion, pin revocation, failed grant admission or failed storage latches a visible stopped state. Idle leases can consume allocations too. Legacy 120-byte manual policies remain manual and require explicit unchanged-policy renewal after phase 6/reason 3; adding rolling consent to an existing manual ledger is refused with 11. These variants describe replication policy, not unavailable transport mode 2. Personal mode 1 admission, reads and unrelated Messenger/Forge service continue independently.

To stop the rolling relationship, use ./lt network remove --socket build/feed-a.sock --slot 0 or revoke its enrolled peer with ./lt onion --socket build/feed-a.sock revoke --peer 0. A single Network grant revocation is narrower than the independently approved rolling policy. Relationship removal/revocation can conservatively burn one final allocation before fresh admission fails; the native failure latch then stops allocation. Restoring service requires current explicit configuration and peer approval.

Typed SDK and publication contract

FeedSDK encodes service operations 491 (bounded event begin/append/commit/poll, cursor timeline and checked body chunks); FeedAccountSDK supplies owned asynchronous UI operations 480; FeedRetentionSDK reaches the explicitly approved typed Vault records 277–279. The account status response is 160 bytes: a 64-byte header plus a 32-byte public key and two 32-byte public scopes. The account, UI and federation packages are version 0.9.1; Identity remains version 0.9.0. For an existing 0.9.0 account installation, package with --account-parent CURRENT_ACCOUNT_RELEASE_ID. Native Launcher requires that exact active predecessor and a newer version; it refuses an unlinked replacement. Administrative 490 is separately bound to Launcher. Its read-only actions 13 and 14 expose rolling authority and exact per-event flags, attempts and reservations; the CLI provides replication-authority. The federation package is version 0.9.1; pass --federation-parent CURRENT_FEDERATION_RELEASE_ID when upgrading an existing 0.9.0 installation, independently of the account parent. For the UI use --ui-parent CURRENT_UI_RELEASE_ID. Each parent names that component’s exact current release. The UI delegates only the 31 rights it holds on a newly forked root. Feed terminal dispatch supplies a native origin and full Network incarnation; a stage handle alone cannot authorize another context's append, cancellation or result collection.

For a retained account UI upgrade, first approve retention and lock with F1/F6. Stop only this personal route with ./lt onion --socket build/feed-personal.sock stop, then stop the old UI and account owner using ./lt ctl --socket build/feed-personal.sock stop OLD_INSTANCE for each printed instance. Start the admitted packages again, approve retention for the newly printed owner, and use F1/F3 with the selected credential. Rebuild only that personal route and authorize its terminal for the new owner. F5 then reconciles authenticated known history before new publishing. The account pins its UI incarnation; a replacement UI does not inherit the old UI’s access. Shared relay/federation listeners continue without reset. An ephemeral account without approved retention intentionally cannot recover its old key.

An event is the original 480-byte native Identity envelope: a 160-byte domain/role/purpose/key-generation framing, canonical 256-byte body and Ed25519 64-byte signature. Its identity is SHA-256 of those exact 480 bytes. The canonical body binds format/version, kind, monotonic author sequence, causal parent, body SHA-256/length, untrusted author time, author federation and selected peer audience, immutable project root, target and action. Bodies are at most 16384 bytes and use checked 512-byte chunks. Forwarding does not replace the signature or make the replica its author. Chronological browsing uses the selected service's local reception order; author time is untrusted metadata and work ticks are not global civil time.

Accepted means the immutable content segment and the smaller metadata index have both committed. The writer preserves readable committed state while another upload waits. Exact duplicates return the existing commitment before quota charging, independently of a dead transport generation. Conflicting author sequence reuse returns 12; stale known key generation 15; invalid signature/schema/text returns 10; forbidden audience returns 11; missing parent or invalid policy lifecycle returns 14; finite allowance/storage exhaustion 4. A service operation 491 commit response of 6 means pending work, not durable acceptance; the UI displays accepted only after checking the committed receipt. No compaction or infinite history is claimed by this finite 64-event profile.

Reports, decisions and appeals

The selected federation's native service signs a decision only under its independently created role 6 moderator key, configured policy version, exact target, reason and supersession. A report is required before hiding; an appeal and preceding decision are required before an upheld/reversed result. This profile submits private reports and appeals to the author identity's home federation; private appeals by a remote-home author to the other federation remain unsupported. Reports and appeals are readable only through the intended federation's administrative path; ordinary timeline/body access refuses their private contents.

./lt feed --socket build/feed-b.sock timeline --moderator --cursor 0
./lt feed --socket build/feed-b.sock read --moderator --event REPORT_EVENT_ID --offset 0 --bytes 512
./lt feed --socket build/feed-b.sock moderate --target ORIGINAL_EVENT_ID --action hide --reason "Chosen federation policy: review requested"
# After an actual native author appeal:
./lt feed --socket build/feed-b.sock moderate --target ORIGINAL_EVENT_ID --action reverse --reason "Appeal reviewed: original decision reversed"

The host command requests an outcome from the authorized native moderator consumer; it does not construct or sign the decision. Native validation enforces the lifecycle and exact command retry. The other federation keeps its own visibility policy, and a reversal never clears a user's local block. Imported policy material confers no moderator credentials.

Retention, recovery and approved portability

First independently unlock Objects domain 3 with its own approved credential, then select the exact account owner. In Feed press F1. F2 selects create/retain, F3 recover, F4 optional preference inclusion, F5 confirms the masked 64-hex-digit unlock credential, F6 locks, F7 forgets, F8 exports public portable state, F9 imports a staged public profile. Escape leaves this panel.

./lt ctl --socket build/feed-personal.sock vault unlock --key OBJECTS_DOMAIN3_CREDENTIAL_FILE
./lt feed --socket build/feed-personal.sock authorize-retention --owner FEED_ACCOUNT_INSTANCE
# Use native F1/F2, type the separate Feed unlock credential, then F5.
./lt feed --socket build/feed-personal.sock ui-status --ui FEED_UI_INSTANCE
# After an explicit native F1/F8 public export:
./lt feed --socket build/feed-personal.sock export-profile --ui FEED_UI_INSTANCE --output build/approved-feed-profile.bin
./lt feed --socket build/destination.sock stage-profile --ui DESTINATION_FEED_UI_INSTANCE build/approved-feed-profile.bin
# Inspect destination scope, then explicitly approve F1/F9 there.

The typed retained record keeps public identity metadata, the sealed author key, exact pending signed event/body and necessary sequence state. Optional preferences are separately selected. F4 explicitly includes local follows/blocks in retention and the approved plaintext portable object; without that opt-in they are omitted. This profile exports the latest public event reference, not a complete history or private policy archive. Raw seeds never enter the UI, ordinary Objects records, public exports, host key files or debug output. Published plaintext may intentionally persist at recipient federations. Lock clears accessible keys and revokes the selected storage grant; recovery requires fresh authorization. A service replacement inherits neither a live handle nor a grant. Recovery remains reconciliation-required until an authenticated selected service supplies checked known author history; an empty destination cannot establish publishing freshness. The current signer generation must exceed known history, and the exact pending commitment is preserved while reconciling.

Ordinary Objects records retain an eight-record/256 KiB subquota within the unchanged aggregate 24-record/1 MiB owner allowance. Project graph records count against the aggregate but do not consume that ordinary subquota; account export therefore remains available after a permitted Fork. Creation retains its 64-grant owner bound; delegated recipients retain their separate 32-grant bound. Physical storage remains 64 records.

Moving hosting within the same identity scope uses the retained author and a willing destination's independent admission; the old host need not be online. A public profile alone is not a publishing credential. Public-profile import can restore approved references/preferences into a separately created destination account; it does not automatically certify a cross-federation identity link. Older whole-backing replacement lacks an external freshness anchor. Conflicting sequence reuse is refused against authenticated known history; unknown rollback cannot be detected by local counters alone.

For operator restart, explicitly retain both its native node credentials and moderator seal before shutdown. Keep the native moderator public value printed by federation-start. Retain command credentials are unlock material, not unwrapped native identity seeds:

Finite resources and assurance

A relay has twelve routed channels, enough for six incoming/outgoing pairs; ordinarily one pending listener and one outgoing reserve leave five active pairs. The sixth consumes the last pair; replenishment waits for reclamation. An idle listener starts its finite handshake deadline when a connection is accepted. Actual listener-command failures retire only that listener and retry at most 32 times with bounded backoff (200, 400, 800, 1600, then 3000 work ticks); diagnostic 58 reports this condition. An explicit operator listen can authorize a new retry allowance. Ordinary client disconnects do not consume that operator allowance. Four bulk contexts are separate. Sixteen terminal banks remain bounded by the twelve possible links. Mailbox has four 8 KiB upload stages and one finite writer; Feed has four 16 KiB stages, seven 128 KiB content segments and a 37888-byte committed metadata index. A federation admits at most 64 events/896 KiB and 16 events/256 KiB per author, tightened by selected operator budgets. Quota exhaustion is explicit; there is no infinite history or automatic compaction claim. ServerStore has eight namespaces, all occupied by this federation profile, so run its backing independently of a mailbox namespace.

Relay setup uses 100000 work ticks and moving transport a 30000-tick progress bound. Terminal contexts independently bound partial frames and admitted IPC tokens to 10000 ticks, and handshake/whole queued request work to 100000 ticks. Pending polls do not renew these bounds; healthy idle authenticated sessions remain reusable. Timeout cancels only the owned token, wipes its working/saved keys and buffers, and retires the matching channel epoch and dependent pair. Mailbox stages separately enforce 10000-tick progress and 60000-tick absolute bounds. Work ticks are not trusted civil time.

Event format 1 has an explicit signature domain, author generation, stable hash identity, bounded causal references, untrusted author time, exact body commitment and signed audience. Service reception order and work ticks are not trusted civil time. Invalid signatures/text/version/size, unauthorized audiences, conflicts, missing parents, stale generations and finite quotas have explicit refusal paths. A retry with the same exact event reconciles durable acceptance independently of a dead terminal generation.

Services are voluntary and zero-price. Wallet/LemmaCoin, payment settlement, small private Messenger groups, modes 2/4, arbitrary exits and public share-page deployment remain separate work. Classical native cryptography and local three-hop execution do not establish post-quantum security, Tor interoperability, global correlation resistance or hostile-state resilience. Independent operators, physical hardware, side channels, full-store freshness and independent security review remain open assurance obligations.

Each authenticated terminal context pins the full native incarnation of its primary service separately from the Registry inspection target. Replacing that service retires the affected context before another request is dispatched; a fresh approved terminal relationship is required. This transport pin does not identify a human or bind durable recovery to a dead context. A current authorized session can still reconcile an exact committed application operation.
