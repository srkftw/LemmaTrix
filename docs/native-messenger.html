Native Messenger and enrolled LemmaNET operation

Campaign008 development guide, 31 October 2026. The executable implementation and the identified acceptance executions are separate evidence. This guide describes local native services and their supported commands; it does not declare MSG-001, RG-07 or the public MVP complete.

Build and install

./lt build
./lt messenger package --publisher-private tests/keys/development-rsa.pem --output build/messenger-packages
./lt messenger vault-init build/alice.img
./lt run --backend qemu --image build/live/guest.bin --socket build/alice.sock --graphics build/alice.qmp --display gtk --network-mux --vault build/alice.img
./lt messenger --socket build/alice.sock start --owner build/messenger-packages/messenger-session.ltrel --ui build/messenger-packages/messenger.ltrel --public tests/keys/development-rsa-public.pem

The example creates a fresh sparse backing before first boot. Attaching it grants no personal retention consent. For fully volatile operation, omit vault-init and --vault; restart then loses the messaging device. The checked-in RSA key is a disclosed development package publisher, not a messaging identity. Use an explicitly selected publisher key and its public pin for a different trust root. Host compilation and package signing are bootstrap operations. Each installed native secret owner independently creates its messaging keys from checked entropy draws; those keys do not pass through this command.

A personal guest occupies three of eight ordinary slots: rights-zero session owner, graphical Messenger with mediated Objects rights799, and rights1024 delivery coordinator. A local native Registry verifier adds one slot when inspecting signed project references. The UI has no raw networking, signing, block-device or personal-vault mount right. The coordinator receives ciphertext and scoped mailbox capabilities, never ratchet keys or attachment plaintext.

Before creating the device, select its federation with the native graphical configuration command below, then press F2 in Messenger. A separately scoped Identity role2 key certifies the independent XEdDSA identity and device. The temporary signer has only three exact management grants and is stopped after committing its public certificate. Admit the coordinator afterward. The shared-service image provides 96 exact operation grants for the combined Messenger/Feed configuration:

./lt messenger --socket build/alice.sock configure --ui ALICE_UI_INSTANCE --federation FEDERATION_HEX
# In the native Messenger window, press F2.
./lt messenger --socket build/alice.sock certify-contact --identity-release build/messenger-packages/identity.ltrel --public tests/keys/development-rsa-public.pem --scope CONTACT_SCOPE_HEX --output build/alice.invitation
./lt messenger --socket build/alice.sock delivery-start --release build/messenger-packages/messenger-delivery.ltrel --owner-release build/messenger-packages/messenger-session.ltrel --ui-release build/messenger-packages/messenger.ltrel --ui ALICE_UI_INSTANCE --public tests/keys/development-rsa-public.pem

The672-byte certified invitation contains the XEdDSA bundle, selected mailbox deposit material and a352-byte Identity certificate. The certificate binds IK, device, selected federation and fingerprint; it does not replace the XEdDSA prekey signature. Certification does not establish civil identity. F3 exports the native invitation, F4 imports it, and F5 or the approval pointer control approves its displayed fingerprint. Legacy unbound invitations are visibly identified and cannot replace an already certified contact. After selecting a mailbox, export again so the invitation carries the current selected pin.

Repeat the personal start, federation, certification and coordinator steps on Bob’s separate guest and backing. Each device creates its own native keys and exports its own public invitation. Repeat the selected-service approval steps on both personal guests.

Separate relay and mailbox operators

Run the following sequence independently on each operator's own guest and backing. Substitute its socket, numeric endpoint, family declaration and output certificate. Repeat for three relays, then use kind mailbox on the fourth operator. Federation, scope and family arguments are nonzero32-byte hexadecimal identifiers. Family declarations are selection constraints, not evidence of independent administration.

./lt server-store init build/relay1.img
./lt run --backend qemu --image build/live/guest.bin --socket build/relay1.sock --network-mux --server-store build/relay1.img
./lt identity --socket build/relay1.sock start --release build/messenger-packages/identity.ltrel --public tests/keys/development-rsa-public.pem
./lt onion --socket build/relay1.sock create --kind relay --federation FEDERATION_HEX --scope SCOPE_HEX --family FAMILY1_HEX --endpoint 127.0.0.1:39001 --bytes 8388608 --work 65536 --output build/relay1.certificate
./lt onion --socket build/relay1.sock retain --key OPERATOR_UNLOCK_CREDENTIAL_FILE
./lt onion --socket build/relay1.sock listen

The explicit unlock credential file contains32 high-entropy bytes, not an exported native seed. Retention encrypts the operator's static transport/onion private scalars and signed certificate in purpose2 sectors1–6. Existing ServerStore roots8–23 and ServiceJobs public receipt keys56–63 are disjoint. After an actual operator restart, run onion recover --key … before listening and explicitly re-enroll adjacent public peers. Active channel/circuit state never resumes. Static-only retention leaves the Identity certification seed ephemeral. On a mailbox operator, use the native receipt setup below and then retain with both selected handles. Identity seals its independent node-certification and receipt-signing seeds into an opaque192-byte blob; Network stores that blob alongside its own static keys. Neither the UI nor the host unwraps a native seed. On recovery, start Identity first; onion recover restores fresh public handles through Identity408. Losing an unretained signer requires a new declaration and explicit pin replacement.

On the mailbox guest, additionally install its native queue owner and select its intentional storage namespace:

./lt messenger --socket build/mailbox.sock mailbox-start --release build/messenger-packages/mailbox.ltrel --public tests/keys/development-rsa-public.pem --namespace NAMESPACE_HEX
./lt messenger --socket build/mailbox.sock mailbox-receipts --identity-release build/messenger-packages/identity.ltrel --mailbox-release build/messenger-packages/mailbox.ltrel --node-key NATIVE_NODE_HANDLE --authorizations 4096 --output build/mailbox.receipt-profile
./lt onion --socket build/mailbox.sock retain --key OPERATOR_UNLOCK_CREDENTIAL_FILE --node-key NATIVE_NODE_HANDLE --receipt-key NATIVE_RECEIPT_HANDLE
./lt messenger --socket build/mailbox.sock mailbox-inventory

onion create prints the native node handle; mailbox-receipts prints the independently generated native receipt handle. After a mailbox restart, recover the sealed keys and configure a fresh finite receipt authorization using those restored handles before deposits. The unchanged public receipt profile and historical receipts remain verifiable; the exact service-incarnation grant does not survive restart. The management command installs exact caller/package/service/operation/generation bindings. Native Network may invoke only mailbox441; its administrative enrollment/inventory operation440 remains separately bound to Launcher. Bare attachment of a backing does not authorize personal retention or operator credential recovery.

For a restarted mailbox, start Identity and the same mailbox package/namespace first, then recover rather than create new operator credentials. Read the fresh restored_identity_handles.node_key and receipt_key from the native recovery result and substitute them below:

./lt onion --socket build/mailbox.sock recover --key OPERATOR_UNLOCK_CREDENTIAL_FILE
./lt messenger --socket build/mailbox.sock mailbox-receipts --identity-release build/messenger-packages/identity.ltrel --mailbox-release build/messenger-packages/mailbox.ltrel --node-key RESTORED_NODE_HANDLE --receipt-key RESTORED_RECEIPT_HANDLE --authorizations 4096 --output build/mailbox.receipt-profile
./lt onion --socket build/mailbox.sock listen

Approve public services and contacts

./lt onion --socket build/alice.sock stage build/relay1.certificate --peer 0
./lt onion --socket build/alice.sock approve --peer 0 --fingerprint ACCEPTED_CERTIFICATE_SHA256
./lt onion --socket build/alice.sock stage build/relay2.certificate --peer 1
./lt onion --socket build/alice.sock approve --peer 1 --fingerprint ACCEPTED_CERTIFICATE_SHA256
./lt onion --socket build/alice.sock stage build/relay3.certificate --peer 2
./lt onion --socket build/alice.sock approve --peer 2 --fingerprint ACCEPTED_CERTIFICATE_SHA256
./lt onion --socket build/alice.sock stage build/mailbox.certificate --peer 3
./lt onion --socket build/alice.sock approve --peer 3 --fingerprint ACCEPTED_CERTIFICATE_SHA256
./lt messenger --socket build/alice.sock select-mailbox --fingerprint MAILBOX_CERTIFICATE_SHA256

Each relay separately approves only its selected next service: relay1 approves relay2, relay2 approves relay3, relay3 approves the mailbox. Ordinary clients never provision all private operator keys. An active pin accepts only a newer same-identity, same-federation/scope declaration. Explicit revocation followed by a new fingerprint approval permits identity replacement. Replayed generations, wrong staged fingerprints and active identity substitution fail closed.

In Messenger, F2 creates a local device. F3 exports its invitation; F4 imports the public invitation as hexadecimal. The management stage-contact command may transport that public invitation to the native UI, but approval still requires inspecting the actual fingerprint and pressing F5 or clicking its approval control. F6 blocks the selected device. A changed identity or mailbox capability is rejected rather than silently replacing the contact. Invitations certify device key material; a fingerprint comparison does not establish a person's civil identity.

./lt messenger --socket build/bob.sock export --certified --output build/bob.invitation
./lt messenger --socket build/alice.sock stage-contact --ui ALICE_UI_INSTANCE build/bob.invitation
./lt messenger --socket build/bob.sock mailbox-authority --output build/bob.mailbox-authority
./lt messenger --socket build/mailbox.sock mailbox-enroll build/bob.mailbox-authority --bytes 1048576 --attempts 256

The96-byte mailbox enrollment material contains a random recipient identifier and separate deposit/fetch capability commitments. It contains no conversation name, message text or private project title. The extended or certified invitation conveys the deposit capability and selected mailbox pin to the intended contact. Fetch authority stays with the recipient secret owner and its narrowly bound coordinator.

Send, receive and inspect

Before stopping Bob’s whole guest, explicitly authorize and create his retained Messenger protocol state through the separate domain2 steps below. Ephemeral operation loses the private prekeys and session on restart. Construct Bob’s own approved route and terminal while his session owner is unlocked. The native coordinator publishes his authenticated prekey bundle automatically. Repeat the read-only status command until prekeys_published is true; a nonzero publication reason is a failure requiring correction before offline delivery:

./lt onion --socket build/bob.sock route
./lt onion --socket build/bob.sock terminal --peer 3 --owner BOB_DELIVERY_INSTANCE --bytes 1048576 --attempts 4096
./lt messenger --socket build/bob.sock delivery-status

Then lock Bob with F8. Alice can construct her independent route while Bob remains admitted. Bob may also stop his own guest; Alice’s offline deposit uses the mailbox’s durably published prekey material.

./lt onion --socket build/alice.sock route
./lt onion --socket build/alice.sock status
./lt onion --socket build/alice.sock terminal --peer 3 --owner ALICE_DELIVERY_INSTANCE --bytes 1048576 --attempts 4096
./lt onion --socket build/alice.sock status

The coordinator publishes the authenticated public prekey bundle and claims the chosen contact’s public prekey through the protected mailbox before an initial session send. A stable claim retry returns the same material; a public claim alone never deletes a private prekey. The secret owner validates the claimed device and signature and commits it before encryption. The circuit must report three constructed hops and the inner terminal must authenticate the selected mailbox fingerprint before sending. Type text into Messenger and press Enter. While a text send is admitted, contact navigation waits for its bounded outcome so that handles and delivery evidence remain attached to that contact. The text gesture may preempt a read-only attachment fetch poll; it cannot interrupt attachment encryption, authentication or durable publication. F7 retries the exact committed ciphertext; Escape cancels bounded local work and reports uncertainty when remote acceptance may already have occurred. PageUp/PageDown select contacts. A missing or broken route is unavailable; required mode1 never selects direct mode3. Explicit bulk applications retain their separate mode3 broker profile. Modes2 and4 remain unavailable.

Delivery labels distinguish local queued work, durable mailbox storage, and authenticated recipient commit. Mailbox acceptance is not a read receipt, independent verification or settlement. Its native zero-price terms count bytes and work/attempts across restart; they do not promise civil-time expiry. The canonical64-byte terms profile is eight little-endian words: 1,1,8388608,65536,8192,16,8,1 (schema, mode, maximum recipient bytes, maximum accepted operations, maximum envelope bytes, resident records, recipients, bounded-retention contract). SHA256 is ad3d1ca92a3d4bd84b678167fc4caf418b4a40d481a8595c409afa5922853588. Actual enrollment can tighten the recipient limits. Mailbox configuration rejects a different terms commitment. Receipt verification binds that profile, the accepted node certificate, stable request, exact ciphertext commitment and original service incarnation. Ciphertext publication and cached signature publication both precede signed acceptance. A mailbox can see opaque sizes, capability-authorized queue operations, service times and its adjacent peer. Relays see adjacent endpoints, circuit-local identifiers, cell counts and timing. These observations permit traffic analysis; local three-hop operation does not establish global correlation resistance.

F11 opens the existing trusted Objects picker. The allowed selection is read/share/revoke data, with at most24 nodes,64 KiB per source node and100,352 bytes in the canonical bundle. The UI freezes the selected project root and reads that bundle in512-byte slices. The secret owner encrypts chunks, commits a bounded exact ciphertext batch, and releases only committed chunks to the coordinator. Insert or the received-project import button explicitly imports a received project after authenticated decryption and canonical validation. Receipt alone never imports, installs, executes, seeds or publishes it. At most two attachment keys, sixteen retry chunks per transfer and bounded mailbox batches are resident.

After a personal restart, an outgoing attachment is an uncertain exact-batch retry. Re-select its same immutable project through F11 to resume; native cached plaintext commitments reject a changed source and return the already committed ciphertext. The local chunk-publication counter proves ciphertext availability, not durable remote acceptance. A coordinator restart requires lock, normal recovery and F11 re-selection to rebuild that whole cached batch; F7 alone assumes the current coordinator still holds its assembled batch. Keep the restored transfer’s original contact selected. If the mailbox reports that its receipt window ended, F7 opens a warning showing the actual transfer fingerprint. Escape preserves the uncertain batch; a separate Enter explicitly permits fresh admission of those same bytes and may duplicate delivery after retained history was evicted. Authorization, integrity and conflicting requests cannot use this confirmation. Keep or recover the source separately through its own Objects policy; Messenger retention does not retain the whole source project automatically. An explicitly completed transfer may instead release its key/cache slot with the command below. Cancelling or forgetting a local attachment cannot withdraw an already stored manifest or ciphertext from a recipient.

After completing or cancelling a transfer, explicitly release its local key/cache slot with the exact attachment handle returned by the native attachment API. For a received attachment, inbox --cursor MESSAGE_SERIAL includes that handle in status word5 (counting from zero). The current graphical transfer controls do not release completed slots automatically. The following management command uses the existing exact Launcher434 grant and requires an unlocked owner; native status5 means locked,3 means an unknown/stale handle, and13 means the removal did not commit. It returns the complete native status header as JSON and exits nonzero on failure. Successful removal commits loss of local attachment decryption/retry authority and frees one of the two slots. It does not remove an imported Objects project or already deposited ciphertext.

./lt messenger --socket build/bob.sock inbox --cursor MESSAGE_SERIAL
./lt messenger --socket build/bob.sock forget-attachment ATTACHMENT_HANDLE

A conversation reference has the exact form LT-PROJECT1 ROOT_64_HEX FEDERATION_64_HEX POLICY_DIGIT. F1 or its reference control requests signed metadata through the same protected terminal broker. The existing Forge federation consumer verifies the response using the chosen local native Registry, including immutable root, federation, policy, signature and current admission knowledge. The final relay cannot forge a successful answer. The terminal operator must separately select its actual read-only Registry:

./lt onion --socket build/mailbox.sock registry-terminal --registry NATIVE_REGISTRY_INSTANCE --federation FEDERATION_KEY_ID_HEX

Run this explicit selection before the terminal becomes active, after configuring the existing Registry with ./lt federation … configure. The proxy admits only existing read-only Registry operations6 and7; it has no configuration, admission or signing authority. Registry federation identity is the existing public signing-key commitment, not a claim inferred from a relay family.

Twelve routed channels supply at most six incoming/outgoing relay pairs; four bulk contexts are separate. Mailbox has four independently owned 8 KiB stages and one bounded serial writer. Retention and loss of authority

Create a new sparse personal backing explicitly with ./lt messenger vault-init build/alice.img, then start that personal guest with --vault build/alice.img. The command refuses an existing path and creates no key or authorization. Its reserved Objects prefix remains uninitialized; Messenger consent does not create or unlock an Objects store. An existing personal backing needs the stated minimum capacity and its own independent Objects policy.

Normal operation is ephemeral until separate Messenger-domain consent and unlock. Merely attaching an Objects backing does not authorize domain2. A retained sender needs protocol state and committed outbox/deduplication state; message-history consent is separate. The UI's F9 form accepts a32-byte high-entropy unlock credential as64 hexadecimal digits, with explicit create, normal recovery or history-import selection and history consent. This development profile is not a human-password KDF. Trusted host input and display adapters remain in the threat model.

./lt messenger --socket build/alice.sock authorize-retention --owner ALICE_OWNER_INSTANCE
./lt messenger --socket build/alice.sock unlock --key MESSENGER_UNLOCK_CREDENTIAL_FILE --mode create --retain-history
./lt messenger --socket build/alice.sock lock
./lt messenger --socket build/alice.sock authorize-retention --owner NEW_ALICE_OWNER_INSTANCE
./lt messenger --socket build/alice.sock unlock --key MESSENGER_UNLOCK_CREDENTIAL_FILE --mode recover --retain-history

F8 locks accessible keys and revokes the domain grant. F10 requires explicit forget confirmation. Normal recovery requires matching authenticated commit/nonce publications. Explicit history import first advances and flushes the nonce allocator, then invalidates and flushes both old sending roots on the input copy. It discards old identity, prekeys, ratchets, outboxes, attachment counters and sending authority. A later normal recovery of that copy returns status13, including after lock. Eligible history is an archival view: F2 returns reconciliation-required until you press F8 to clear that history and its cached contact references. Then press F2 for a fresh device, followed by F9/create and renewed contact approval. Old history is never merged into reused contact slots. The allocator remains so creating the new domain with the same credential cannot reuse its old nonces. Preserve any backup separately if it is still needed as a history source. Substitution of an original external whole-backing copy remains undetectable without an external freshness anchor. Lock/forget does not erase external backups, host memory or recipient copies.

Messenger domain2 occupies a fixed1024-sector range beginning5394976 on purpose1, after the indexed Objects extent. Its key and access policy are independent from Objects domain3. Wallet domain1 remains denied. Both personal and operator recovery are explicit boot/unlock operations, not automatic mounts.

Bounds and remaining assurance

The current shared-service image has eight ordinary slots, six service roles,96 exact operation grants, sixteen opaque transport channels and2MiB ordinary private arenas. The current ABI extension records their exact layout; Campaign008 used the preceding five/four/32/four profile. The built-in Network code allocation is explicitly416 KiB within its existing512 KiB physical slot; ordinary packages retain256 KiB. Secret-bearing compiler returns clear their fixed spill frames. This is an audited lowering policy, not a verified compiler or a constant-time guarantee. AES uses a secret-indexed substitution table. Host compromise, side-channel resistance, physical ARM hardware, independent operators, Tor interoperability and production deployment remain unqualified. A full installed Messenger check on the emulated AArch64 backend timed out during bounded host package inspection before UI startup; representative compiled checks passed, while full installed operation there remains unqualified. Classical X3DH/Double Ratchet is not post-quantum.
