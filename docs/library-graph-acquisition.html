Native Library Game graph acquisition

The separate LibraryFetch package acquires the actual signed Game Project closure through an enrolled seed. The native Library supplies frozen federation admission metadata and a bounded acquisition operation. The recipient does not require administrative preloading of the game's source, executable or level resources. Metadata display, consumer eligibility, executable admission, acquisition consent and local execution approval remain separate decisions.

The fetcher declares Objects rights 127 and network.broker 1024, total 1151; it has no display/input, audio, backing, server.store or vault authority. Its submit/poll/cancel API accepts only the exact current Launcher-bound Library incarnation returned by syscall 119. It copies the selected admission before scheduling work, verifies an actual consumer+executable classification 5 against the selected immutable Project head, checks the chosen seed's signed service description and authenticated positive bulk mode, and obtains its own caller-scoped Network-v2 grant. Its protocol stream is the first eight bytes of the immutable Project head interpreted little endian, OR 1; request IDs are a separate monotonic sequence. Local capability handles never cross the protocol.

Selected provider closure

LibraryGraphServe extends the existing native LibraryPeer package with explicit role 3. An operator delegates one selected Project read root and approves its exact immutable head, peer identity, service, stream, byte budget and lifetime. Preparing the scope traverses only that root's validated closure and caches at most 24 bounded node records. Every response rechecks the exact live root/head before reading. A root update, scope revocation or unavailable node produces a real error. The provider cannot use a supplied ordinal as a capability or arbitrary sector address.

Acquisition job and installation boundary

Fetcher operationContract
710 begin832 bytes: header with seed slot 1 or 2 at +8, unique operation at +16, payload byte ceiling ≤1 MiB at +24; zero remaining arguments; exact 768-byte signed admission at +64. One active operation; an exact repeated begin returns its queryable state, conflicting replacement while running returns busy.
711 inspect/resultExact owned operation. Reply words: status, selected delegated root, state, actual received bytes, declared total, terminal reason, current node ordinal, version 1. States 1 running, 2 ready, 3 cancelled, 4 failed. Completion delegates the exact imported root once, then returns the cached same result. The selected root scope is read/share/revoke/export (89); it does not grant execution approval.
712 cancelExact owned operation. Cancels pending network work, revokes future network authority and aborts unpublished Objects stages. A completed operation remains queryable. A timed-out commit reply is reconciled by ordered lookup of the operation-bound local alias/head, rather than retrying publication or claiming timeout rolled it back.

Each job admits at most 24 nodes and 1 MiB of payload through the existing Import-v1/2 format. The fetcher reserves a fixed 32-KiB private address region, holds one ≤512-byte transfer range plus bounded metadata, and stages payload in Objects. Its derived transport ceiling is twice the approved payload ceiling plus 32,768 bytes for bounded protocol overhead. Network grants and local deadlines use monotonic ticks; the operation deadline is 90,000 ticks. Loss of the selected connection fails the job and reclaims unpublished stages; a retry requires a fresh operation/policy. This small-project path does not claim streamed-media checkpoint recovery.

Every node's expected ID, parent, schema and payload hash enters the private transaction. Objects validates actual payload hashes, canonical node identities, typed dependency closure, quotas and name collisions before publishing one complete root. The existing synchronous final import seal does not yield while its ProjectGraph import scope is active. Registry current-knowledge checks occur before publication and again before handing the result to the Library. This is not a claim of global revocation freshness or asynchronous legacy graph sealing.

The Library checks the exact imported head and current executable admission again before its trusted installation portal. It delegates only the selected read/share/export scope to the actual compositor incarnation; the trusted local approval mediates code installation and declared capabilities. A read/export root does not install an executable by itself. Source-only level packs remain inert content under the game's separate format and scope checks.
