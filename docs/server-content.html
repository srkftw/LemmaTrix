Authorized headless content archive

ServerContent is the positive operator-authority frontend for intentional selected-content retention. The Lean Vault/storage compartment reuses its bounded chunk transaction engine with a separately selected purpose-2 device, separate format magic/domain, explicit namespace, immutable manifest commitment and byte ceiling. This backend intentionally stores authorized operator data in plaintext. It never reads an Objects-vault key and never substitutes plaintext storage for a personal retention request.

The profile retains up to four separately selected complete immutable content roots per backing, each optionally with its exact 1536-byte signed consumer/admission metadata. Four ephemeral operator grants are available. A grant binds the full live owner incarnation, archive slot 0–3, namespace32, expected manifest SHA-256, quota ≤6,029,312 bytes, seed role 2 and the positive encrypted-bulk enum 3. Issuance requires Launcher administrative authority and a recipient with server.store (2048), or the administrator itself. A hash by itself creates no read/retention authority. Restart requires a fresh current operator grant; live capabilities and transport keys are absent from disk.

Personal v3/v4 operations and server operations share one bounded content archive engine in service 3. A busy operation reports status 7; another caller cannot retarget its backend, identity, buffers or current work. Locking the personal vault clears its key/domain state and cancels personal work while authorized server work continues under its distinct namespace policy. Final server publication rechecks the exact current grant, owner liveness, namespace, root commitment and byte ceiling.

Additive storage and integrity

./lt server-store init IMAGE --content exclusively creates a 150,944-sector explicit server backing. The existing format-1 header remains unchanged and its eight one-MiB namespaces continue to use sectors below 33,088. Existing files are never enlarged or silently reformatted. Slot s has separate root sectors 33,088 + s ×29,464 and the following sector; its banks start at 33,096 + s ×29,464 + bank ×14,728. Slot 0 remains readable on the earlier 62,552-sector content backing; higher slots require sufficient explicitly provisioned capacity. A payload-only format-5 index has 512 bytes; format 6 includes the selected signed catalog metadata in a 2048-byte index. Chunk records are 4608 plaintext bytes plus SHA-256, padded to ten sectors.

The immutable signed manifest/Merkle root and the fresh operator grant authenticate the intended content; a provider-supplied checksum is not an admission decision. Recovery checks canonical metadata, namespace/root/quota, exact chunk index/length, record digest and every Merkle proof through the ordinary ContentJobs importer before publishing a complete available root. A writable backing can alter checksums, so the expected manifest commitment is essential. Optional consumer metadata must match the same manifest/content ID/length and signed consumer commitment; its signatures retain their separate registry admission checks.

Retention writes the inactive bank, flushes it, publishes the alternate root and flushes that root. The previous complete generation remains available during interrupted writes. Recovery creates fresh selected read grants for the approved live recipient. A seed must separately acquire its current network role/grants and explicitly bind that recovered content to its serving policy. No arbitrary backing-sector range API is exposed. Metadata-only registries continue to work without owning media payloads.

The Library seed runner provides normal pinned-package configuration, startup, native inspection, stop and recovery commands. Simultaneously recovered payloads share the 6,029,312-byte volatile ContentJobs profile even though each retained archive has its own backing banks. The disclosed adapters only transport explicit setup, selected bytes and requests. Acquisition decisions, chunk verification, asynchronous storage work, namespace policy and publication remain Lean guest code. Physical storage durability, independent operators and larger resource profiles retain separate acceptance work.
